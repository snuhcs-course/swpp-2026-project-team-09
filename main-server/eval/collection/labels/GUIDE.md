# 평가 A·B 라벨 안내

정답은 사람이 원문을 읽고 붙인다. 모델이나 파서가 낸 값을 옮기지 않는다. 먼저 이 문서를 끝까지 읽는다.

## 누가 어떤 파일을 채우나

| 사람           | 파일                             | 양                |
| -------------- | -------------------------------- | ----------------- |
| P05 담당       | `a.owner.yaml`, `b.owner.yaml`   | 글 78건, 쌍 120개 |
| 두 번째 라벨러 | `a.second.yaml`, `b.second.yaml` | 글 15건, 쌍 30개  |

- 파일 맨 위 `labeller`에 GitHub ID를, `labelledOn`에 라벨한 날짜(`2026-10-31` 꼴)를 적는다.
- 두 사람은 **따로** 붙인다. 끝나기 전에 상대 라벨을 보거나 상의하지 않는다.
- 두 번째 라벨러에게는 자기 파일 2개, 이 문서, `places.tsv`, 저장본 폴더 `posts/`만 준다. P05 담당의 라벨은 주지 않는다. `set-a.yaml`과 `set-b.yaml`은 글을 왜 골랐는지 적은 파일이라 답을 짐작하게 하므로 라벨이 끝날 때까지 열지 않는다. P05 담당도 라벨 중에는 열지 않는 것이 좋다.
- 원문은 `url`로 열거나, 사이트가 바뀌었으면 `file`의 저장본(`eval/collection/` 아래)을 연다. 글의 이미지까지 본다. 저장본이 기준이므로 둘이 다르면 저장본을 따르고 `note`에 적는다.
- `null`은 아직 채우지 않은 칸이다. `note`는 비워 두어도 된다. P05 담당은 `pnpm eval:collection:status`(main-server에서)로 남은 빈칸 수를 본다. 이 명령은 일치도도 보여 주므로 두 번째 라벨러는 돌리지 않는다.
- P05 담당은 파일을 고친 뒤 테스트로 형식을 확인할 수 있다: `pnpm exec vitest run --project unit test/eval-collection-set`.

## 평가 A: 글마다

**`announcesEvent`**: 사람이 어떤 시각, 어떤 장소에 가거나 접속해서 참여하는 일을 알리는 글이면 `true`. 채용 공고, 모집 공고, 제출만 하는 공모처럼 함께 모일 시각이 없으면 `false`.

**`sessions`**: 글이 알리는 회차마다 한 줄. 미리 있는 줄은 빈칸일 뿐 정답이 아니다. 회차가 더 있으면 줄을 더하고(`n`을 이어서), 없으면 지운다. 비교과 글에 미리 만든 줄 수는 그 페이지의 강좌 정보 표에 있는 회차 수다. `announcesEvent`가 `false`인 글은 `sessions: []`로 둔다.

회차마다:

| 칸             | 적는 값                                                                                                                                        |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `start`, `end` | 서울 시각 `2026-11-02T10:00`. 날짜만 있으면 `2026-11-02`. 글에 없으면 `none`                                                                   |
| `place`        | `places.tsv`의 `label` 칸 그대로(예: `63 학생회관`). 온라인이거나, 캠퍼스 밖이거나, Place 하나로 정할 수 없으면 `none`                         |
| `overPeriod`   | 전시처럼 정해진 기간 동안 아무 날이나 갈 수 있는 행사면 `true`. 며칠에 걸친 학회처럼 일정이 정해진 것도 기간 전체를 한 회차로 읽을 때만 `true` |
| `mayPublish`   | 아래 기준                                                                                                                                      |

**`mayPublish`**: 이 회차를 이 값 그대로 Global Event로 올려도 되면 `true`. 셋을 모두 만족해야 한다.

1. `announcesEvent`가 `true`다.
2. 시작이 글에서 분명하게 읽힌다(기간형이면 첫날과 마지막 날).
3. 장소가 Place 하나다. **온라인 회차는 `false`다**(2026-10-31 P05 담당 결정). 스펙의 Judgement는 Place 하나에 맞는 회차만 통과시키므로, 온라인을 `true`로 두면 C1의 분모에 자동 발행이 불가능한 회차가 들어간다.

그 밖의 약속:

- **이미 지난 날짜여도 똑같이 붙인다.** 받은 날짜와 무관하게 글의 내용만 본다.
- **신청·접수 기간은 행사 시각이 아니다.** 신청 기간밖에 없으면 `start`는 `none`이다.
- **연도가 없으면** 글의 맥락으로 읽어 적고, 맥락으로도 정할 수 없으면 `none`이다.
- **건물 번호만 있으면**(`301동 117호`) 다른 캠퍼스라는 말이 없을 때 관악으로 읽어 그 번호의 Place를 고른다. 다른 캠퍼스나 학교 밖이면 `none`이다.
- 판단이 어려운 칸은 고르고 `note`에 이유를 적는다. 합의 때 다시 본다.

## 평가 B: 쌍마다

**`sameEvent`**: `a`와 `b`가 같은 때, 같은 곳에서 열리는 **같은 행사**를 알리면 `true`, 아니면 `false`. "모르겠음"은 없다. 판단이 어려우면 고르고 `note`에 이유를 적는다.

- `session`에 숫자가 있으면 그 글의 그 회차만 비교한다. `null`이면 글 전체를 비교한다.
- 한 글이 여러 프로그램을 함께 알릴 때(다대일), 상대가 그중 하나면 `true`다. 예: 어느 축제의 전체 안내 ↔ 그 축제 안의 공연 하나의 안내.
- 여러 회차의 프로그램을 통째로 알리는 두 글은 회차 수가 같으면 `true`다.
- 제목이 달라도 같은 행사면 `true`, 제목이 거의 같아도 다음과 같으면 `false`: 대면 ↔ 비대면, 1차 ↔ 2차, 다른 날 또는 다른 시각의 같은 시리즈, 같은 시각의 다른 행사.
- 같은 때, 같은 곳의 같은 강의가 신청 대상만 달리 따로 올라왔으면 `true`다.

## 끝난 뒤

P05 담당과 두 번째 라벨러가 모두 끝나면 다음 순서로 간다.

1. 네 파일을 그대로 커밋한다. **이 파일들은 원본이다. 이후에 고치지 않는다.**
2. `pnpm eval:collection:status`로 일치도(p_o, κ, 양성·음성 일치, n)를 내서 `../README.md`의 표에 적는다.
3. 어긋난 항목을 두 사람이 토의해 정한다. 무엇을 왜 그렇게 정했는지 `../README.md`에 적는다.
4. `a.owner.yaml`, `b.owner.yaml`을 복사해 `a.gold.yaml`, `b.gold.yaml`을 만들고, 합의로 바뀐 칸만 고친다. 평가는 이 두 파일로 채점한다.
