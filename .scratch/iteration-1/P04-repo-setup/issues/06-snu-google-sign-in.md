# 06: Sign in with an SNU Google account

Parent: [P04 spec](../spec.md)
Status: ready-for-agent
Blocked by: 02 (Data stores and main server connection)

## What to build

An SNU student signs in with their SNU Google account. The app obtains a Google ID token and sends it to the main server. The main server verifies the token, creates the User on the first sign-in and returns an access token and a refresh token. Later requests that carry the access token are recognised as that User. A person with a Google account outside SNU gets a clear refusal.

Refresh and sign-out are ticket 07. The sign-in screen belongs to P06.

## Acceptance criteria

- [x] Sign-in verifies the ID token's signature, audience, expiry, that the email is verified, and that the hosted domain claim equals `snu.ac.kr`.
- [x] The email address alone is not accepted as proof of the domain: a token with an `@snu.ac.kr` email but no matching hosted domain claim is refused.
- [x] A refusal states its reason, so that an account outside SNU can be told apart from an invalid token.
- [x] The accepted audiences are settings, so that the app's and the admin site's Google clients can both sign in.
- [x] A User is identified by the Google subject identifier. The first sign-in creates the User, and later sign-ins with the same subject return the same User.
- [x] The User's identifier is a UUID v4 generated by the database, as the identifier rule in the feature module note requires.
- [x] The access token is valid for 1 hour and is signed with a private key held only by the main server. The matching public key is a setting that other servers can be given.
- [x] The refresh token is valid for 30 days and is stored hashed.
- [x] A protected route recognises the User from the access token. A missing, expired or altered token gets 401.
- [x] Google's token verification sits behind an interface. Tests replace it with a verifier that accepts prepared tokens. Nothing else is replaced.
- [x] The key pair and the Google client settings are validated at startup and listed in the example settings file without secrets.
- [x] Tests through the public API cover: sign-in accepted for an SNU account; refused for another domain, an unverified email, a wrong audience and an expired token; a protected route refused without a token.
- [x] Manual check by a person: a real SNU account's ID token carries the hosted domain claim, and a Gmail account's does not. The result is recorded under `## Comments` in this ticket.

## Comments

### Decisions tickets 07–11 build on (2026-09-29)

Agreed with 김태현 before the implementation.

- **Access tokens**: ES256 JWTs signed with `@nestjs/jwt` (`JwtModule.registerAsync` in `AuthModule`). The payload is `{ sub: <User id> }` plus `iat` and `exp`, valid for 1 hour. Administrator status is not in it (ticket 09).
- **Keys**: `ACCESS_TOKEN_PRIVATE_KEY` (PKCS#8) and `ACCESS_TOKEN_PUBLIC_KEY` (SPKI) hold PEM text on one line with `\n`. `pnpm keys:generate >> .env` appends a new pair. Startup checks the PEM header, the P-256 curve and that the two form a pair. Ticket 11 gives the socket server `ACCESS_TOKEN_PUBLIC_KEY` only and verifies with `@nestjs/jwt` and `algorithms: ['ES256']`.
- **Routes**: `POST /auth/google` takes `{ idToken }` and answers 200 `{ accessToken, refreshToken }`. `GET /users/me` answers `{ id, email }`. Ticket 07 adds its routes under `/auth`, and ticket 08 extends `/users/me`.
- **Refusals** keep Nest's default body `{ statusCode, message, error }`: 400 for a body that fails its schema, 401 for an invalid, expired or wrong-audience ID token or access token, and 403 for an account outside SNU or an unverified email.
- **Modules**: `src/auth/` holds sign-in, the Google verifier and `AccessTokenGuard`. `src/users/` holds `UsersService` and `/users/me`. `@Public()` and `@CurrentUser()` are in `src/common/`, because several features use them.
- **Guard**: `AccessTokenGuard` is registered with `APP_GUARD`, so every HTTP route needs an access token unless it is marked `@Public()` (health and sign-in). A hybrid app does not pass `APP_GUARD` to its Redis message handlers unless `inheritAppConfig` is set, and `main.ts` does not set it.
- **Validation**: request bodies are zod schemas in the feature's `dto/`, given to the decorator (`@Body({ schema: signInSchema })`) and checked by Nest 12's `StandardSchemaValidationPipe`, registered as `APP_PIPE`. The 400 message names the field.
- **Tables**: `users` (`id`, `google_subject` unique, `email`) and `refresh_tokens` (`id`, `user_id`, `token_hash` unique, `expires_at`). Prisma models and fields are `User`/`googleSubject`, mapped to snake_case with `@map` and `@@map`. A refresh token is 32 random bytes in base64url, stored as a SHA-256 hex hash. The foreign key has no index and no cascade yet; ticket 07 adds an index if sign-out looks tokens up by User.

### Google verification in tests (2026-09-29)

`GoogleIdTokenVerifier` is an abstract class. `AuthModule` provides `GoogleAuthLibraryVerifier`, which calls `OAuth2Client.verifyIdToken({ idToken, audience })` from google-auth-library 11.1.0, as Google's documentation describes. That call checks the signature, issuer, audience and expiry. `AuthService` then requires `hd === 'snu.ac.kr'` and `email_verified === true`.

`startApp` replaces the verifier with `TestGoogleIdTokenVerifier` (`test/google.ts`). It calls `verifySignedJwtWithCertsAsync`, the method `verifyIdToken` calls after fetching Google's keys, with a test RSA public key instead. The tests sign their ID tokens with the matching private key, so the wrong-audience and expired-token tests run the library's own checks. Breaking the hosted domain check, the email check, the audience list, the refresh token hash or the guard each made the matching tests fail.

When Google's keys cannot be fetched, the real verifier rethrows the `GaxiosError` (500) instead of refusing the token with 401. No test runs the real verifier. Signing in through the running server with a real ID token does.

### Startup validation of the key pair (2026-09-29)

zod 4 runs an object-level `refine` even after a field inside it has failed. The check that the two keys form a pair then crashed on a key that was not PEM text, and comparing an RSA key with an EC key through `KeyObject.equals()` left an OpenSSL error (`different key types`) that made the next `createPrivateKey` in the process fail. The pair check therefore runs only when every other setting is valid (`when` in `settings.ts`), and a test covers a key that is not PEM text.

### First DTO and `prefer-readonly-parameter-types` (2026-09-29)

Ticket 01 asked to revisit the rule's options when the first DTO arrived. The DTO is a zod schema given to `@Body({ schema })`, so the pipe reads the schema, not the parameter's type. The parameter is typed `Readonly<SignInDto>` and the options stay as they are. `.oxlintrc.json` is unchanged.

### Manual check with real Google accounts (2026-09-29)

윤유상 got ID tokens from the OAuth 2.0 Playground with the app's web client and the scopes `openid email profile`, and sent each one to the running main server.

- SNU account: the token had `aud` equal to the app's client ID, `hd: 'snu.ac.kr'` and `email_verified: true`. `POST /auth/google` answered 200. The database then held one User, with a UUID v4 id and an `@snu.ac.kr` email, and one refresh token.
- Gmail account: the token had the same `aud`, no `hd` and `email_verified: true`. `POST /auth/google` answered 403 `Sign in with an SNU Google account (snu.ac.kr).` No User was created.

The Google Cloud project `SNU Now` has audience External and publishing status Testing, with no test users. Google lets any account sign in to a Testing app that requests only name, email address and profile, so the app needs neither test users nor verification. It has two web clients, the app's and the admin site's, and their IDs are in `.env.example`. The admin site's client has no JavaScript origins yet; P12 adds them. The Android client comes with P06.

The first attempt answered 500 with `The table public.users does not exist`: the local database volume had been recreated, and `pnpm start:dev` does not apply migrations. Running `pnpm db:migrate` first, as the README says, fixed it.
