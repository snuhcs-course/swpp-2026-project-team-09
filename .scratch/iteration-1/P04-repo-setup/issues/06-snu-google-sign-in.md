# 06: Sign in with an SNU Google account

Parent: [P04 spec](../spec.md)
Status: ready-for-agent
Blocked by: 02 (Data stores and main server connection)

## What to build

An SNU student signs in with their SNU Google account. The app obtains a Google ID token and sends it to the main server. The main server verifies the token, creates the User on the first sign-in and returns an access token and a refresh token. Later requests that carry the access token are recognised as that User. A person with a Google account outside SNU gets a clear refusal.

Refresh and sign-out are ticket 07. The sign-in screen belongs to P06.

## Acceptance criteria

- [ ] Sign-in verifies the ID token's signature, audience, expiry, that the email is verified, and that the hosted domain claim equals `snu.ac.kr`.
- [ ] The email address alone is not accepted as proof of the domain: a token with an `@snu.ac.kr` email but no matching hosted domain claim is refused.
- [ ] A refusal states its reason, so that an account outside SNU can be told apart from an invalid token.
- [ ] The accepted audiences are settings, so that the app's and the admin site's Google clients can both sign in.
- [ ] A User is identified by the Google subject identifier. The first sign-in creates the User, and later sign-ins with the same subject return the same User.
- [ ] The User's identifier is a UUID v4 generated by the database, as the identifier rule in the feature module note requires.
- [ ] The access token is valid for 1 hour and is signed with a private key held only by the main server. The matching public key is a setting that other servers can be given.
- [ ] The refresh token is valid for 30 days and is stored hashed.
- [ ] A protected route recognises the User from the access token. A missing, expired or altered token gets 401.
- [ ] Google's token verification sits behind an interface. Tests replace it with a verifier that accepts prepared tokens. Nothing else is replaced.
- [ ] The key pair and the Google client settings are validated at startup and listed in the example settings file without secrets.
- [ ] Tests through the public API cover: sign-in accepted for an SNU account; refused for another domain, an unverified email, a wrong audience and an expired token; a protected route refused without a token.
- [ ] Manual check by a person: a real SNU account's ID token carries the hosted domain claim, and a Gmail account's does not. The result is recorded under `## Comments` in this ticket.
