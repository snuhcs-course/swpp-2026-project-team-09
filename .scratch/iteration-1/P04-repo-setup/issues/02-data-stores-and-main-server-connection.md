# 02: Data stores and main server connection

Parent: [P04 spec](../spec.md)
Status: ready-for-agent
Blocked by: 01 (Main server skeleton)

## What to build

One command starts PostgreSQL, Redis and the main server on a developer's laptop. The main server keeps its schema as migrations in its own database with PostGIS enabled, and it is connected to NestJS messaging over Redis. Its readiness check reports "not ready" when either data store cannot be reached. Together with ticket 01, this is the pattern the socket, worker and match servers follow.

## Acceptance criteria

- [x] One command starts PostgreSQL, Redis and the main server.
- [x] The database image is built from the official PostgreSQL 18 image with the PostGIS 3 package added, and it runs without emulation on Apple Silicon. If that fails, the official PostGIS image under emulation is used and the reason is recorded under `## Comments` in this ticket.
- [x] One PostgreSQL instance holds two databases, one for the main server and one for the match server, each with its own role. The main server's role cannot read or write the match database.
- [x] Redis 8 is configured never to evict records.
- [x] Prisma is pinned exactly at 7.10.0. Schema changes are recorded as migrations, and one command brings an empty database up to the current schema.
- [x] The first migration enables PostGIS in the main database.
- [x] The feature module note states the identifier rule: every record is identified by a UUID v4 generated by the database. The first table (ticket 06) follows it.
- [x] The main server is connected to NestJS messaging over Redis, for events and for request and response. The messages themselves belong to P07 and P08.
- [x] The readiness check reports the database and Redis. It reports "not ready" when either is down, and the liveness check is unaffected.
- [x] The database and Redis settings are validated at startup and listed in the example settings file.
- [x] Tests run against a real PostgreSQL and a real Redis started in containers. They cover readiness with both stores up, readiness with one store down, and a spatial function answering in the main database.

## Comments

### Database image on Apple Silicon (2026-09-28)

The image is built from `postgres:18` with the `postgresql-18-postgis-3` package and runs natively on Apple Silicon (arm64, no emulation): PostgreSQL 18.6 with PostGIS 3.6.4. The official PostGIS image was not needed.

### PostGIS under the main server's own role (2026-09-28)

PostGIS is not a trusted extension, so only a superuser can enable it. The main role, which owns the main database, got `permission denied to create extension "postgis"`. Giving the role superuser would also let it into the match database. The image therefore marks PostGIS trusted (`trusted = true` in `postgis.control`), and the first migration enables it under the main role. Each role also has `CREATEDB`, because `prisma migrate dev` creates a temporary shadow database and enables PostGIS there too. The match database has no PostGIS.

### What tickets 03–05 follow (2026-09-28)

- `compose.yaml` at the repository root is the one command: `docker compose up --build`. The database image and the script that creates both databases and roles are in `infra/postgres/`. Each server has its own `Dockerfile` in its folder and is added to `compose.yaml` as a service.
- A server image with a database runs `pnpm db:migrate` and then `node dist/main`. While developing, run `docker compose up -d postgres redis` and `pnpm start:dev` on the laptop.
- Tests start their own containers with Testcontainers. `test/global-setup.ts` builds the database image from `infra/postgres/`, starts Redis, applies the migrations and hands the settings to the tests through `inject('settings')`.
- Prisma 7.10.0 reads `prisma7.config.ts`, the name `prisma init` gives it. The config loads `.env` itself. The generator states `importFileExtension = "js"`: the Docker image generates Prisma Client before it has `tsconfig.json`, and without that line it generated imports ending in `.ts`, which Node cannot load.
- `messagingOptions()` in `src/common/messaging.ts` builds the Redis options once, for `main.ts`, the messaging client and the readiness check. It sets `retryAttempts`: without it Nest stops messaging for good once Redis restarts. Nest's Redis server subscribes only to patterns that have a handler, so a message round trip can be checked once P07 and P08 add handlers.
- The documented pattern comes first; when a lint rule blocks it, the lint configuration changes. `PrismaService` receives `ConfigService` as a plain constructor parameter, as Nest's Prisma page does, and the messaging client is registered with `useFactory` and `inject: [ConfigService]`, as Nest's microservices page does.
- pnpm 12 runs a dependency's install scripts only when `pnpm-workspace.yaml` allows them. Prisma's are allowed; the native add-ons that testcontainers pulls in are not needed.

### Startup and shutdown (2026-09-29)

- Startup stops when either data store cannot be reached. Nest's Redis server subscribes to its channels only after its first connection succeeds, so a server that started without Redis would stay unsubscribed after Redis came back. The database is checked the same way: `PrismaService` runs `SELECT 1` in `onModuleInit`, because with PrismaPg `$connect()` only creates the connection pool. Once a server runs, readiness reports a store that goes down.
- `PrismaPg` gets `connectionTimeoutMillis: 5_000`, as Prisma's v7 connection pool page suggests to keep Prisma 6's timeout. pg waits for a new connection without limit by default, so a database host whose packets are dropped held startup, and every query after it, until the operating system gave up.
- `main.ts` calls `app.init()` before `startAllMicroservices()`, as Nest's hybrid application page advises, so that no message arrives before the database has answered.
- `main.ts` calls `app.enableShutdownHooks()`. Nest 12 drains the HTTP requests in progress when the app closes, but it closes on SIGTERM only with this call. Without it the container ended with exit code 137 and `onModuleDestroy` never ran.
- The image runs `node dist/main` directly, not through pnpm, and `compose.yaml` sets `init: true` for the server. After its shutdown hooks, Nest raises the signal again to exit, and a process running as PID 1 ignores that signal.
