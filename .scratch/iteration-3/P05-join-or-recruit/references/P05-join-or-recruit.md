- 결과(`eval/results/`)는 기본으로 무시되지만 `git add -f`로 커밋할 수 있다. dirty 검사는 추적하지 않는 파일을 보지 않는다. 그래서 `git add`하지 않은 새 케이스 YAML도 돌고, run 이름에는 `-dirty`가 붙지 않는다 [S33].
- 채점이 하는 일 [S30]
  - 행동(`actionOf`): Proposal이 있으면 PROPOSE다. 카드가 보이거나 lookup이 답을 받았으면 TOOL이고, ASK를 받는 케이스에서 글이 mentions를 담으면 TOOL+ASK다. **ASK만 기대하는 케이스는 lookup을 부르는 순간 found든 none이든 실패한다.**
  - 도구: required ∪ allowed 밖의 호출은 실패가 아니라 over-calling으로 센다. forbidden만 턴을 실패시킨다.
  - 카드: "이 seed들이 보였는가"와 종류별 개수 min/max를 본다. seeds를 정답 전체로, `max`를 정답 수로 두면 **정확 집합 일치를 지금도 판정한다**. `max: 0`으로 빈 정답도 된다. 없는 것은 합산 정밀도·재현율, 순서, 카드 필드 검사다. 카드 기대와 케이스는 `strictObject`(`{kind, seeds, min, max}`)라, 카드마다 하위 집합 태그 같은 칸을 YAML에 쓰면 세트 로드가 실패한다.
  - run-score의 합산은 행동 종류별 recall, 도구 선택, 인자, over/under-calling, 카테고리별 pass, pass^k, 사용량이다. 카드의 합산 정밀도·재현율은 없다 [S30].
  - `pnpm eval:score <run.json>`은 저장된 run을 모델을 부르지 않고 다시 채점한다. run JSON은 케이스의 expect 사본과 턴의 trace(카드 포함)를 담는다. 그래서 합산 코드는 R0 뒤에 더해도 R0을 다시 채점할 수 있다. `--category`로 일부 카테고리만 돌릴 수 있다 [S92].
  - `actionRecall`은 TOOL+ASK 턴을 TOOL과 ASK 양쪽에 센다. confusion 표의 관측값은 mentions를 보지 않고 문장 끝 어미로 TOOL+ASK를 가른다. 그래서 "합류해 보세요."는 TOOL로 찍힌다.
- 보태는 법 [S28][S29][S31]
  - 새 카테고리: `cases/<이름>.yaml`을 두면 자동으로 로드된다.
  - 고정 테스트 `eval-cases.integration.test.ts`도 고친다. 카테고리 표와 총 62(:123-130), live 3개와 `repeat: 3` 5개(:140-144)를 고정하고, :146의 테스트 이름이 "TOOL+ASK는 ambiguous-intent만"이다. ambiguous-intent는 모두 knownFailure여야 하고, "학관"은 knownFailure 케이스에서만 쓸 수 있다(:152-165). WORLD_FACTS는 hobby 검색의 답에 자리 찬 `아침 러닝 크루`와 `"placesLeft":0`이 있어야 한다고 고정한다(:234-239).
  - 새 도구: `normalise.ts`의 TOOLS에 항목을 둔다. 없으면 어떤 행동 규칙에도 세지 않는다.
  - 새 seed 종류·카드 종류·지도 레이어: `world.ts:50`, `expect.ts`와 `cases.ts`의 enum을 넓힌다.
- 세계는 run당 한 번 seed되고, 케이스마다 새로 넣는 것은 셔틀 차량뿐이다 [S31]. 지금 Assistant에는 쓰기 도구가 없어 케이스 사이로 상태가 새지 않는다. 코드 주석이 적듯 "seed와 케이스는 함께 바뀐다": 세계는 모든 케이스의 입력이다 [S31].
- 세계의 질문자는 김하늘 한 명이다. `QuestSeed`에는 리더나 Holder를 적는 칸이 없다. 모든 모집 Quest는 리더 정다은이 만들고, 자리 찬 하나를 오세훈이 채운다. 질문자는 `seedQuests`에 넘어가지 않아, 지금 세계에서는 질문자가 Quest를 들 수 없다 [S32][S31].
- 비용: Haiku 5.5는 100만 토큰당 입력 $0.10, 출력 $0.50이다 [S49][S50]. 지금 세트 한 번(75턴)이 $0.17–0.68이고, P4·P5 케이스 40개를 3번씩 더해도 $0.6–2.3이다 [S48]. 다만 가격 조회가 실패하면 fallback 값(100만 토큰당 5/25 USD)으로 계산되어 [S33], $5 예산 가드가 턴당 입력 20k–80k 토큰 가정에서 약 12–43턴에 run을 멈춘다(내 계산 [S48]).
- Haiku 5.5는 OpenRouter 목록에 temperature·top_p·seed가 없고, `reasoning`·`reasoning_effort`는 있다 [S49]. Anthropic의 공개 migration guide는 Haiku 5.5에서 temperature·top_p·top_k를 빼라고 적는다 [S50]. "기본값이 아닌 값은 400으로 거절된다"는 문장은 claude-api 스킬 번들에만 있고 공개 문서로는 확인하지 못했다(미확인). 내 판단: `--temperature 0`을 주면 run 이름의 `temp0`이 사실과 다르게 찍힌다. 비결정성은 반복(pass^3)으로 잰다. Miller(2024)도 temperature를 낮추지 말고 반복으로 분산을 줄이라고 권한다 [S81].
- run 이름에는 넘긴 모델 문자열과 제한·sampling만 들어가고, trace에는 실제로 응답한 모델 id가 없다 [S33]. 별칭 `anthropic/claude-haiku-5.5`가 R0와 R1 사이에 새 스냅숏을 가리키면 기록한 버전이 틀린다(4.5).
- 긴 판(threshold 장치 설계는 5.5, 하네스에 얹는 법은 5.6, run 날짜표는 4.4)은 P04 보고서에 있다 [S85].

### 2.3 공통 사실 ③ 시간표 접근 (P5 Q7의 바탕)

- 시간표는 `TimetableClass { courseName, times[] }`와 `ClassTime { weekday, startTime/endTime, placeId?, room? }`다. API `/timetable/classes`는 본인 것만 읽는다. 컨트롤러 주석이 "다른 User의 시간표에 닿지 않는다"고 적는다 [S26].
- Assistant에는 시간표를 읽는 도구가 없다. AssistantModule은 TimetableModule을 import하지 않는다 [S26]. P07 spec은 "시간표나 User의 위치를 추천에 쓰는 것"을 out of scope로 두었다 [S27]. 공강을 계산하는 코드도 없다.
- P5의 카드에 붙을 "직전 수업에서의 도보 시간"과 "수업과 겹침"은 P4가 만들 시간표 도구와 이동시간 표에 기댄다. 그 설계와 근거는 P04 보고서 2절(현황)과 3절(선택지 비교)의 "Q1 시간표 접근"과 "Q2 이동시간 표"에 있다 [S85]. P5는 이를 조사하지 않는다(Q7, 5절).

### 2.4 행사 수집, Draft, 원문 키

- 행사 Source는 `snu_events` 하나다. 워커가 SNU 행사 목록을 오늘부터 365일 범위로 하루 4회(00·06·12·18시, 코드에 "임시") 읽는다 [S19]. 페이지 하나를 5초 타임아웃으로 읽고, 요청 사이에 쉬지 않는다. 읽을 수 없는 글이 3연속이면 Collection이 실패한다 [S20][S19].
- 파서는 규칙만이고 모델이 없다. 시간줄 라벨은 `일시|일자|일정|기간`이다. 날짜는 4자리 연도가 있어야 읽고, 오전/오후가 확실할 때만 시각을 읽는다 [S19].
- 발행 규칙은 한 줄이다: `published = readFrom === 'body' && start.hasTimeOfDay && named !== null`(`global-events.service.ts:41`). 아니면 Draft다 [S16]. 관리자가 발행하려면 startsAt과 위도·경도가 있어야 한다 [S22].
- 장소 연결(`named-place.ts`)은 장소 문자열 전체가 정확히 Place 하나를 가리킬 때만 된다. **번호만 있거나 이름만 있으면 학교 이름(서울대·관악캠퍼스·SNU)이 함께 있어야 한다.** 그래서 학과 글에 흔한 `301동 118호`는 Draft가 된다. 다른 캠퍼스·병원·온라인은 뺀다 [S18]. 찾은 Place의 id는 저장되지 않고 좌표만 복사된다 [S16].
- 실측: 2026-10-03 전체 수집 82건 중 13건 발행, 69건 Draft였다(발행 16%, Draft 84%). 이 82건은 git에 없어 다시 잴 수 없다 [S39]. 2026-10-01 표본 48건에는 행사 아닌 글이 약 10건 있었고, 같은 행사가 두 번 올라온 쌍(bbsidx 176375/176285)이 1개 있었다 [S40].
- 이번에 18건(저장된 글 6건과 2026-10-22~26의 SNU Now 글 12건)에 우리 코드를 다시 돌렸다. 규칙만으로 6/18이 발행됐다 [S46][S58]. 라벨상 발행할 수 있는 것만 분모로 하면 회차 6/17(35%), 글 6/13(46%)이다. 16%와 33%는 행사 아닌 글까지 넣은 전체 글 대비 발행률이라 분모가 다르다 [S46]. 저장된 6건은 워커 파서 단위 테스트의 픽스처다 [S46]. 내 판단: 이 18건은 naive(규칙 파서)를 이미 돌린 글이므로 수집 모듈의 고정 세트에 넣지 않고 개발·보정 세트로만 쓴다(5절).
- GlobalEvent에는 종류, 마감, 대상, Place FK, 회차가 없다. 여러 회차 글은 첫 회차 하나로 저장되고 관리자가 나눈다 [S15][S38]. 신청 기간과 마감은 description 안에만 있다 [S38].
- **원문 키는 하나뿐이다.** [S15][S17]
  - `postNumber Int? @unique`는 Source를 가리지 않는 테이블 전체의 키다.
  - 워커의 질문 "이 글들 저장했나?"는 글 번호만 담는다.
  - 메시지의 `source`는 `z.enum([Source.snu_events])`, 글 키는 `z.int32().positive()`, 원문 링크는 https만 받는다.
  - 그래서 두 번째 Source를 붙이면 지금은 메시지가 400으로 거절된다. enum을 넓혀도 번호가 SNU의 bbsidx와 같으면 `skipDuplicates`로 조용히 버려지고, 문자열 키나 http 링크는 다시 거절된다.
  - 시각을 어디서 읽었는지(`readFrom`)는 `body | header | null`뿐이고, 발행 규칙은 `readFrom === 'body'`를 요구한다 [S17][S16]. 목록 칸에서 일시를 읽는 Source(음악대학, 일정형 게시판)는 새 값을 더하고 발행 규칙을 고치거나 `body`로 볼지 정해야 한다(Q6, 7절).
- 저장은 한 트랜잭션의 `createManyAndReturn({ skipDuplicates: true })`이고, 저장된 글은 어떤 상태든 다시 읽거나 바꾸지 않는다 [S16][S15]. 워커는 메인 서버의 답을 5초만 기다린다 [S20]. 내 판단: 모델을 부르는 판정은 이 요청 안에 넣을 수 없다.
- 관리자 화면은 Draft 목록("Still needs" 열), 편집, 발행·폐기·취소, 손 입력을 한다. Draft 목록에는 쪽 나눔과 Source 거름이 없고, 끝난 Draft도 걸러지지 않는다 [S22][S16][S23]. 행사 페이지의 "Source" 카드는 원문 하나만 보인다 [S23].
- 앱에는 이미 "자세히" 버튼이 있어 `sourceUrl`을 연다. 앱의 행사 종류(career/event/festival)는 서버 값이 아니라 앱이 단어로 추측한 것이다 [S24].
- 다음 단계로 P07 spec이 적은 것은 이렇다: "규칙 먼저, 그다음 AI로 시작·끝·장소를, 회차마다 따로 — 행샤 방식 — 다음 iteration에" [S38].

### 2.5 Quest 입장 규칙과 `searchRecruitingQuests`

- 후보 하나는 `{id, title, board, globalEvent(제목만), joinPolicy, placesLeft, next{startsAt, endsAt, place(라벨만)}, description(300자)}`이다. 시작이 이른 순으로 20개를 준다 [S6].
- 입력은 `{board?, from?/to?(날짜), globalEventId?}`뿐이다. 시각대("저녁"), 단어, 장소 조건이 없다 [S6].
- **자리가 찬 Quest도 후보에 남는다.** Board·행사·기간으로만 거르고 자리·시각대·장소 조건은 없다. 정렬 뒤에 20개로 자른다 [S6][S11]. 모집 목록은 Open과 Approval, 내가 들지 않은 것, 앞에 남은 Sub Quest가 있는 것이다 [S11].
- 내가 이미 든 Quest는 목록 쿼리에서 빠진다(`holders: none`). `showQuests`도 모집 목록에 있는 Quest만 카드로 채우므로(`listedAmong`), 내가 든 Quest는 카드로 보일 수 없다. Assistant에는 내 Quest를 읽는 도구가 없다 [S11][S30][S3]. 그래서 "이미 18:00 배드민턴에 참여 중이에요" 같은 답은 지금 도구로는 할 수 없고, 도구를 더해도 글로만 답할 수 있다.
- 입장 거절 순서는 QUEST_NOT_FOUND → ALREADY_HOLDER → 방식별 → QUEST_ENDED → QUEST_FULL → SHARED_QUEST_HELD다 [S11].
- 같은 Global Event에 한 User의 Quest는 하나다(`@@unique([userId, globalEventId])`). 행사 없는 Quest는 제한이 없다 [S15].
- 입장할 때 같은 행사의 Quest를 **혼자** 들고 있으면 그 Quest를 지우고 들어간다. 둘 이상이 든 Shared Quest가 있으면 거절한다. 입장(`freeForSharedQuest`), 승인제 참여 요청(`holdsSharedQuestFor`), Matching 요청(자체 질의)의 세 곳이 모두 SHARED_QUEST_HELD로 거절한다 [S12][S13].
- 승인제 참여 요청은 정원을 보지 않고 보내지고, 리더가 수락할 때 입장 규칙을 거쳐 QUEST_FULL로 거절될 수 있다. 요청만으로는 Holder가 늘지 않는다 [S13].
- 행사 Quest의 Sub Quest는 장소 라벨로 행사의 장소 문자열을 쓰고, `placeId`는 null이다. 일반 Quest의 장소는 Place id, 점과 라벨, 라벨만 셋 중 하나다 [S14].
- `attend`(행사의 Quest 만들기)는 published 행사만 받는다. 같은 행사의 Quest를 이미 들었으면 새로 만들지 않고 그것을 돌려준다 [S12]. 그래서 Draft에는 Quest가 생길 수 없다.
- eval 세계의 Quest 11개 중 Place id가 있는 것은 3개다(`내일 점심 학식 같이`, `어제 점심 번개`, `알고리즘 스터디`). 6개는 라벨만 있고(`주말 배드민턴`의 `포스코스포츠센터 체육관` 포함), 2개는 행사 Quest다 [S32][S14].

**수집기에 걸리는 것(사실)** [S59][S20][S17]

- 페이지네이션: GET으로 읽히는 계열은 쪽 번호가 GET 인자다. KBoard는 `?pageid=N`(18곳 모두), 공용 CMS 표형·일정형은 `?page=N`(21곳 중 19곳), Gnuboard 5는 `&page=N`(9곳 모두)이다. 테마 게시판과 세미나형은 목록만 `?var_page=N` GET이고 본문은 폼 POST다. eGovFrame 3곳(cbe, dentistry는 폼 POST, medicine은 AJAX POST)과 snufrance는 쪽 넘김이 POST이고, psir·gspa는 JS·AJAX, cse는 매개변수 미확인이다. 오래된 게시판은 쪽이 많다(math 세미나 150쪽, cba 공지 1,198쪽, cuee 292쪽). 지금 수집기는 빈 쪽이 나올 때까지 읽으므로 이런 Source에는 Q6의 "저장된 글을 만나면 멈춤"이 필요하다(내 판단) [S59][S19].
- 날짜 꼴: `YYYY-MM-DD`, `YYYY/MM/DD (요일) 오전 HH:MM`, 연도 없는 `10월 28일(수) 19:30`, 영어 월 `12 Nov, 2026`, `7PM`. 지금 `event-time.ts`는 이 꼴들의 시각을 읽지 못한다(에이전트 셋이 복사본으로 실행해 확인).
- 장소: `56동105호`, `16동 654호`처럼 번호만 적는 글이 많다. 지금 규칙으로는 Draft다(2.4).
- 인코딩: philosophy, engedu, complit, ipbi는 EUC-KR이고, 응답 헤더에 charset이 없는 곳도 있다. 지금 `PageFetcher`는 `response.text()`로 읽고, POST는 JSON 본문만 보낸다. 테마 게시판의 본문 요청은 form-urlencoded다.
- https: 원문 링크는 https만 받는데, complit·ipge·brainscience·gspa는 http로 답했다(https가 되는지는 미확인). 그보다 먼저, 운영 워커의 NetworkPolicy는 인터넷으로 TCP 443만 연다 [S90]. 그래서 http로만 답하는 사이트는 링크 규칙과 상관없이 운영에서 읽을 수 없다. 80 포트를 열지, 그 Source를 뺄지는 그 Source를 붙일 때의 결정이다(7절).
- 시각을 읽은 곳: 목록 칸에서 일시를 읽는 Source는 `readFrom`에 맞는 값이 없다(2.4) [S17].
- 글 키: 게시판마다 번호(bbsidx, wr_id, uid, bid, number)를 따로 매겨 범위가 겹친다. 16진 id나 슬러그도 있다.
- 첨부·이미지: 본문을 읽은 글 23건 중 5건(22%)이 이미지나 첨부뿐이었다. 그중 2건은 머리의 구조화 칸에 일시·장소가 있다. 공지 게시판은 첨부 아이콘이 많다(사범대 공지 평균 81%, 농생대 25/30). 표본이 작아 비율의 오차가 크다.
- 교차 게시: 국제처의 "교환학생 (모집) 설명회" 제목이 저장 파일 42개 호스트에 있다. 다른 묶음(같은 강연이 인문대학과 영문과에, 음악대학 공연과 snu_events 174158)도 관찰됐다.
- 약관·저작권: 이메일무단수집거부 문구가 15개 호스트에 있다. 이용약관 링크는 6개 호스트, 저작권법 제97조 경고문은 1곳(mse), "저작권 보호정책" 문서는 0곳이다. 내 판단: 학과 글에는 담당자 이메일이 흔하므로, 저장할 때 이메일 주소를 가리는 것이 안전하다. 법 해석은 확인하지 않았다(미확인, PM 확인 사항).
- 같은 서버: SNU WordPress 멀티사이트들은 같은 IP 대역(147.47.107.4–6)에 있다. 노문 REST 요청 1건이 학교 방화벽에 막혔다. 내 판단: 요청 간격은 호스트가 아니라 서버(IP)마다 잡는다.

**조사하지 않은 것과 방법에서 벗어난 것(사실)** [S59]

- 주소를 찾지 못한 협동과정 4곳: 미술경영, 줄기세포생물학, 과학사 및 과학철학, 평화·통일학.
- 표 밖: 농생대 전공 사이트 5곳(hort, aged, anibiotech, bm, ageng), 같은 호스트의 다른 게시판(수의대·약대 공지, 농생대 행사안내), 연계·연합전공 3곳.
- 상세 글을 읽은 사이트는 28곳(29건)뿐이다. WebSearch 한도가 차서 다섯 에이전트가 상세 대신 홈을 읽어 게시판 주소를 찾았다. 나머지 107곳의 글 구조(텍스트·이미지·첨부, 시간·장소 줄의 꼴)는 미확인이다. 사이트당 GET 1건이면 확인된다.
- 테마 게시판의 본문을 GET으로 얻는 길(`/wp-json/wp/v2/posts/<id>`, 카테고리 RSS)은 미확인이다. 1회 시도는 방화벽에 막혔다. 폼 POST로 본문을 받는 것이 허용되는 수집인지는 PM의 정책 결정이다.
- 에이전트가 스스로 적은 요청 규칙 위반: 301 리다이렉트를 1초 간격 없이 따라간 4건(s-agr-med), dentistry의 `Crawl-delay: 60` 미준수(s-grad-pro), architecture에서 robots.txt보다 먼저 `/notice/` 1건(s-eng), 범위 밖 요청 3건(s-grad-coop).

### 2.6 행샤(hangsha-server, main 브랜치)

2026-10-26–27에 main @ `6fe44cbe`(2026-10-22, PR #197 병합 커밋)를 읽었다. LICENSE가 없어 코드·프롬프트·패턴 목록을 옮기지 않고 방법만 내 말로 적는다 [S52][S1].

- 수집 흐름: 배치 하나가 extra.snu.ac.kr(비교과)와 SNU Now를 차례로 돈다. 학과 게시판과 메일은 읽지 않는다 [S53].
- AI 파서: SNU Now 글에만 쓴다. 기본 모델은 `gemini-3.5-flash-lite`이고(PR #200, 2026-10-22), `prod` 프로필에서만 켜진다. 요청 간격은 4.5초, 429/503일 때만 다시 시도해 최대 3번 시도한다 [S52][S53][S55].
- 출력은 strict JSON schema(모든 필드 required + nullable)다. 주최, 분류(7개 값), 장소, 신청 시작·끝, 행사 시작·끝, 회차 목록을 낸다. 회차가 둘 이상이면 회차마다 한 행을 저장한다. 원문 인용과 필드별 확신도는 없고, 시작<끝 같은 검사도 파서에는 없다 [S52].
- AI가 기간이나 회차를 하나라도 내면 규칙 값을 대신한다. 장소는 AI 값으로 덮인다(null이어도). 호출이 실패하면 규칙 값으로 그대로 저장한다(fail open) [S52][S55].
- Draft나 검토 대기 상태가 없다. 모두 바로 노출되고, 배치 끝에 새 행사 요약을 Discord로 보낸다. 요약은 일관성 검사로 "확인 필요"를 표시한다(신청 시작>끝, 행사 시작>끝, 일반 행사가 7일 넘음, 원문 링크 없음 등). 관리자가 고친 필드는 다음 동기화에서 지킨다 [S53].
- 공개 수치(정확도, 무인 발행 비율)는 없다. PR 본문은 "정확도는 모델 출력에 따라 달라질 수 있다"는 취지만 적는다 [S55].
- 공개 API로 본 운영 결과 [S56][S58]
  - 2026-10-01~11-30 범위에 453행(SNU Now 276, extra 177)이 있었다.
  - id 975–1199의 SNU Now 136행은 주최·장소가 모두 비고 분류가 모두 같은 값이며, 회차가 나뉜 글이 없다. 내 판단: 10-01 무렵부터 Gemini 전환(10-22)까지 약 3주 동안 AI 파서가 돌지 않았고, fail open이라 규칙 값만으로 노출된 것으로 보인다. 확인하려면 행샤 운영 로그가 필요하다(미확인).
  - 전환 뒤 글 12건을 조사 에이전트 하나가 원문과 대조했다(사람이 검토하지 않았다). 회차 시작 15/15, 끝 14/14, 장소 문자열 12/12, 마감 3/3이 맞았고, 지어낸 마감은 0/9였다. 내 판단: 글 12건이라 오류 0이어도 95% 상한은 약 25%다(3/n).
- 같은 행사 처리 [S54][S53]
  - 같은 원문의 재발견은 신청 링크와 기간으로 한다.
  - Source 사이(PR #197, 2026-10-22): SNU Now 회차마다 같은 날 시작하는 extra.snu 행사를 후보로 하고, 정규화한 제목의 글자 bigram Jaccard로 최대 3개를 고른다. 문턱은 시작 시각이 같으면 0.16, 같은 날이면 0.58이다. Jaccard는 모델에 줄 후보를 고르는 앞단이고, 판정은 모델이 한다. 모델이 고르고 확신도를 말하게 해서, high이면서 제시한 후보 id일 때만 그 회차를 뺀다. 모델 입력은 id, 회차, 제목, 시작·끝, 주최, 본문 앞부분(지금 글 3,000자, 후보 1,500자)이다. **장소 칸은 없지만**, 본문에 장소 줄이 있으면 모델이 그것을 본다 [S54][S52]. 한 글의 두 회차가 같은 기존 행사로 판정되면 둘 다 남긴다. 호출이 실패하면 아무것도 빼지 않는다. 기존 DB의 중복과 같은 Source 안의 중복은 다루지 않는다. 단위 테스트는 22개다.
- 행샤의 공개 API 대신 직접 수집하기로 팀이 2026-09-27에 정했다 [S1][S40].

### Q2 수집 AI 모듈

**행샤의 방식(요약, 2.6).** 규칙 다음에 AI가 시작·끝·장소·회차를 채우고, strict 스키마로 받는다. 실패하면 규칙 값으로 그대로 노출하고(fail open), 검토 보류 없이 사후에 Discord로 검수한다. 원문 인용, 필드별 확신도, 결정적 검증은 없다 [S52][S53]. 공개 수치는 없다 [S55].

- 권하는 결합(내 판단)

  5. AI 호출 실패, 시간 초과, 스키마 불일치는 Draft다(fail closed). Collection 상태에 "AI 미적용 n건"을 남긴다. 행샤의 3주 공백이 사용자에게 보이지 않았던 것을 거울로 삼는다 [S56].
- Iteration 3에 넣는다면 범위를 시간·장소·회차·`isEvent`로 묶는다. 종류·마감·대상은 AI 채움값으로 관리자 화면에만 두면 스키마·앱 변경이 준다. 시나리오의 종류 필터가 꼭 필요하면 `kind` 한 열만 더한다(내 판단).

### Q3 중복 판별: 규칙과 모델 입력

#### (a) Source 간 같은 행사

**데이터에서 본 것(사실).** 행샤 공개 API의 2026-09-01~10-31 목록 653행(두 Source)을 읽었다 [S57].

- 같은 행사로 보이는 쌍이 약 15쌍 이상 남아 있다(원문은 열지 않았고, 조사 에이전트 하나의 판단이다. 사람이 검토하지 않았다).
- 같은 시작 시각 안에서 **제목 유사도로는 같은 행사와 다른 행사를 가를 수 없다.** 같은 행사로 본 8쌍의 bigram Jaccard는 0.27–1.0이고, 다른 행사는 0.02–0.83이다(이웃사랑 1차/2차 0.83). 판단이 어려운 대면/비대면 쌍은 0.91–0.94다.
- 같은 행사 8쌍 중 온라인은 4쌍뿐이다. "대부분 온라인"이 아니다. 대신 같은 행사의 장소 문자열이 Source마다 다르다("-"와 "온라인 (Zoom)", "연건캠퍼스 … 우봉홀"과 "-").
- 주최 표기도 Source마다 다르다("전공설계지원센터"와 "학부대학 전공설계지원센터").
- 다대일 대응이 있다. 한쪽은 5일짜리 기간형 한 행이고, 다른 쪽은 하루씩 5회차다(전공탐색주간, 디지털 리터러시 아카데미). 행샤의 "두 회차가 한 기존 행사에 붙으면 둘 다 남긴다" 규칙이 이런 쌍을 중복으로 남긴다.
- SNU 목록 안의 재게시 쌍 176375/176285는 제목이 주제 제목과 시리즈 제목으로 달라 Jaccard가 0.31이다. 시작·주최·장소(온라인)는 같다 [S57][S40].

**판별 방법의 선택지**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| N0 제목 유사도 규칙(행샤의 후보 거름을 그대로 판정 규칙으로 쓴 것) | 같은 시작 + 정규화 제목 Jaccard ≥ τ. 행샤에서는 이 단계가 후보만 고르고 판정은 모델이 한다 [S54] | 단순하다. naive 베이스라인으로 좋다 | 1차/2차·대면/비대면 쌍에서 잘못 합치고, 제목이 다른 재게시를 놓친다 [S57] |
| 블록 안 모든 쌍을 모델이 판정 | 쌍마다 같음/다름 | 표현 변이를 본다 | LLM은 과하게 같다고 한다. ECB+ 쌍 판정에서 GPT-4(zero-shot CoT)는 재현율 93.7, 정밀도 57.5였다. 그 세트는 6,662쌍 중 2,282쌍(34%)이 양성이다 [S72]. 블록 안 양성이 1% 미만인 우리 데이터에서는 정밀도가 더 낮을 것이다(내 판단) |
| 규칙 → 금지 규칙 → 애매한 쌍만 모델의 고르기 → 관리자(권장) | 아래 | 정밀도를 우선한다. 모델 호출이 적다 | 규칙과 금지 목록을 우리 데이터로 정해야 한다 |

**권장 흐름(내 판단).**

- 단위는 회차다. 지금은 글의 첫 회차로 비교한다 [S38].
- 블로킹: 기존 Global Event 중 시작 날짜가 ±1일 안인 것. draft·published·cancelled·discarded를 모두 포함한다. 장소로는 거르지 않는다(위의 장소 문자열 차이). 블로킹이 놓친 쌍의 비율(Pair Completeness)을 따로 잰다 [S74]. Meta의 특허도 시작 시각 ±1시간과 지도 칸으로 블로킹한다 [S80].
- 명백한 쌍(모델 없이 붙임; 모두 금지 규칙에 걸리지 않을 때)
  - R0 같은 (Source, 원문 키).
  - R1 같은 정규 URL을 가리킴(학과 글이 SNU 목록 글이나 같은 extra.snu 항목에 링크) + 같은 시작.
  - R2 같은 포스터 이미지 해시 + 같은 시작.
  - R3 정규화 제목이 같음 + 같은 시작(분 단위).
  - R4 시리즈명+회차 같은 핵심 구가 다른 제목에 들어 있음 + 같은 시작. 주최는 필수 조건이 아니라 포함·정규화 비교의 특징으로만 쓴다.
- 금지 규칙(자동으로 붙이지 않음): 시작 시각이 다름, 차수·회차 표지가 다름(1차/2차), 방식 표지가 다름(대면/비대면), 역할 표지가 다름(헬퍼/디자이너), 둘 다 Place가 있는데 다르고 멀다. 행샤 표본의 어려운 음성 쌍에서 뽑았다.
- 다대일: 새 회차가 기존 기간형 행사의 기간 안에 들면 그 행사에 붙인다.
- 애매한 쌍: 새 원문 하나에 후보 3개까지 주고 "그중 하나 또는 없음"을 고르게 한다. 고르기가 쌍 판정보다 낫다는 결과가 있다. GPT-4o-mini의 평균 F1이 쌍 판정 67.80(예시 6개면 77.94), 둘씩 비교(Comparing) 84.36, 고르기 82.26이었고, 중간 크기 LLM으로 먼저 거른 뒤 고르게 하면(ComEM) 86.42였다. 같은 표의 비용은 고르기가 비교의 약 1/7이다 [S71]. 내 판단: 비교가 고르기보다 F1이 약간 높지만, 비용과 "후보 중 하나 또는 없음"이라는 꼴이 관리자 큐와 맞아 고르기를 권한다. 같은/다른 행사 예시 몇 개를 넣으면 zero-shot보다 크게 오른다 [S69]. 프롬프트에 따라 F1이 흔들리므로 프롬프트를 고정하고 커밋 해시로 기록한다 [S70].
- 모델 입력: 양쪽의 제목, 시작·끝과 시각 유무, 시간 줄을 어디서 읽었는지, 장소 문자열과 연결된 Place(이름·번호, 또는 없음/온라인), 주최(있으면), Source 이름, 시간 줄·장소 줄, 본문 앞부분, 회차 목록, 본문의 링크. 좌표는 보내지 않는다. 같은 Place·가까움은 서버가 계산한 값만 보낸다. 다른 사람이 쓴 글이므로 `<data>`로 감싼다 [S3].
- 모델 출력(스키마 강제): 고른 후보 id 또는 null, `same | different | unsure`, 같다는 근거 필드(start_equal, title_series_match …), 다르다는 필드(round_differs …), 한 줄 이유. GPT-4가 정보가 모자라도 결정을 강요하는 과신 경향이 있다는 보고가 `unsure`를 두는 근거다 [S73].
- 채택: `same`이고, 고른 id가 이번에 제시한 후보 안에 있고, 시작이 같을 때만 붙인다. `different`면 새로 만든다. `unsure`, 실패, 형식 오류면 새 원문을 **Draft로** 저장하고 "같은 행사일 수 있음: 후보 X"를 남긴다. 규칙상 발행됐을 글이어도 판정 전에는 발행하지 않는다. 발행하면 카드가 두 장 보이고 Quest가 갈라지기 때문이다. 대가로 무인 발행률이 내려가므로 두 지표를 같이 보고한다.
- 실패 비용: 잘못 합치면 다른 행사 하나가 사용자에게 안 보인다. 놓치면 카드가 두 장이고 Quest가 두 Global Event로 갈라진다. 내 판단: 자동 병합은 정밀도 우선(틀린 자동 병합 0)으로 하고, 놓침은 관리자 큐와 쪼개짐 지표로 드러나게 한다.

**"같으면 원문으로 붙인다"에 필요한 스키마 변경(내 판단).**

- 원문 테이블 하나를 더한다: `{id, source, postKey(문자열), url, globalEventId, title, body, readAt, 붙인 방법(first | rule:R0–R4 | model | admin), 근거}`, unique `(source, postKey)`. 기존 행은 `source = snu_events, postKey = post_number`로 옮긴다. GlobalEvent의 `sourceUrl`은 "대표 원문"으로 남겨 옛 APK의 '자세히' 링크가 계속 쓰게 한다. `postNumber @unique`는 새 수집이 쓰지 않게 되면 뗀다.
- 워커의 질문은 `{source, postKeys: string[]}`로, 메시지는 Source enum 여러 값과 문자열 키로 바꾼다. https 제한은 Source마다 다시 본다(일부 학과는 http로만 답했고, 운영 워커는 443만 나간다, Q1) [S90].
- GlobalEvent에 `placeId`(Place FK)를 더해 장소 연결이 찾은 id를 버리지 않는다. 같은 장소 판정과 장소 연결 정확도를 Place id로 재려면 필요하다.
- 판정 대기 행 `SameEventCandidate {postId, globalEventId, reason, decision: pending | same | different, decidedBy, decidedAt}`. 관리자 큐이면서 2인 라벨과 쌍 F1의 라벨 세트로 그대로 쓴다.
- 상태별로 붙이는 법
  - published: 원문 목록에만 더하고 보이는 필드는 바꾸지 않는다. 시각이나 장소가 다르면 관리자 알림만 남긴다. 발행된 행사의 시각을 자동으로 바꾸면 그 행사의 Quest를 든 사람의 일정이 말없이 바뀐다.
  - Draft: 원문만 더하거나, 빠진 필드(시각, Place)를 새 원문에서 채우고 발행 규칙을 다시 돌린다. 뒤의 것은 필드마다 어느 원문에서 왔는지 기록하고, 두 원문이 같은 필드에서 충돌하면 채우지 않는다. 행샤가 관리자 수정 필드를 지키는 방식이 참고가 된다 [S53].
  - discarded: 붙이고 discarded로 둔다. 다른 게시판에서 같은 공지가 새 Draft로 돌아오지 않는다.
  - cancelled: 붙이고 상태를 그대로 둔다.
- 판정은 저장 뒤의 비동기 단계로 둔다. 저장이 한 트랜잭션이고 워커는 5초만 기다리기 때문이다 [S16][S20]. 원문을 붙이거나 합칠 때 GlobalEvent의 `version`(관리자 동시 편집 검사)도 비교한다 [S15][S16].
- 이미 있는 두 Global Event가 나중에 같은 행사로 밝혀지면 [S12][S13][S14]

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|

- 일정: 원문 키 부분(질문·메시지에 Source, `(source, postKey)` unique)은 Source를 하나라도 더하면 11-01 전에 필요하다(약 1–1.5 h, Q6). 판정 로직 전체(규칙, 모델, 관리자 큐)는 에이전트 8–11 h로 본다(내 추정). 라벨 데이터도 모자라므로(5절) Iteration 4를 권한다.

Source 간 양성 쌍이 없어 고정 세트와 threshold를 먼저 커밋할 수 없다. 원문 키 부분만 Source를 더할 때 된다. 11-04에는 평가할 판정이 없다(해당 없음). 11-05(P22)에는 설계를 서술만 하고 depth로 주장하지 않는다. 지표가 없기 때문이다. 11-06(P20)에는 해당 없다. 모델을 쓰는 판정을 Iteration 3에 만들면 수집 AI 모듈처럼 수업 규칙(고정 세트, threshold 선커밋, 결과 보고)이 따로 적용된다 [S1].

#### (b) Quest(화면의 "파티") 간 같은 활동

**오늘의 필드로 되는가(사실과 판단)** [S6][S14][S11]

| 조건 | 오늘 | 판단 |
|---|---|---|
| 같은 활동 | title·board·description(300자)·행사 제목으로 모델이 판단 | 된다. 행사 Quest는 같은 globalEventId가 곧 같은 활동이다 |
| 같은 날 | `next.startsAt`의 날짜, 입력 from=to | 된다 |
| 시작 ±30분 | 모델이 시각 문자열을 빼서 비교. 서버 조건 없음 | 되지만 결정적이지 않다. 모델의 시각 계산 실수가 지표에 섞인다 |
| 같은 Place | 라벨만 간다. Place id는 DTO에 있지만 도구가 버린다 | id 비교는 안 된다. 세계 Quest 11개 중 id가 있는 것은 3개뿐이다 |

**"내가 들어갈 수 있는" Quest의 정의(입장 규칙을 그대로 따름)** [S11][S12][S13]

1. Open이나 Approval이다. 2. 내가 Holder가 아니다. 3. 앞에 남은 Sub Quest가 있다(1–3은 이미 있다).
4. 자리가 남았다(`holderCount < capacity`). 승인제 요청은 자리를 보지 않고 보내지지만 수락 때 거절되므로 뺀다.
5. 같은 행사의 Shared Quest를 들고 있지 않다. 같은 행사의 Quest를 혼자 든 것은 거절 사유가 아니다.
6. 승인제 Quest에 이미 보낸 요청은 거절 사유가 아니다. 내 판단: 빼지 말고 `requested: true`로 표시해 "이미 참여 요청을 보냈어요"라고 답하게 한다.
7. 초대받은 Quest는 `invited: true`로 표시만 한다(내 판단).

4–5번(자리, 같은 행사 Shared Quest)을 **U2a**, 6–7번의 표시와 "이미 참여"(`held`)를 **U2b**로 나눈다(내 판단). U2a는 후보마다 이미 있는 `capacity`·`holderCount`와 `holdsSharedQuestFor`로 거른다 [S6][S12]. U2b는 더 크다: 모집 쿼리가 내가 든 Quest를 빼므로 `held`는 내 Quest를 따로 읽어 같은 활동·시각을 맞춰야 하고, 그 Quest는 카드로 보일 수 없어 글로만 답한다. `requested`는 참여 요청 테이블, `invited`는 초대를 따로 읽는다. 도구 설명과 프롬프트도 바뀐다 [S11][S13][S30]. 행사 Quest라면 행사 카드의 `내 파티` 배지가 이미 그것을 보인다 [S87].

## 4. 권장 naive 베이스라인과 개선 경로

**순서의 규칙(사실).** threshold는 평가를 한 번이라도 돌리기 전에 eval set과 같은 저장소에 커밋한다. 결과를 본 뒤 정한 값은 선언하지 않은 것으로 친다. 계획을 바꿔야 하면 원래 값을 두고 수정값과 이유를 옆에 적는다 [S1][S43]. 실제 모델로 돌린 run은 아직 없으므로 지금은 깨끗하다 [S35].

- 내 판단: 실제 모델로 고정 세트를 돌리는 일은 threshold 커밋(C0, P8) 전에는 하지 않는다. 구현 중의 확인은 ScriptedModel 통합 테스트로 한다. 실제 모델 리허설(가격 조회, 모델 id, 도구 호출 확인; P04 보고서 4.4의 10-30 리허설)과 앱의 수동 채팅은 고정 세트에 없는 표현만 쓰고 결과를 커밋하지 않는다. 그 사실을 테스트 문서에 한 줄 적는다. 고정 세트의 질문으로 써 보면 결과를 본 뒤 threshold를 정한 셈이 되기 때문이다 [S43]. 이 체크아웃에는 OpenRouter 키가 없으므로 리허설과 R0을 누가 어떤 키로 돌릴지 정한다(7절).
- naive 베이스라인은 C0 시점의 코드다. 무엇을 naive에 남기고 무엇을 P12로 미룰지는 PM이 정한다(7절). 아래는 권장안이다.
- run마다 단계를 하나씩 바꾼다. 두 단계를 한 번에 바꾸면 어느 쪽이 지표를 움직였는지 가를 수 없다. 짝 비교(exact McNemar, 양측 0.05)로 개선이 유의하려면, 반대로 뒤집힌 케이스가 0·1·2개일 때 고쳐진 케이스가 각각 6·8·10개 이상 있어야 한다 [S48]. 내 판단: P5 케이스 20–30개로는 그보다 작은 개선은 "방향"으로만 말하고, failure analysis를 케이스 단위로 적는다.
- Iteration 3의 공식 run은 R0(naive)와 R1(개선) 둘이고 P12는 2 h다 [S86]. 그래서 기능마다 R1에서 바꿀 단계를 **하나** 정한다(권장: 있으면 합류는 U2a, 행사 합류는 S1). 시간이 남으면 11-04~05에 `--category join-event`처럼 그 기능만 따로, 단계마다 깨끗한 커밋에서 run을 더 돌릴 수 있다. P5 한 번은 약 $0.2–0.8이라 병목은 돈이 아니라 사람과 날짜다 [S92][S48]. 아래 표의 나머지 단계는 Iteration 4까지의 경로다. 팀 일정표의 Iteration 4에는 이 일을 맡을 행이 따로 없다(가까운 것은 P5 "Improve matching and AI reliability" 4 h) [S86].

### 4.2 있으면 합류

- naive(권장, 내 판단): **U1만 넣은 코드**. U1은 "공개 모집 요청이면 먼저 `searchRecruitingQuests`로 찾고, 맞는 것이 있으면 카드와 합류 질문, 없으면 새 제안"이라는 프롬프트 규칙이다. 도구는 지금 그대로다(자리 찬 Quest가 남고, 시각·장소 조건이 없다).
  - 지금 코드 그대로(U1도 없음)를 naive로 두면 합류 제안 정확도는 구조상 0이고 쪼개짐은 F≈1이다(:51이 바로 proposeQuest를 부른다) [S3]. 이렇게 하면 R0이 P5의 기능 없이 돌아 11-01 "implement"와 맞지 않는다(내 판단).

### 4.5 failure analysis 형식 (run마다 한 표)

| run(이름·커밋) | 단계 | 실패한 케이스 id | 실패한 검사(action / cards / proposal / tools) | 원인 분류(프롬프트 규칙 / 도구 거름 / 검색 순서·20칸 / 모델 판단 / 정답·규칙서 오류) | 바꾼 것(프롬프트·모델·검색) | 바뀐 설정 | 다음 run에서 |
|---|---|---|---|---|---|---|---|

- 수집 모듈(새 행일 때)은 칸을 바꾼다: 실패한 글·회차, 틀린 필드(시작·끝·장소·`isEvent`), 실패한 결정적 검사의 이름, 원인 분류(추출 / 인용 / 검사 규칙 / 캠퍼스 기본 / 정답 오류), 바꾼 것(프롬프트·모델·검사).
- 실행 설정을 run마다 적는다 [S43].
  - 모델: `anthropic/claude-haiku-5.5`. 2026-10-26–27의 OpenRouter 목록에서 이 별칭의 `canonical_slug`는 `anthropic/claude-haiku-5.5-20261007`이다 [S49]. 하네스는 넘긴 문자열만 기록하고 응답 모델 id를 남기지 않으므로 [S33], run 날마다 목록의 `canonical_slug`를 결과에 적는다. 날짜판 id로 부를 수 있으면 그것으로 run한다(미확인: 키로 한 번 불러 보면 확인된다). trace에 응답 모델 id를 남기는 변경은 P04 보고서 5.6의 9번이다 [S85].
  - 디코딩: sampling은 공급자 기본값(이 모델은 바꿀 수 없음, seed 없음), `reasoning`도 정하지 않으므로 공급자 기본값 [S49].
  - 제한 8 steps / 30 s / 1,000 토큰 [S5]. 프롬프트 버전 = 커밋 해시(추적하지 않는 파일까지 깨끗한 트리에서만) [S33].
  - 명령: `pnpm eval --model anthropic/claude-haiku-5.5`, 다시 채점은 `pnpm eval:score <run>.json` [S92], threshold 판정은 새로 만들 `pnpm eval:check <run>.json`(예시 이름, 지금 없음; P04 보고서 5.5) [S85].
- 정답이나 규칙서가 틀린 것으로 판명된 케이스는 freeze 뒤에 고치지 않는다. failure analysis에 그 사실을 적고, 바로잡은 케이스를 새 id로 더한다 [S43].

  - 기간 없는 검색의 기본 창(다음 7일)에 걸리는 10-26~28의 행사는 기존 케이스가 쓰는 검색어(재즈, 콘서트, 축제, 공연, 강연, 진로, 취업)를 제목·설명에 쓰지 않는다. 제목에 `축제`, `재즈 콘서트`도 넣지 않는다(resolver 고정) [S29].
  - 새 hobby Quest는 두지 않는다. 두면 `finding-parties-exercise`와 `compound-exercise-or-make`의 정답이 바뀐다 [S34]. P04 보고서도 같은 이유로 운동 Quest를 더하지 않는 (나)를 권한다 [S85].
  - 묶음 예: 합창단 음악회, 피아노 독주회, 점심 버스킹(낮), 오케스트라 연주회, 뮤지컬, 연극 정기 공연, 국악 연주회(17:00 경계), "공연예술의 미래 특강"(제목에 "공연"인 강연), "공연 스태프 모집 설명회", 기간형 사진 전시(10-26~11-27), 낮 세미나 10–12개(창 안의 행사를 21개 이상으로). 질문 10–12개, 정답 globalEvent 카드 약 25장이다. `repeat: 3`이면 micro 분모가 약 75장이다.
  - 세계를 넓힌 뒤에는 WORLD_FACTS와 세계 설명("행사 7")을 고친다 [S29].
- 세계는 P4와 같이 쓴다(내 판단). P04 보고서 5.4는 같은 세계에 질문자의 시간표, 질문자가 든 Quest(목 14:00–14:30), Quest의 끝 시각, 수요일 오후·저녁의 meal·show 모집 Quest 6–8개, PLACES 추가, 행사 좌표 수정을 더한다 [S85]. 그러면 P5의 "오늘 저녁 고기 먹을 사람 4명 모집해줘"(수요일 저녁 meal)에 같은 날 후보가 더 생겨 정답 카드 집합과 판별 규칙 (vi)의 결과가 바뀐다. 반대로 P5의 T6(질문자가 든 Quest)는 P4의 바쁨 판정을 바꾼다. 그래서:
  - 세계 담당 한 명이 P4–P7의 세계 변경을 목록 하나로 모으고(10-28), 세계를 10-29에 얼린 뒤에 정답을 라벨한다(7절).
  - P5의 seed는 P4 케이스가 쓰지 않는 날에 둔다: T6의 Quest는 일요일(10-25), T7·T7'의 행사 E·E2는 기본 7일 창 밖인 10-29(목) 이후. 제목에는 resolver 고정 단어와 기존 검색어를 쓰지 않는다.
  - 서로 정답을 바꾸지 않는지는 C0 전에 ScriptedModel 통합 테스트로 본다(실제 모델 run 아님). P04 보고서의 정답 대조 unit 테스트도 세계가 바뀌면 실패해 표류를 잡는다 [S85].
- T6·T7·T7'은 데이터만 더해서는 안 되고 세계 코드를 바꿔야 한다: `QuestSeed`에 `leader`와 `holders`(질문자 포함)를 더하고, `seedQuests`에 질문자를 넘기고, seed 검사를 고친다. `@@unique([userId, globalEventId])` 때문에 한 사람은 행사 E의 Quest를 하나만 들 수 있으므로, T7의 "다른 사람의 Open Quest"는 리더가 아닌 사람(지금 세계의 오세훈을 쓰면 된다)이 이끈다 [S32][S31][S15]. 에이전트 0.5–1 h(내 판단).

#### 지표, assertion, threshold

threshold 값은 모두 제안이다(내 판단). 형식은 P04 보고서 5.5와 같다(`kind: floor | target`, 고정 case-id 목록, `naiveStructural` 표시) [S85].

- floor는 R0(naive)가 넘어야 할 바닥이다. 못 넘으면 결함으로 다룬다. target은 P12 뒤의 개선 목표이고, R0의 미달은 예정된 결과다. 강의도 capability eval은 낮은 pass rate에서 시작한다고 한다 [S44].
- 테스트 문서에는 한 줄로 정해 둔다(내 판단): "각 지표의 pass threshold는 target이다. floor는 regression floor로 따로 PASS/FAIL을 표시한다." P04와 같은 문장으로 맞춘다(7절).
- floor를 두지 않는 것("—")은 두 경우뿐이다. (1) naive가 **구조상** 못 넘는 하위 집합: J3b(T7은 U2a 없이는 서버가 Shared Quest 보유를 모른다). (2) naive 예상이 0 근처인 capability 하위 집합: E3·E4. 둘 다 thresholds 파일에 `naiveStructural` 또는 `kind: capability`와 "R0 FAIL 예상"을 C0에 적는다. 나중에 낮출 수 없으므로 floor는 naive 예상의 아래 끝보다 충분히 낮게 둔다.
- 값은 비율과 고정 n의 개수(예: `min: 17/20`)로 같이 적는다. 분모가 run마다 달라지는 지표(C2)는 개수로 적는다.
- threshold가 없는 지표(E6의 floor, J5)는 "diagnostic(threshold 없음)"으로 따로 묶어 선언 지표와 섞지 않는다.
- 파일 꼴의 예(내 판단; 이 보고서만으로 읽히게 P04 보고서 5.5의 형식을 줄여 옮겼다 [S85]. case id와 seed 이름은 보기다):

```yaml
# main-server/eval/thresholds.yaml (C0에 eval set과 함께 커밋; 첫 공식 run 전)
sets:
  p5-fixed: [join-or-recruit-badminton-saturday, join-event-this-week-evening-shows]   # 실제로는 C0의 id 전부
subsets:
  J3b: [[join-or-recruit-shared-quest-held, 오세훈의 Open Quest]]   # (case id, seed)
thresholds:
  - id: p5.join.action.floor        # J1
    metric: actionAccuracy
    scope: {category: join-or-recruit, set: p5-fixed}
    kind: floor
    comparator: '>='
    value: 0.50
    min: 27/54                      # 18 케이스 × 3번일 때
    declared: 2026-11-01
  - id: p5.join.action.target
    metric: actionAccuracy
    scope: {category: join-or-recruit, set: p5-fixed}
    kind: target
    comparator: '>='
    value: 0.85
    min: 46/54
    declared: 2026-11-01
  - id: p5.join.serverTrap.target   # J3b: floor 없음, R0 FAIL 예상
    metric: trapPass
    scope: {subset: J3b}
    kind: target
    naiveStructural: true
    comparator: '='
    value: 1.0
    declared: 2026-11-01
```

- pass/fail 표시: 판정 명령(예시 이름 `pnpm eval:check <run>.json`, 지금 없음)이 run 커밋의 이 파일을 읽어 항목마다 `achieved k/n`과 PASS / FAIL / NOT-RUN(scope의 케이스가 다 돌지 않음)을 scorecard의 "Thresholds" 절에 낸다. 값을 바꿀 때는 원래 항목을 두고 `revises:`·`reason:`을 단 새 항목만 더한다 [S43][S85].

- 정의 메모
  - micro 정밀도에서 카드를 하나도 안 보인 케이스는 분모에 0을 더하고, 빈 정답 케이스는 재현율 분모에 0을 더한다. 그래서 E5가 따로 있다.
  - 정답 카드마다 L/P를 정한다. 한 케이스에 둘이 섞일 수 있다. 이 태그와 하위 집합의 분모 정의는 정답의 일부이므로 C0의 `thresholds.yaml`에 `(case id, seed)` 목록으로 둔다(케이스 YAML에는 둘 자리가 없다) [S30].
  - 파티 수는 앱이 이미 행사 카드에 배지로 보인다(앱이 모집 목록에서 셈) [S87]. 하네스 지표가 아니고, 필요하면 앱 쪽 테스트로 잰다. 인원·마감·대상은 Iteration 4의 카드 필드라 Iteration 3에는 재지 않는다(2.1).
  - 한 행사가 셋 이상의 Source에 올라오면 쌍 수가 군집 크기의 제곱으로 늘어 큰 군집에 무게가 쏠린다(내 판단). 그래서 원소마다 같은 군집 안의 맞는 비율을 평균하는 B³도 함께 적는다. B³와 CoNLL F1의 정의는 [S72]를 따른다. F-measure는 정밀도와 재현율에 주는 가중이 방법마다 달라져 F1만으로 방법을 견주는 데 한계가 있다 [S76]. 내 판단: 쌍이 드물어 비율만 보면 흔들리므로 TP/FP/FN 개수를 함께 적는다. 쌍 F1과 군집 지표는 알고리즘의 순위를 다르게 매길 수 있다 [S75]. 블로킹 밖에서 놓친 쌍은 쌍 F1에 보이지 않으므로 Pair Completeness를 따로 잰다 [S74].
  - 작은 n의 한계: n=20에서 80%를 관측하면 95% 구간은 58–92%다. 오류 0이어도 30회차면 95% 상한이 9.5%, 60회차면 4.9%다. "틀린 연결 0"은 그 세트에 대한 진술이다 [S48].
- naive의 실제 값은 모른다(미확인). 실제 모델 run이 한 번도 없기 때문이다 [S35]. 채팅 지표의 floor는 이 불확실성 때문에 예상보다 구간 반폭만큼 낮게 둔다(내 판단). 수집 모듈의 C1 floor는 고정 세트와 겹치지 않는 개발 세트 18건의 관측(회차 약 35%)에서 정했다고 테스트 문서에 적는다. 고정 세트에는 naive를 C0 전에 돌리지 않는다 [S46][S43].

#### 케이스별 assertion (문자열 완전 일치만 쓰는 것은 없다)

- 행동: 규칙 기반 판정(`actionOf`)과 키워드 mentions("이 중 하나" 목록) [S30].
  - 합류 제안: `actions: [TOOL+ASK]`, `tools.required: [searchRecruitingQuests, showQuests]`, `forbidden: [proposeQuest]`, `text.mentions: [[합류, 참여, 함께하실래, 들어가실래]]`, `cards: [{kind: quest, seeds: 정답, max: 정답 수}]`. 승인제면 mentions에 `[[참여 요청, 신청, 승인]]`을 더한다. 카드 검사를 같이 거는 이유는 "합류할 수 있는 파티가 없어요" 같은 부정문도 mentions를 채우기 때문이다.
  - 새 제안: `actions: [PROPOSE]`, `proposal{…}`, `tools.allowed: [searchRecruitingQuests, showQuests]`(먼저 찾기가 over-calling으로 잡히지 않게), `cards: [{kind: quest, max: 0}]`.
  - 되묻기: 지금처럼 `actions: [ASK]` + mentions. lookup을 부르면 실패한다는 점을 케이스 머리 주석에 적는다.
  - 이미 참여(7절 (v)-A를 고르면, U2b가 있을 때): `actions: [TOOL]`, mentions `[[이미]]`, proposeQuest 금지, quest 카드 `max: 0`(내가 든 Quest는 카드로 보일 수 없다 [S30]). (v)-B면 이 케이스는 새 제안 케이스다.
- 도구: required / allowed / forbidden. 인자는 정규화 비교(날짜, Board, id → seed 이름).
- 카드: seed 이름 집합 + 개수. 합산 지표는 run-score가 낸다.
- Proposal: 필드 정규화 비교(시각은 분 단위, Board, 정원, 초대 목록).
- 서버 거름·카드 필드: 통합 테스트의 정확한 값과 metamorphic 관계(조건을 더하면 후보는 부분집합, Quest에 Holder를 채워 정원이 차면 그 Quest가 빠진다) [S44].
- 수집: 필드별 정규화 비교(분 단위 시각, enum, Place id, 대상 범주 집합)와 스키마 유효성.
- 쪼개짐: 생긴 Quest 수(정수)와 잘못된 합류 수.

#### 정답 만드는 법, 2인 라벨, TA 상의

- 행사 합류: 세계 행사마다 종류 라벨(공연 / 강연·세미나 / 전시 / 축제 / 대회·경기 / 설명회·박람회 / 모집·공모 / 기타)을, 질문마다 조건(종류·기간·시간대·장소)을 두 사람이 따로 붙인다. 합의된 속성에 케이스 쪽 스크립트로 결정적 필터를 돌려 정답을 낸다. 서버 코드를 쓰지 않는 것은 위키 정책이 "정답은 코드와 독립인 근거에서"이기 때문이다 [S45].
  - 써 둘 규칙(내 판단): 이번 주는 오늘부터 일요일, 기간이 없으면 다음 7일(프롬프트 :48과 같게) [S3]. 시간대는 7절 (ii)의 표. 기간형 행사는 시간대를 말한 질문에는 정답이 아니다.
  - 종류 사전(우리가 쓴 것, 행샤·식샤의 목록과 무관): 두 사람이 종류를 붙이는 기준이자 검색어 확장의 입력이다. 정답은 사전으로 계산하지 않는다. 사전이 틀려도 정답이 따라 틀리지 않게 하기 위해서다.
- 있으면 합류: 7절의 결정이 들어간 규칙서를 두 사람이 케이스마다 독립적으로 적용해 정답 행동과 정답 카드 집합을 붙인다. 카드는 (케이스, 목록에 나올 수 있는 Quest) 쌍마다 예/아니오로 붙인다(20 × 약 10 = 약 200쌍). 라벨은 세계 freeze(10-29) 뒤에 한다. 세계가 바뀌면 후보 집합이 바뀌기 때문이다.
- **라벨 시간(이 보고서의 다른 곳은 이 줄을 가리킨다; 내 판단)**
  - 있으면 합류: 라벨러당 40–60분 × 2 + 합의 15–30분 = 합 1.6–2.5 h.
  - 행사 합류(지금 세계의 행사 7개와 질문 3–4개): 라벨러당 10–15분 × 2 + 합의 10분 = 합 0.5–0.7 h. 다음 주 묶음(행사 약 30개, 질문 10–12개)을 넣으면 라벨러당 30–40분 × 2 + 합의 15분 = 합 1.3–1.6 h로 바뀐다.
  - 둘을 합한 P5 최소안의 라벨은 2.1–3.2 h다.
  - 공지 읽기(새 행일 때): 합 8–9 h. 같은 행사(Iteration 4): 합 4–6 h.
- 공지 읽기·같은 행사: 두 사람이 원문을 보고 라벨한다(시간은 위 줄; 같은 행사는 라벨 쌍 120–160개). 같은 행사 세트는 블록 안 쌍만 라벨하면 양성이 몇 %밖에 안 된다. 어려운 양성(제목이 다른 재게시, 온라인)과 어려운 음성(1차/2차, 대면/비대면, 역할, 같은 시각 다른 행사)을 일부러 넣어 양성 비율을 30–50%로 맞추고, 블록 전수 부분은 Pair Completeness와 실제 유병률 추정에 따로 쓴다(내 판단).
- 일치도 보고: 관측 일치율 p_o, Cohen's κ(부트스트랩 95% 구간), 양성 일치 p_pos = 2a/(2a+b+c), 음성 일치 p_neg = 2d/(2d+b+c), n을 함께 적는다. 관측 일치가 높아도 우연 일치 항이 크면 κ가 낮게 나오는 역설이 Feinstein & Cicchetti(1990)에 기술돼 있고, 짝 논문이 p_pos·p_neg를 따로 보고하자고 제안했다고 2차 요약이 전한다(서지만 확인했고 원문은 열지 않았다) [S79]. κ의 구간 이름(0.61–0.80 substantial 등)은 Landis & Koch를 따르되 임의적이라는 점을 적는다 [S77]. Krippendorff α ≥ 0.800은 참고 문턱이다 [S78].
  - 모의실험(내 계산) [S48]: 두 라벨러가 각자 95% 정확하고 서로 독립이면, 양성 10%일 때 κ 평균 0.60(n=80에서 95% 범위 0.31–0.84), 30%일 때 0.78, 50%일 때 0.81이다. 그래서 κ만 보고 라벨을 버리면 안 된다.
  - 불일치는 토의로 정하고, 두 원래 라벨 파일과 합의 절차를 남긴다. 합의된 정답만 케이스의 expect에 들어간다.
- **TA 상의.** 모두 팀이 라벨한 세트이므로 강의는 평가 전에 TA와 계획을 "discuss"하라고 하고, 라벨을 누가 어떻게 만들었는지 적으라고 한다 [S43]. 보내기만 해서는 상의가 아니고, 답이 라벨 규칙이나 threshold를 바꾸려면 라벨 전에 와야 한다(내 판단). 강의도 전문가 둘이 독립적으로 같은 판정에 이르는지 보라고 한다 [S44].
  - 메시지 하나로 P4·P5(가능하면 P6·P7까지)를 묶는다. P04 보고서 5.8도 한 메시지를 권한다 [S85]. P5 쪽 내용: 라벨러 둘의 이름, 세트와 케이스 수, 라벨 단위(케이스 × 후보 Quest 쌍, 행사 종류), 일치도 보고(p_o, κ, p_pos·p_neg), 불일치의 합의 절차, "한 디렉터리를 한 세트로 읽는다"는 해석. 판별 규칙 (i)–(viii)과 무관하므로 PM 결정을 기다리지 않아도 된다.
  - 날짜(내 판단): P5 라벨이 10-29에 시작하므로 **10-28 발송**, 회신 요청 10-30을 권한다. P04 보고서 4.4·5.8은 내용 확정 10-28, 발송 10-29, 회신 요청 10-31을 적는다 [S85]. 두 보고서 가운데 하나로 PM이 정한다(7절). 10-29 발송이면, 회신이 라벨 규칙을 바꿀 때 10-31에 다시 라벨한다(위 라벨 시간만큼).
  - 회신이 C0까지 없으면 계획대로 얼리고, 테스트 문서에 보낸 날짜·내용과 "C0 때 회신 없음"을 적는다. 회신이 있으면 그 날짜와 요지를 C0 커밋 메시지와 테스트 문서에 적는다. freeze 뒤에 TA가 바꾸라고 하면 고정 세트는 고치지 않고 새 케이스·새 판으로 대응한다 [S43].
  - 보내는 사람은 PM(김태현)을 제안한다. 라벨러 이름은 a·b 라벨 파일과 함께 테스트 문서에 적는다.

  - (b) 순서: 보인 카드 중 겹치지 않는 것이 모두 겹치는 것 앞에 오는지(위반 쌍 수 = 0이면 통과). 서버가 정렬해 주면 unit·통합 테스트로, 모델이 정렬하면 하네스에 `order` 검사를 더해 잰다 [S30].
  - "직전 수업에서의 도보 시간"은 이동시간 표의 조회값이므로 표 자체의 정확도는 P4의 평가가 맡는다. P5는 카드에 그 값이 맞게 붙었는지만 통합 테스트로 본다(내 판단).
- 2단계 케이스는 freeze 뒤의 추가분이다. 추가 날짜와 이유를 문서에 적고, 그 케이스의 threshold를 첫 run 전에 따로 커밋한다(add-only) [S43].
- "갈 수 있는 파티" 후보 거르기(자리 남음, 이미 든 파티 제외, 같은 행사 Quest 보유 제외)는 P4 Q9에 따라 이 보고서의 Q3(b)와 Q4가 설계했다. P4의 공강 파티도 같은 서버 거름(U2a)을 쓰면 된다(내 판단). U2a를 P12(R1)에 넣으면 P4의 공강 파티 케이스의 답도 R1에서 바뀔 수 있으므로, 두 기능의 R1 설정을 함께 적는다.
- UAT 이야기: P20(11-06)에 정하는 UAT 이야기는 Iteration 3 뒤에 고칠 수 없다 [S43]. P5 시나리오 원문(카드의 도보 시간, 겹침 표시, 지도 강조, "몇십 배"의 행사)을 그대로 수락 기준으로 쓰면, Iteration 4의 UAT까지 끝나지 않는 항목이 고칠 수 없는 FAIL이 된다. 내 판단: Iteration 4 UAT 전에 끝나는 것만 수락 기준에 넣는다(7절).

## 6. Tech depth 주장문 초안 (P22용)

테스트 문서의 지표를 인용하고, 계획과 결과를 다시 적지 않는다. 설계 문서와 테스트 문서는 분리되기 때문이다 [S1][S43]. 어느 주장문을 쓸지는 Q5와 7절의 결정을 따른다.

### 6.1 (A) 공지 읽기 — 새 행 (b)가 승인될 때

한국어

> 학교와 학과 게시판의 공지는 형식이 제각각이어서, 규칙만으로는 많은 글이 Draft로 남는다(테스트 문서 §3, C1의 규칙 베이스라인). SNU Now의 행사 수집 모듈은 공지를 회차 단위의 행사로 읽는다. 모델은 회차마다 시작·끝·장소와 행사인지 아닌지를 정해진 스키마로 내고, 값마다 그 값을 읽은 원문의 줄을 함께 낸다. 서버는 그 줄이 원문에 있는지, 날짜·요일·시각이 그 줄과 맞는지, 신청 기간 줄이 아닌지, 장소가 Place 하나에 정확히 연결되는지를 결정적으로 검사한다. 모든 검사를 통과한 회차만 사람 손 없이 발행하고, 나머지는 실패한 검사와 함께 관리자에게 Draft로 보낸다. 모델 호출이 실패하면 발행하지 않는다. 이 설계는 정확도를 지킨 채 사람 손 없이 발행되는 행사를 늘리는 것을 목표로 한다. 근거 지표는 테스트 문서 §3의 무인 발행률(C1)이고, 틀린 발행(C2)과 틀린 장소 연결(C3)의 상한과 함께 선언돼 있다.

English

> Notices on the university's and departments' boards follow no common format, so rules alone leave many of them as
> Drafts (Testing Documentation §3, rule-only baseline of C1). SNU Now's collection module reads a notice into one
> event per occurrence. For each occurrence the model returns the start, end and place, and whether the notice is an
> event at all, in a fixed schema, each value with the line of the post it was read from. The server checks
> deterministically that the line is in the post, that its date, weekday and time agree with the value, that it is
> not an application-period line, and that the place names exactly one Place. Only occurrences that pass every check
> are published without a person; the others go to the Administrator as Drafts with the checks they failed, and a
> failed model call publishes nothing. The design aims to publish more events without a person while holding
> accuracy. The evidence is the unattended-publication rate (C1) in the Testing Documentation (§3), declared together
> with ceilings on wrongly published occurrences (C2) and wrong Place links (C3).

### 6.2 (C) 질문 응답 — (b)가 안 될 때

한국어

기본 판(쪼개짐은 Iteration 4; 다음 주 행사 묶음이 C0에 없으면 E3·E4 대신 E1·E2를 쓴다):

> SNU Now Assistant는 행사를 찾을 때 질문을 종류·기간·시간대 조건으로 바꾸고, 같은 뜻의 다른 말까지 넓혀 찾는다. 모집 Quest(화면의 "파티")를 만들어 달라는 요청에는 바로 새 글을 만들지 않는다. 같은 활동·같은 날·비슷한 시각의 모집 Quest를 먼저 찾고, 서버는 그중 사용자가 들어갈 수 있는 것만 후보로 준다. 자리가 찬 Quest와, 같은 행사의 Shared Quest를 이미 든 사용자에게는 그 행사의 다른 Quest를 주지 않는다. 맞는 것이 없거나 사용자가 원할 때만 새 공개 Quest를 제안한다. 같은 활동의 모집글이 여러 개로 쪼개져 모두 무산되는 일을 줄이는 것이 목적이다. 근거는 테스트 문서 §3의 E3·E4(같은 뜻의 다른 말과 행사가 많을 때의 재현율), J1·J2(행동과 합류 카드의 정확도), J3b(서버 거름이 있어야 풀리는 함정)다.

English

> The SNU Now Assistant turns an event question into a kind, a period and a time of day, and widens the kind to words
> of the same meaning. Asked to recruit for a Quest (a "파티" on the screens), it does not post a new one at once: it
> first looks for recruiting Quests of the same activity, day and time, and the server returns only those the User can
> join, leaving out full Quests and, for a User who already holds a Shared Quest for a Global Event, the other Quests
> for that event. The Assistant proposes a new public Quest only when none fits or the User insists. The aim is to
> stop recruiting posts for one activity from splitting until none of them fills. The evidence is in the Testing
> Documentation (§3): recall with synonyms and at volume (E3, E4), action and join-card accuracy (J1, J2), and the
> traps that only the server's filter can avoid (J3b).

쪼개짐을 Iteration 3에 C0와 함께 넣었을 때만 끝에 덧붙인다: "그리고 같은 요청을 여러 사용자가 차례로 보낼 때 모집글이 쪼개지는 정도(FR)" / "and the fragmentation of recruiting posts when several Users send the same request in turn (FR)".

- 내 판단: P22(11-05)를 쓸 때 R1이 끝나지 않았으면 위 문장은 그대로 쓴다. 움직임을 주장하는 문장("naive보다 올랐다")은 넣지 않는다. 결과는 테스트 문서의 몫이다 [S1].
