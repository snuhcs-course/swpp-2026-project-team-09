## 1. 비교과(extra.snu) 수집 추가

할 일
- 비교과 목록과 상세를 읽는 수집기를 만든다.
- 비교과의 구조화된 칸(신청 기간, 활동 기간, 회차별 일시·장소)을 Global Event의 시작·끝·장소로 옮긴다.

빠지면 안 되는 것
- **두 번째 Source를 받는 저장 구조로 바꾸기 (가장 먼저).** 지금 원문 키는 SNU 글 번호(`postNumber`) 하나이고 Source 구분이 없다. 두 번째 Source를 붙이면 메시지가 거절되거나, 번호가 겹쳐 조용히 버려진다. `(Source, 글 키)` 구조로 바꾸는 마이그레이션, 워커의 "저장했나?" 질문, 메시지 DTO를 함께 고친다. 3번의 원문 테이블과 같이 설계한다.
- **헤드리스 브라우저.** 비교과 상세 페이지는 접속 대기열(NetFunnel) 때문에 일반 GET으로는 안 열린다. 행샤는 Playwright로 연다. 그러면 워커에 크롬 의존성이 생기고 메모리가 늘어난다(행샤 CronJob 메모리 상한 1 GB). 워커 Docker 이미지와 k8s 설정을 바꿔야 한다.
- **로그인으로 튕기는 글.** 일부 글은 SSO 로그인 페이지로 넘어간다. 건너뛰고 기록을 남긴다.
- **여러 회차인 글.** 비교과는 회차마다 일시·장소를 따로 준다. 한 행으로 둘지 회차마다 나눌지 정한다.
- **목록 범위.** 행샤는 신청 상태 코드 `0001`–`0004`로 거른 목록을 앞 4쪽만 읽는다(한 쪽 12건). 각 코드의 뜻은 아직 모른다.
- **이용 정책.** robots.txt와 약관 확인, 요청 간격.
- **장소 연결.** 비교과 장소 문자열에는 학교 이름이 없는 경우가 많아서, 지금 장소 규칙("번호만 있으면 학교 이름 필요")으로는 Draft가 된다. 2번의 캠퍼스 기본 가정과 같이 본다.

## 2. AI로 Draft 판정해서 발행

할 일
- 규칙만으로 발행되지 못한 Draft(시간이 애매함, 장소 미연결 등)를 AI가 읽고, 통과한 것만 발행한다.
- 서버에 "AI가 판정해서 넣은 것"을 따로 볼 수 있게 남긴다. 앱으로 가는 응답에는 넣지 않는다.

빠지면 안 되는 것
- **ADR.** 용어집의 Draft 정의가 "관리자가 발행한다"이다. AI가 발행하면 정의가 바뀌므로 ADR과 GLOSSARY, README를 고친다.
- **실행 위치.** (W) 워커가 글을 읽은 직후 AI를 부르고 결과를 메시지에 싣는 안과, (M) 메인 서버가 Draft로 저장한 뒤 비동기로 채우는 안이 있다. 보고서 권장은 (W). 워커는 메인 서버의 답을 5초만 기다리므로, 받는 요청 안에서 AI를 부를 수는 없다.
- **안전장치 (보고서 권장).**
  - AI는 정해진 스키마로 회차마다 시작·끝·장소와 행사 여부(`isEvent`)를 내고, 값마다 **근거가 된 원문 줄**을 함께 낸다.
  - 서버가 기계적으로 검사한다: 근거 줄이 본문에 있는지, 날짜·요일·시각이 근거 줄과 맞는지, 신청·접수 기간 줄이 아닌지, 시작 < 끝인지, 한 회차가 24시간 이하인지, 장소가 Place 하나에 정확히 붙는지.
  - 모든 검사를 통과한 회차만 발행한다. 나머지는 Draft로 두고, 관리자 화면에 AI 채움값, 근거 줄, 실패한 검사 이름을 보인다.
  - AI 호출 실패, 시간 초과, 형식 오류이면 발행하지 않는다(fail closed). 행샤는 실패해도 그대로 노출해서(fail open) 약 3주 동안 AI가 안 돈 것을 아무도 몰랐던 것으로 보인다.
- **"AI가 넣은 것" 기록.** 행사에 발행 경로(관리자 / 규칙 / AI), AI 채움값, 근거 줄, 통과·실패한 검사, 모델 id, 판정 시각을 저장한다. 관리자 화면에 거름 조건과 열을 추가한다. 앱 DTO에는 넣지 않는다.
- **장소 기본 가정.** "학교 Source면 다른 곳을 밝히지 않는 한 관악"을 넣을지 정한다. 보고서 실험(개발 세트 18건)에서 규칙만 6/18, AI 추가 10/18, 캠퍼스 기본 가정 추가 13/18이었다. 연건·시흥·평창 Source에는 쓰면 안 된다.
- **기존 Draft 다시 돌리기(backfill).** 이미 쌓인 Draft에도 한 번 돌릴지 정한다. 관리자가 고친 Draft(version > 1)는 건드리지 않는다.
- **데이터 정책.** 공지 본문에는 담당자 이름·전화·이메일이 흔하다. 외부 모델(OpenRouter)로 보내도 되는지 PM이 확인한다.
- **워커 설정.** OpenRouter 키를 워커에 연결한다(운영 Secret, 로컬 `.env`). 워커의 `package.json`에 AI 라이브러리를 추가한다. 운영 워커는 443 포트만 나가는데, OpenRouter는 https라 문제없다.
- **참고: 행샤 방식.** 프롬프트 규칙(신청·행사 기간 분리, 오전/오후를 뒤 시각에도 적용, 회차 분리, 확정된 장소만)은 참고할 만하다. 다만 LICENSE가 없어서 코드·프롬프트 문장은 복사하지 않는다.

## 3. 같은 행사 판별과 중복 제거

할 일
- SNU Now와 비교과에 같이 올라온 같은 행사를 AI가 판정해 하나의 Global Event로 만든다.

빠지면 안 되는 것
- **원문 테이블.** 한 Global Event에 원문 여러 개를 붙이는 테이블(Source, 글 키, URL, 붙인 방법, 근거). 1번 저장 구조와 같이 만든다.
- **판정 흐름 (보고서 권장).**
  - 시작 날짜 ±1일로 후보를 좁힌다.
  - 명백한 쌍은 규칙으로 붙인다: 본문 속 링크가 같은 글을 가리킴, 정규화한 제목이 같음 + 같은 시작.
  - 금지 규칙으로 막는다: 시작 시각이 다름, 1차/2차, 대면/비대면, 역할이 다름.
  - 애매한 쌍만 AI가 "후보 중 하나 또는 없음"을 고른다.
  - `unsure`이거나 실패하면 Draft로 두고 관리자 큐로 보낸다.
- **다대일.** SNU Now는 한 글로 묶고 비교과는 회차마다 따로 올리는 경우가 있다(아래 예시 #5). 처리 방식을 정한다.
- **합칠 때의 규칙.** 이미 Quest(파티)가 달린 행사끼리는 합칠 수 있는지 정한다(보고서 권장: Quest가 없는 쪽만 합침). 발행된 행사의 시각이 원문끼리 다르면 자동으로 바꾸지 말고 관리자 알림을 남긴다.
- **비동기.** 판정은 저장 뒤의 별도 단계로 둔다. 워커가 5초만 기다리기 때문이다.

## 4. 채팅: 있으면 합류, 없으면 만들기

할 일
- "모집해 줘"라고 하면 AI가 바로 새 글을 만들지 않고, 같은 활동·같은 날·비슷한 시각의 모집 Quest를 먼저 찾는다. 있으면 카드를 보여 주고 합류할지 묻는다. 없거나 사용자가 "그래도 새로"라고 하면 새로 제안한다.
- 서버가 들어갈 수 없는 Quest를 거른다: 자리가 찬 Quest, 같은 행사의 Shared Quest를 이미 든 사용자에게 그 행사의 다른 Quest. 정렬·20개 자르기 **앞에서** 거른다.

빠지면 안 되는 것
- **판별 규칙을 PM이 정한다.** 정답 라벨에 필요하다. 권장안:
  - (i) 요청에 없는 조건은 비교하지 않는다. 날짜가 없으면 오늘부터 7일.
  - (ii) 시각을 말하면 ±30분, "저녁"처럼 시간대만 말하면 17–21시 창.
  - (iii) 장소를 말했을 때만 서버가 same / near / other / unknown으로 판정.
  - (iv) 공개 모집에만 적용.
  - (v) 이번에는 Shared Quest 보유만 거르고, "이미 참여 중" 안내는 다음 iteration.
  - (vi) 후보가 여럿이면 인원 많은 순.
  - (vii) 활동과 날짜가 있으면 찾고, 없으면 묻는다.
  - (viii) "민턴"은 동의어, "배민"(배달의민족)은 함정.
- **기존 시험 케이스 수정.** `making-parties-for-event`는 정답이 새 제안에서 합류로 뒤집힌다. 모집 케이스 셋은 먼저 찾기가 over-calling으로 잡히지 않게 허용 도구를 넓힌다. `ask-missing-fields-in-one-question`은 (i)·(vii) 결정에 따라 바뀐다.
- **시험용 세계 확장.** 질문자가 든 Quest, 리더가 다른 Quest를 seed하려면 `QuestSeed`와 `seedQuests`를 바꿔야 한다. P4–P7의 세계 변경과 한 목록으로 모으고, 같은 날 얼린다.
- **함께 하면 좋은 것.** 행사 검색에서 비슷한 말까지 찾기(프롬프트만 바꿈), 검색어를 필터가 아니라 우선순위로 쓰기(약 1 h).

## 5. 검색 도구에 조건 추가 (시각, 파티 인원·마감)

할 일
- **시각:** 행사 검색과 파티 검색 도구 입력에 `after` / `before`(날짜 + 시각)를 추가하고, 서버가 시각으로 거른다.
- **파티 인원:** 파티 검색 도구에 남은 자리 조건(예: `minPlacesLeft`, "2명 이상 자리 남은 파티")을 추가하고 서버가 거른다. 기본값은 "자리가 1개 이상 남은 것"으로, 4번의 서버 거르기와 같은 코드다.
- **파티 마감 여부:** 파티에는 따로 마감 필드가 없다. "마감"은 자리가 다 찼거나 다음 모임 시작이 지난 것이고, 둘 다 지금 데이터로 계산된다. 마감된 파티는 기본으로 후보에서 뺀다. 도구 결과에는 지금처럼 남은 자리(`placesLeft`)와 참여 방식(바로 참여 / 승인제)을 준다.
- 행사의 인원·신청 마감은 이번 범위가 아니다(행사 테이블에 해당 칸이 없고, 찾을 일도 없다고 판단함).

이유
- 지금은 두 도구 모두 날짜(`YYYY-MM-DD`)까지만 받는다. "11/2 17:00 이후"는 그날 전체를 받아 AI가 시각을 읽고 고른다. 후보를 시작이 이른 순으로 20개까지만 주기 때문에, 그날 후보가 많으면 **저녁 것부터 잘린다.**
- 파티 검색은 자리가 찬 파티도 후보로 준다. 남은 자리를 AI가 읽고 판단하므로 결정적이지 않고, 자리 찬 파티가 20칸을 차지한다.

빠지면 안 되는 것
- 프롬프트와 도구 설명에서 "17:00 이후"를 그날 저녁만으로 볼지, 그 뒤 며칠까지로 볼지 정한다.
- "저녁" 같은 시간대 표현은 4번의 판별 규칙 (ii)와 같은 표를 쓴다.
- 기간 내내 이어지는 긴 행사(전시 등)를 시각 조건에서 어떻게 다룰지 정한다.
- 승인제 파티는 참여 요청이 정원을 보지 않고 보내지지만, 리더가 수락할 때 자리가 차 있으면 거절된다. 그래서 자리 조건은 승인제에도 똑같이 적용한다.
- "4명 모집해 줘"처럼 사람 수를 말한 모집 요청을 합류 후보 찾기에 쓸지(예: 남은 자리가 그 수 이상인 파티만) 정한다. 4번 판별 규칙에 한 줄 추가한다.
- 시험 케이스와 고정 테스트(WORLD_FACTS의 자리 찬 `아침 러닝 크루` / `"placesLeft":0` 고정 등)를 같이 고친다.
