# P5 Iteration 3 메트릭과 기록 규칙

작성 2026-10-30. 짝 문서는 `iter3-p5 계획.md`이다. 근거는 P05 사전조사 보고서, P19 AI metric 스펙·케이스(`.scratch/iteration-2/P19-ai-metric/`), 현재 코드와 CI(`.github/workflows/ci.yml`)다. threshold 값과 시간은 모두 제안이고, PM이 확정한다.

## 1. 무엇을 메트릭으로 평가하나

수업 규칙상 고정 세트, threshold 선커밋, run 결과, failure analysis가 필요한 것은 **AI가 판단하는 기능**이다. 결정적인 서버 로직은 메트릭이 아니라 일반 테스트(CI)로 검증한다.

| 기능 (계획 번호) | AI가 판단하나 | 메트릭 | 일반 테스트 |
|---|---|---|---|
| 1. 비교과 수집 | 아니요 (파서) | 수업 의무 없음. 운영 기록만 | 필요 |
| 2. Draft AI 판정·발행 | 예 | **평가 A** | 필요 |
| 3. 같은 행사 판별 | 예 (애매한 쌍) | **평가 B** | 필요 |
| 4. 있으면 합류, 없으면 만들기 | 예 | **평가 C** | 필요 |
| 5. 검색 조건 (시각, 파티 자리·마감) | 조건을 정하는 건 AI, 거르기는 서버 | 평가 C의 케이스 + **평가 D**(검색) | 필요 |

## 2. 기능별 평가

### 평가 A. Draft AI 판정·발행

목적: 사람 손 없이 얼마나 많이 발행했는지와, 발행한 것이 틀리지 않았는지. 둘은 서로 맞바꿀 수 있으므로 **항상 짝으로** 보고한다.

| id | 요소 | 정의 | 비교 방법 | 바닥 / 목표 (제안) |
|---|---|---|---|---|
| C1 | 무인 발행률 | 정답과 맞게 자동 발행된 회차 ÷ 정답상 발행할 수 있는 회차 | 회차 단위 | ≥ 25% / ≥ 60% |
| C2 | 틀린 발행 | 발행된 회차 중 시작·장소(끝이 있으면 끝)가 하나라도 틀린 **개수** | 시작·끝은 분 단위, 장소는 Place id | ≤ 2회차 / ≤ 1/30 |
| C3 | 틀린 장소 연결 | Place id를 냈는데 정답과 다른 수 | Place id | = 0 / = 0 |
| C4 | 필드별 정확도 | 시작·끝·장소·행사 여부의 정밀도·재현율, **지어낸 값 비율**(정답에 없는데 낸 값) | 필드별 정규화 비교 | 스키마 유효 100% / 시작 정밀도 ≥ 0.95, 재현율 ≥ 0.80 |

- **고정 세트:** 아직 아무 파서도 돌리지 않은 공지 60건(약 70–80회차). SNU Now와 비교과를 섞고, 이미지만 있는 글, 행사가 아닌 글, 여러 회차인 글, 신청 기간 줄이 있는 글, 연도 없는 날짜, 번호만 있는 장소를 일부러 넣는다.
- **개발 세트:** 보고서에서 규칙 파서를 돌린 18건. 바닥선을 정하는 데만 쓰고 고정 세트에 넣지 않는다.
- **정답:** 두 사람이 원문을 보고 따로 라벨한다. 회차마다 시작·끝·장소, 행사 여부, "발행해도 되는가"를 붙이고, 일치도를 보고한 뒤 합의한다.
- **naive(R0):** 지금의 규칙 파서. 개선 단계 예: AI 채움 → 근거 줄 검사 → 캠퍼스 기본 가정 → (선택) 3번 반복 일치.

### 평가 B. 같은 행사 판별

목적: 잘못 합쳐서 행사가 사라지는 일이 없는지(정밀도 우선), 그리고 중복을 얼마나 잡는지.

| id | 요소 | 정의 | 바닥 / 목표 (제안) |
|---|---|---|---|
| D1 | 잘못된 자동 병합 | 다른 행사를 자동으로 합친 수 | = 0 / = 0 |
| D2 | 쌍 정밀도·재현율·F1 | **TP/FP/FN 개수를 함께** 적는다 | — / 관리자 큐 포함 재현율 ≥ 0.80 |
| D3 | 후보 단계 누락 | 시작 ±1일 후보에서 빠진 진짜 쌍의 비율 (Pair Completeness) | ≥ 0.95 |
| D4 | 판단 보류율 | AI가 `unsure`로 관리자에게 넘긴 비율 | ≤ 0.30 |
| D5 | 다대일 | 한 글 ↔ 여러 회차 묶음을 맞게 묶은 비율 | 진단용(threshold 없음) |

- **고정 세트:** 쌍 120–160개.
  - 양성: 본문에 상대 링크가 있는 쌍, 제목이 다른 쌍, 다대일.
  - 어려운 음성: 대면/비대면, 1차/2차, 같은 시각의 다른 행사.
  - 양성 비율을 30–50%로 맞춘다. 예: SNU Now 178079 ↔ 비교과 PGM012002382는 같은 행사이고, SNU Now 177707(비대면)은 함정이다.
- **정답:** 두 사람이 쌍마다 같음/다름을 따로 라벨한다. 양성이 드물면 κ가 낮게 나오기 쉬우므로 관측 일치율, 양성 일치, 음성 일치를 함께 보고한다.
- **naive(R0):** 같은 시작 + 제목 유사도 규칙만. 개선 단계 예: 금지 규칙 → 애매한 쌍만 AI가 고르기 → 다대일 처리.

### 평가 C. 채팅: 있으면 합류 + 검색 조건

목적: 맞는 행동(합류 제안 / 새로 만들기 / 되묻기)을 하는지, 맞는 파티를 보여 주는지, 함정에 빠지지 않는지.

| id | 요소 | 정의 | 바닥 / 목표 (제안) |
|---|---|---|---|
| J1 | 행동 정확도 | 합류 제안 / 새 제안 / 되묻기 판정을 통과한 실행 비율 | ≥ 0.50 / ≥ 0.85 |
| J1-P | 새 제안 정확도 | 새로 만들 때 Proposal 필드(시각, 게시판, 정원) | ≥ 0.80 / ≥ 0.90 |
| J2 | 합류 카드 정확 집합 | 보여 준 파티 = 정답 파티 | ≥ 0.40 / ≥ 0.80 |
| J3a | 모델이 피할 수 있는 함정 | 자리 찬 파티, 시간은 같은데 다른 활동, "배민" | ≥ 2/3 / 3/3 |
| J3b | 서버 거르기가 있어야 피하는 함정 | 같은 행사 Shared Quest 보유 | 바닥 없음(naive는 구조상 실패) / 전부 통과 |
| J4 | 잘못된 합류 | 다른 활동의 파티를 보여 준 횟수 | ≤ 2/6 / 0/6 |
| J6 | 두 턴 흐름 | 행사 카드 → "그 행사 파티 있어?" → 그 행사의 파티 카드 | ≥ 0.60 / ≥ 0.90 |
| J5 | 안정성 | 3번 반복에서 모두 통과한 케이스 비율 (pass^3) | 진단용 |

- **고정 세트:** 채팅 하네스에 새 카테고리 YAML(`join-or-recruit` 18–20케이스 + 시각·자리·두 턴 케이스). 각 3번 반복한다.
- **정답:** PM이 정한 판별 규칙서를 두 사람이 케이스마다 따로 적용해 붙이고 합의한다.
- **naive(R0):** "먼저 찾기" 프롬프트만. 개선(R1): 서버 거르기 + 시각·자리 조건.

### 평가 D. 조건에 맞는 행사·파티를 다 찾는지 (검색)

목적: "공연 가는 파티 찾아줘"에서 비슷한 말, 오타, 후보가 많을 때도 빠짐없이, 엉뚱한 것 없이 찾는지.

| 하위 집합 | 예시 | 지금 코드에서 예상 |
|---|---|---|
| L 글자 그대로 | "공연" → 제목에 공연 | 통과 |
| P 비슷한 말 | "공연" → `피아노 독주회`, `뮤지컬 〈…〉` (제목·설명에 "공연" 없음) | **행사는 실패**(단어 필터에서 빠짐). 파티는 AI가 읽어서 통과 가능 |
| T1 글쓴이 오타 | `콘서드 같이 가실 분` 파티, `재즈 콘서드` 행사 | 파티는 통과 가능, **행사는 실패** |
| T2 질문 오타 | "콘서드 가는 파티 찾아줘" | AI가 고쳐 넘기면 통과 |
| V 후보가 많음 | 같은 날 행사 21개 이상, 정답이 저녁에 몰림 | **실패**(이른 20개만 넘어감) |
| H 시각 경계 | "11/2 17:00 이후" → 16:30은 빼고 17:00은 포함 | 결정적이지 않음 |
| S 자리 | 자리 찬 파티 빼기, "2명 자리 남은 파티" | 결정적이지 않음 |
| E 빈 정답 | 해당하는 것이 없음 | 통과 |

| id | 지표 | 바닥 / 목표 (제안) |
|---|---|---|
| E1 | 카드 micro 정밀도 (Σ맞게 보인 카드 ÷ Σ보인 카드, 3번 반복 합산) | ≥ 0.70 / ≥ 0.90 |
| E2 | 재현율, 하위 집합 L | ≥ 0.70 / ≥ 0.90 |
| E3 | 재현율, 하위 집합 P·T1 | 바닥 없음(R0 실패 예상) / ≥ 0.80 |
| E4 | 재현율, 하위 집합 V | 바닥 없음(R0 실패 예상) / ≥ 0.80 |
| E5 | 빈 정답 맞힘 (카드 0장 + "없어요" 류 답) | ≥ 4/6 / 6/6 |
| E6 | 정확 집합 일치율 | 진단용 |

- 정답 카드는 `seeds = 정답 전체`, `max = 정답 수`로 **정확 집합**으로 둔다. 엉뚱한 카드를 허용하지 않기 위해서다.
- 하위 집합 태그는 케이스 YAML에 둘 자리가 없으므로(`strictObject`), threshold 파일에 `(case id, seed)` 목록으로 둔다.
- 카드 합산(micro 정밀도·재현율)은 run-score에 새로 추가해야 한다(1–1.5 h, P4와 같은 코드). 저장된 run을 다시 채점할 수 있으므로 R0 뒤에 넣어도 된다.
- **시험용 세계에 넣을 데이터:** 비슷한 말 행사, 오타 글, 같은 날 행사 21개 이상.
  - 기존 케이스가 묻지 않는 날짜(예: 다음 주)에 둔다.
  - 기존 케이스가 쓰는 검색어(재즈, 공연, 축제 등)를 제목에 피한다.
  - hobby 게시판 Quest는 더하지 않는다(운동 케이스 정답이 바뀜).
  - **세계는 11-01 고정 전에** 넣는다. 세계는 모든 케이스의 입력이라 고정 뒤에는 바꿀 수 없다.

#### P19가 이미 다루는 것과 빠진 것

P19 성적표는 행동 재현율, 도구 선택, 인자 정확도, 과잉·과소 호출, 카테고리별 통과율, pass^3이다. **검색 결과의 정밀도·재현율은 없다.**

| 확인하고 싶은 것 | P19 현황 |
|---|---|
| 전부 다 찾나 | 케이스 단위로만, 느슨하게. 정답 카드가 모두 보여야 통과지만, `max`가 정답보다 큰 케이스(예: 정답 2개, 최대 3장)는 엉뚱한 카드 하나를 허용한다. 여러 케이스를 합친 지표가 없다 |
| 비슷한 말 | 사실상 없음. "이번 주에 공연 뭐 있어?"의 정답 `가을 재즈 콘서트`는 설명에 "정기 공연입니다"가 있어서 결국 글자 그대로 일치하는 케이스다 |
| 뜻으로 고르기 (파티) | 조금. "같이 운동할 파티" → `저녁 농구 한 판`(설명에 "운동" 없음). 다만 게시판으로 이미 좁혀진 상태다 |
| 오타 | 없음 |
| 후보가 많을 때 | 없음 (세계가 행사 7, 파티 11) |
| 자리 찬 파티 빼기 | 간접적. 자리 찬 `아침 러닝 크루`가 세계에 있지만 직접 검사하는 케이스는 없다 |
| 시각 조건 | 없음. 날짜 인자만 본다 |
| 없는 걸 없다고 하기 | 있음 (`no-data`) |

## 3. 테스트와 CI

지금 CI는 서버마다 `pnpm test`(vitest e2e-spec, 실제 DB 컨테이너)를 돌린다. 실제 모델로 채점하는 `pnpm eval`은 CI에 없다(키 없음, 비용, 비결정성). 하네스 자체의 테스트(`eval-*.e2e-spec.ts`)는 CI에서 돈다.

### 3.1 CI에 넣는 것 (모델 없이 결정적, `pnpm test`)

| 기능 | 테스트 | 서버 |
|---|---|---|
| 1 | 비교과 목록·상세 파서(저장한 HTML 픽스처), 로그인으로 튕긴 글 건너뛰기, 회차 매핑, `(Source, 글 키)` 저장과 중복 거절 | worker, main |
| 2 | 근거 줄 검사 함수(본문에 있는지, 요일·시각 일치, 신청 줄 배제, 24시간 초과), 가짜 모델 응답으로 발행 판단, **AI 실패 시 발행 0건**, "AI가 넣은 것" 저장, **앱 응답에 AI 필드가 없는지**, 관리자 화면 거름 | worker, main |
| 3 | 명백한 쌍 규칙(같은 링크 등), 금지 규칙(대면/비대면 등), 합치기 동작(Quest 있는 행사는 안 합침), `unsure`면 Draft + 관리자 큐 | main |
| 4·5 | 서버 거르기(자리 찬 Quest, Shared Quest 보유)가 **20개 자르기 전에** 일어나는지, 시각 `after`/`before` 경계(17:00 정각 포함 여부), 자리 조건, "조건을 더하면 결과는 부분집합" 관계, 가짜 모델로 "먼저 찾기" 흐름 | main |
| D (검색 단계) | 조건을 주고 검색 서비스를 직접 불렀을 때 **정답이 후보 안에 있는지**(후보 재현율). 오타·비슷한 말 글이 후보에 들어가는지(개선 뒤), 21개 이상일 때 저녁 것이 잘리지 않는지 | main |
| 평가 도구 | 새 실행기(수집, 같은 행사)의 채점 코드, 고정 세트 무결성(개수 ≥ 30, 라벨 파일 형식, threshold 파일이 세트의 모든 id를 덮는지), threshold 판정 코드 | main, worker |

- 검색 단계(평가 D의 CI 테스트)와 선택 단계(평가 C·D의 모델 run)를 나눠야, R0·R1에서 실패했을 때 "서버가 후보에 안 줬다"와 "AI가 못 골랐다"를 구분할 수 있다.
- 기존 고정 테스트(`eval-cases.e2e-spec.ts`의 케이스 개수, 카테고리 표, `repeat` 개수, WORLD_FACTS)는 케이스가 늘 때마다 깨진다. P4–P7이 동시에 고치므로, "고정 세트를 포함하는지" 검사로 **한 번만** 바꾼다.
- AI를 부르는 부분은 채팅처럼 가짜 모델(`test/scripted-model.ts` 방식)로 테스트한다. 수집 쪽에도 같은 모델 포트(주입)를 둔다.

### 3.2 CI 밖에서 돌리는 것 (실제 모델)

- `pnpm eval`(채팅, 평가 C·D)과 새 수집·같은 행사 실행기(평가 A·B)의 R0·R1 run.
- 정해진 날, 깨끗한 커밋에서 돌리고 결과를 커밋한다(아래 4절).

### 3.3 추가하면 좋은 CI (선택, PM 결정)

1. **저장된 결과 다시 채점:** 커밋된 run JSON을 모델 없이 다시 채점하고(`pnpm eval:score`) threshold 판정까지 하는 단계. 키가 필요 없고 결정적이다. 채점 코드를 바꿔도 옛 결과가 같은 숫자를 내는지 지켜 준다.
2. **수동 실행 워크플로:** GitHub Actions에서 버튼으로 실행하는 eval 작업(`workflow_dispatch`)에 OpenRouter 키를 Secret으로 넣는다. 누가 어느 커밋으로 돌렸는지 GitHub에 남는 대신, 키와 예산 관리가 필요하다.

## 4. 기록 규칙: "이걸 바꿨더니 이만큼 좋아졌다"를 증명하려면

### 4.1 순서 규칙 (수업 규칙)

1. **threshold는 첫 run 전에 커밋한다.** 고정 세트와 같은 저장소, 같은 커밋(C0)에 둔다. 결과를 본 뒤 정한 값은 선언하지 않은 것으로 친다.
2. **고정 세트는 고정 뒤에 고치지 않는다.** 정답이나 규칙서가 틀린 것으로 판명되면 failure analysis에 적고, 바로잡은 케이스를 **새 id로 추가**한다.
3. **threshold를 바꿔야 하면** 원래 항목을 지우지 않고 `revises:`(원래 id)와 `reason:`을 단 새 항목을 더한다.
4. **고정 세트로 실제 모델을 미리 돌리지 않는다.** 리허설과 앱에서의 수동 채팅은 고정 세트에 없는 표현으로만 하고, 결과를 커밋하지 않는다. 이 사실을 테스트 문서에 한 줄 적는다.
5. **세계(시험 데이터)는 C0 뒤에 바꾸지 않는다.** C0 뒤에는 세계를 바꾸지 않는 케이스만 추가한다. 세계를 바꿔야 하는 평가는 별도 세계나 별도 질문자로 두고, 그 평가의 threshold를 그 평가의 첫 run 전에 따로 커밋한다.

### 4.2 이름 붙이기

| 이름 | 뜻 |
|---|---|
| **C0** | 고정 세트 + threshold + 세계를 담아 체크인(11-01) 전에 `2.0/Main`에 merge한 squash 커밋. 태그를 단다(예: `eval-freeze-iter3`). 기능별로 늦으면 기능마다 따로 C0를 둔다 |
| **R0** | C0의 깨끗한 후손 커밋에서 돌린 첫 공식 run (naive 기준선) |
| **R1, R2 …** | 개선을 하나씩 넣은 뒤의 run |

### 4.3 run마다 기록할 것

| 항목 | 이유와 주의점 |
|---|---|
| 날짜와 시각 (KST) | 모델 별칭이 가리키는 버전이 바뀔 수 있어서 시점이 필요하다 |
| **커밋 해시 + 브랜치/태그** | 프롬프트·도구·서버 코드의 버전이다. **추적하지 않는 파일까지 깨끗한 트리**에서만 돌린다. 하네스의 dirty 검사는 `git add`하지 않은 파일을 보지 못한다. 그래서 새 케이스 YAML을 커밋하지 않고 돌려도 run 이름에 `-dirty`가 붙지 않는다 |
| 고정 세트 버전 | 케이스 id 목록과 해시. C0 태그를 적는다 |
| threshold 파일 버전 | 커밋 해시와 각 항목의 `declared` 날짜 |
| 세계 버전 | seed 파일의 커밋. 시계 고정값(지금 2026-10-21 수 14:05) |
| **모델** | 넘긴 문자열(예: `anthropic/claude-haiku-5.5`)과 **그날의 실제 버전**(OpenRouter 목록의 `canonical_slug`, 10-27 기준 `anthropic/claude-haiku-5.5-20261007`). 하네스는 응답한 모델 id를 기록하지 않으므로 손으로 적는다. 날짜판 id로 부를 수 있으면 그것으로 돌린다 |
| 디코딩 설정 | 공급자 기본값(Haiku 5.5는 temperature를 받지 않음, seed 없음), reasoning 설정. 비결정성은 반복으로 잰다 |
| 실행 제한 | 8 steps / 30 s / 출력 1,000 토큰. 바꾸면 그 run이 다른 조건이라는 뜻이다 |
| 반복 횟수 | 예: 케이스마다 3번 |
| 임베딩 모델 (도입하면) | 모델 id와 차원 |
| 수집 실행기 (평가 A·B) | 파서 버전(커밋), 켠 검사 목록, 캠퍼스 기본 가정 사용 여부 |
| 사용량과 비용 | 입력(캐시 읽기·쓰기 따로), 출력 토큰, 추정 비용. 가격 조회가 실패하면 대체 가격으로 계산되어 예산 가드가 일찍 멈출 수 있다 |
| 실행한 사람과 키 | 누가 어떤 키·예산으로 돌렸는지 |
| 결과 파일 | `eval/results/`는 기본으로 무시되므로 `git add -f`로 커밋한다. JSON(모든 턴의 trace)과 성적표 `.md`를 같이 둔다 |

### 4.4 비교를 믿을 수 있게 하는 규칙

- **run마다 바꾸는 것은 하나만.** 두 가지를 한 번에 바꾸면 어느 쪽이 지표를 움직였는지 가를 수 없다.
- **같은 고정 세트, 같은 세계, 같은 설정으로만 비교한다.** 다르면 숫자를 나란히 놓지 않는다. 비교는 `pnpm eval:compare <a.json> <b.json>`으로 한다.
- **작은 표본의 한계를 적는다.**
  - 짝 비교(exact McNemar, 양측 0.05)에서 개선이 유의하려면, 반대로 뒤집힌 케이스가 0·1·2개일 때 고쳐진 케이스가 각각 6·8·10개 이상이어야 한다. 그보다 작은 개선은 "방향"으로만 말한다.
  - n = 20에서 80%를 관측하면 95% 구간은 58–92%다. 오류 0이어도 30회차면 95% 상한이 9.5%, 60회차면 4.9%다.
  - 비율은 항상 `k/n` 개수와 함께 적는다.
- **채점 코드를 바꾸면** 이전 run도 새 코드로 다시 채점하고(`pnpm eval:score`), 다시 채점한 커밋을 적는다.
- **외부 데이터는 스냅숏으로.** 평가 A·B의 원문은 사이트가 바뀌므로 HTML을 저장해 두고 받은 날짜를 적는다. 실행기는 저장본만 읽는다.
- **정답의 출처를 남긴다.** 라벨러 두 사람, 라벨 날짜, 두 원래 라벨 파일, 일치도(p_o, κ, 양성·음성 일치, n), 합의 절차. TA에 보낸 날짜와 회신 요지(또는 "C0 때 회신 없음").

| 실패한 케이스 | 실패한 검사 (행동 / 카드 / Proposal / 도구 / 필드) | 원인 분류 | 다음 run에서 바꾸는 것 |
