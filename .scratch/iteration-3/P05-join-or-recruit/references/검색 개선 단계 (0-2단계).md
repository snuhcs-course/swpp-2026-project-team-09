# 행사·파티 검색 개선 단계 (0–2단계)

작성 2026-10-30. 채팅 Assistant가 "조건에 맞는 행사·파티를 찾아 주는" 검색 단계를, 행사·파티가 수백–수천 건으로 늘어도 버티게 바꾸는 계획이다. 오픈소스 Onyx(사내 문서 검색 AI)의 검색 구조를 참고했다. 시간은 모두 추정이다.

관련 문서: `iter3-p5 계획.md`(4·5번), `iter3-p5 메트릭.md`(평가 D).

## 1. 지금 구조와 한계

### 1.1 지금 흐름

```
사용자 질문
  → Haiku가 검색 도구 호출 (기간, 단어 등)
  → 서버가 DB에서 후보를 거르고 시작이 이른 순으로 최대 20개
  → Haiku가 후보를 읽고 맞는 것을 골라 ID로 카드 표시
```

| 위치 | 지금 동작 |
|---|---|
| 행사 검색 도구 (`search-global-events.ts`) | 입력: `from`/`to`(날짜), `place`, `words`(최대 5개). 서버는 기간이 겹치고 **제목이나 본문에 단어가 하나라도 들어간**(대소문자 무시 부분 일치) 발행 행사만 남긴다. 시작이 이른 순으로 20개 |
| 파티 검색 도구 (`search-recruiting-quests.ts`) | 입력: `board`, `from`/`to`(날짜, 생략 가능), `globalEventId`. **단어 입력이 없다.** 모집 중인 Quest를 DB에서 **전부** 읽은 뒤 메모리에서 기간으로 거르고, 시작이 이른 순으로 20개 |
| 고르기 | Haiku가 후보의 제목·설명(300자)·시각을 읽고 고른다 |
| 실행 제한 | 메시지당 8단계, 총 30초, 단계당 출력 1,000토큰, 재시도 0 |

### 1.2 한계

- **행사는 단어 필터에서 빠지면 끝이다.** "공연"으로 검색하면 제목·본문에 "공연"이 없는 "피아노 독주회"는 후보에 오르지 않는다. 글쓴이 오타("콘서드")도 같다.
- **20개 제한과 정렬이 어긋난다.** 시작이 이른 순으로 자르므로, 그날 후보가 많으면 저녁 행사나 늦은 파티부터 잘린다.
- **시각 조건이 없다.** 날짜 단위까지만 거르고, "17:00 이후"는 AI가 시각 문자열을 읽고 판단한다.
- **파티는 자리 찬 것도 후보로 준다.** 자리는 AI가 읽고 판단한다.
- **파티 검색은 매번 전체를 읽는다.** 수천 건이면 무거워진다.
- 파티는 AI가 후보를 다 읽으므로 비슷한 말과 오타에는 비교적 강하다. 다만 게시판을 잘못 골랐거나 후보가 20개를 넘으면 빠진다.

## 2. 참고: Onyx의 검색 구조

Onyx(onyx-dot-app/onyx)의 검색 도구는 5단계다.

1. **검색어를 여러 갈래로 만든다.** LLM이 의미 검색용 문장 1개와 키워드 검색어 최대 3개를 따로 만든다. 원래 질문과, 대화 LLM이 넘긴 검색어도 함께 쓴다. 키워드 프롬프트에는 "드물거나 고유한 용어는 바꾸거나 확장하지 말라"는 규칙이 있다.
2. **검색어마다 하이브리드 검색을 한다.** OpenSearch에서 두 갈래를 동시에 돈다.
   - 벡터 유사도 검색(임베딩, 코사인 유사도, 후보 500)
   - 키워드 검색(BM25, 단어 중 하나라도 맞으면 걸림. 가중치는 본문 일치 1.0, 본문 구절 일치 1.5, 제목 0.1, 제목 구절 0.2)

   권한 같은 공통 필터는 두 갈래에 똑같이 건다. 갈래마다 점수를 min-max 정규화한 뒤 0.5 : 0.5로 평균한다. 오타 허용(fuzziness)은 "재현율이 오히려 나빠지고 느려서" 일부러 껐다.
3. **여러 검색어의 결과를 가중 RRF로 합친다.** `점수 = Σ 가중치 / (50 + 순위)`. 가중치는 의미 검색어 1.3, 키워드 검색어 1.0, 대화 LLM 검색어 0.7, 원래 질문 0.5다.
4. **LLM이 고른다.** 합친 후보를 보여 주고 "관련 있는 번호만, 의심되면 넣어라"로 고르게 한다.
5. 고른 문서마다 앞뒤 내용을 더 읽을지 LLM이 정한다(우리에게는 해당 없음).

**설계 원칙:** "AI의 각 결정 단계를 최대한 단순하게", "확실한 규칙(권한)은 코드가 검색 쿼리에서", "후보는 기계가 넓게 모으고 AI는 작은 묶음에서 고른다".

**우리와 다르게 할 것**
- **OpenSearch를 새로 들이지 않는다.** 운영 DB가 RDS PostgreSQL 18(`db.t4g.micro`)이라, Postgres 확장(`pg_trgm`, `pgvector`)으로 같은 구조를 만든다.
- **검색어를 만드는 LLM 호출을 따로 두지 않는다.** Haiku가 도구를 부를 때 검색어 묶음을 같이 만든다. 30초 제한 안에서 시간을 아끼기 위해서다.
- **고르기도 따로 부르지 않는다.** 지금처럼 대화 중인 Haiku가 후보를 읽고 고른다.

## 3. 0단계: 지금 구조 안에서 고치기

**목표:** 수백 건 규모까지 "기간 안 후보는 AI가 다 읽게" 만든다. 새 확장이나 외부 서비스가 필요 없다.

### 3.1 바꾸는 것

1. **확실한 조건은 서버가 SQL로 거른다.**
   - 파티: 자리 남음(`holderCount < capacity`), 다음 모임이 아직 안 지남, 같은 행사의 Shared Quest를 이미 들고 있지 않음(`holdsSharedQuestFor` 재사용), 게시판, 기간.
   - 행사: 발행됨, 안 끝남, 기간.
   - 파티 검색은 지금처럼 전부 읽은 뒤 메모리에서 거르지 않고, 조건을 **DB 쿼리로 옮긴다.**
   - 거르기는 **정렬과 20개 자르기 앞에서** 한다.
2. **시각 조건을 추가한다.** 두 도구 입력에 `after`/`before`(날짜 + 시각)를 넣고 서버가 거른다. "17:00 이후"의 경계(정각 포함 여부)와, 기간 내내 이어지는 긴 행사를 어떻게 다룰지 정한다.
3. **자리 조건을 추가한다.** 파티 검색 입력에 남은 자리 조건(예: `minPlacesLeft`)을 넣는다. 기본은 1 이상이다.
4. **행사 검색의 단어를 "필터"에서 "우선순위"로 바꾼다.**
   - 지금: 단어가 하나라도 들어간 행사만 남김.
   - 바꾸면: 기간(과 시각) 안의 행사를 **모두** 후보로 두고, 단어가 맞는 행사를 앞에 세운다. 맞는 것이 몇 개인지에 따라 순서를 정하고, 같으면 시작 순으로 한다. 남은 칸은 단어가 안 맞는 행사로 채운다.
   - 효과: "피아노 독주회", "재즈 콘서드"처럼 단어가 안 맞는 행사도 칸이 남으면 AI가 읽고 판단할 기회를 얻는다.
5. **후보 수와 설명 길이를 조정한다.** 후보 20 → 30개, 설명 300 → 150자 정도. 입력 토큰이 크게 늘지 않게 맞춘다.
6. **프롬프트를 고친다.**
   - 검색어에 비슷한 말도 넣으라고 지시한다(예: 공연 → 콘서트, 음악회, 연주회, 뮤지컬).
   - 게시판을 확신할 수 없으면 게시판 없이 파티를 검색하라고 지시한다.
   - 고를 때는 "확실히 다른 것만 빼라"는 관대한 기준을 둔다(Onyx의 "의심되면 넣어라"와 같은 방향).

### 3.2 예시

"11/2 저녁에 볼 만한 공연 있어?" →
- 도구 입력: `after = 2026-11-02 17:00`, `before = 2026-11-02 23:59`, `words = [공연, 콘서트, 음악회, 연주회, 뮤지컬]`
- 서버: 그날 17시 이후 발행 행사 전부 → 단어가 맞는 것 먼저 → 30개까지
- Haiku: 후보를 읽고 "피아노 독주회"(단어 불일치, 뒤쪽에 있음)도 공연으로 골라 카드로 보여 줌

### 3.3 효과와 한계

- **해결:** 시각 경계, 자리 찬 파티, 20칸에서 저녁 것이 잘리는 문제, 단어 필터 때문에 비슷한 말·오타 행사가 후보에서 빠지는 문제(후보가 30개 안일 때).
- **남는 한계:** 기간 안 후보가 30개를 넘으면 단어가 안 맞는 행사는 여전히 뒤에서 잘린다. "다음 달 공연 다 보여줘"처럼 넓은 질문에 약하다.

### 3.4 범위와 시간

- 이번 Iteration 계획 4·5번(서버 거르기, 시각·자리 조건)과 대부분 겹친다. 그래서 **Iteration 3에 같이 하는 것을 권한다.**
- 시간: 2–3 h (계획 4·5번과 겹치는 부분 포함, 테스트 별도).

## 4. 1단계: 키워드 갈래 개선 (pg_trgm + 키워드 묶음 + RRF)

**목표:** 후보가 30개를 넘어도 "가장 그럴듯한 것"이 앞에 오게 한다. 오타와 조사가 붙은 표현도 점수로 잡는다.

### 4.1 pg_trgm: 글자 3개 조각으로 비슷한 정도를 재기

- Postgres에 기본으로 들어 있는 확장이다(`CREATE EXTENSION pg_trgm`).
- 단어 앞에 빈칸 두 개, 뒤에 하나를 붙여 연속 3글자 조각으로 자르고, **유사도 = 겹치는 조각 수 ÷ 두 단어 조각의 합집합 크기**로 0–1 점수를 낸다.

```
"콘서트" → [  콘] [ 콘서] [콘서트] [서트 ]
"콘서드" → [  콘] [ 콘서] [콘서드] [서드 ]
겹침 2 / 합집합 6 = 0.33  (기본 문턱 0.3 → 비슷하다고 잡힘)
```

| 비교 | 유사도 | 결과 |
|---|---|---|
| 콘서트 vs 콘서드 (끝 글자 오타) | 2/6 = 0.33 | 잡힘 |
| 공연 vs 공연을 (조사) | 2/5 = 0.40 | 잡힘 |
| 콘서트 vs 곤서트 (첫 글자 오타) | 1/7 = 0.14 | 못 잡음 |
| 공연 vs 독주회 (뜻만 같음) | 0 | 못 잡음 → 2단계 |

- 위 숫자는 계산 방식을 손으로 따라 한 값이다. **실제 DB에서 확인해야 한다.**
- 긴 본문 안에 단어가 있는지 볼 때는 `word_similarity`(본문 중 가장 비슷한 부분과 비교)를 쓴다.
- 제목·설명 컬럼에 GIN 인덱스(`gin_trgm_ops`)를 건다.
- **주의:** pg_trgm이 한글을 "단어 글자"로 인식하는지는 DB의 문자 설정(locale/ctype)에 달려 있다. 로컬 DB와 RDS에서 각각 확인한다.

### 4.2 도구 입력: 키워드 묶음

```json
{
  "after": "2026-11-02T17:00", "before": "2026-11-02T23:59",
  "keywordGroups": [
    ["공연", "콘서트"],
    ["음악회", "연주회", "독주회"],
    ["연극", "뮤지컬"]
  ]
}
```

- `words` 한 목록 대신 **관점이 다른 묶음 최대 3개**를 받는다. Haiku가 도구를 부를 때 만든다(추가 LLM 호출 없음).
- 묶음마다 따로 순위를 매기는 이유: 한 목록에 다 넣으면 흔한 단어("공연")가 점수를 독차지한다. 묶음을 나누면 "독주회"처럼 덜 흔한 표현으로 쓴 행사도 자기 묶음에서 1등이 될 수 있다.
- **필터가 아니라 순위용이다.** 기간·시각·게시판·자리 같은 확실한 조건만 필터로 남긴다.
- 파티 검색에도 같은 입력을 추가한다(예: `["배드민턴", "민턴", "배드"]`).
- 프롬프트: "질문한 종류를 비슷한 말까지 넓혀 묶음으로 넣어라. 고유한 이름(행사명, 동아리명)은 바꾸지 말라."

### 4.3 RRF: 순위 목록 여러 개를 하나로 합치기

```
최종 점수 = Σ  가중치 / (k + 그 목록에서의 순위)        k = 50 (Onyx와 같음)
```

예시 (가중치 모두 1):

| 행사 | 묶음 A 순위 | 묶음 B 순위 | 묶음 C 순위 | 최종 점수 |
|---|---|---|---|---|
| 가을 재즈 콘서트 | 1 | 3 | — | 1/51 + 1/53 = **0.0385** |
| 피아노 독주회 | — | 1 | — | 0.0196 |
| 뮤지컬 〈렌트〉 | — | — | 1 | 0.0196 |
| 공연 스태프 모집 설명회 | 2 | — | — | 0.0192 |

- 여러 묶음에 나온 것이 위로 오고, 각 묶음의 1등은 다른 목록에 없어도 상위권에 남는다.
- 점수 대신 순위를 쓰므로 묶음마다 점수 범위가 달라도 공평하다.
- 원래 질문 문장으로 만든 목록을 하나 더 넣고 가중치를 낮게(0.5) 줄 수 있다.
- 어느 묶음에도 안 걸린 기간 안 행사는 맨 뒤에 시작 순으로 붙인다(0단계의 "남은 칸 채우기" 유지).
- 구현은 서버 코드의 작은 함수 하나다.

### 4.4 효과, 한계, 시간

- **해결:** 후보가 많을 때의 순위, 오타(첫 글자 제외), 조사, AI가 떠올린 비슷한 말.
- **남는 한계:** AI가 떠올리지 못한 표현, 글자가 전혀 다른 같은 뜻.
- **시간:** 3–5 h (마이그레이션, 검색 서비스 두 곳, 도구 입력·프롬프트, 테스트).
- **시점:** Iteration 4 후보(PM 결정).

## 5. 2단계: 의미 갈래 추가 (pgvector + 임베딩)

**목표:** 글자가 전혀 다른 같은 뜻(공연 ↔ 독주회)과, 수천 건 규모에서도 의미로 가까운 후보를 찾는다. Onyx의 "벡터 + 키워드 하이브리드"에 해당한다.

### 5.1 바꾸는 것

1. **임베딩 저장.** 행사와 Quest에 임베딩 컬럼(`vector(차원)`)을 둔다.
   - 만드는 시점: 행사 발행·수정, Quest 생성·수정 때 제목 + 설명으로 만든다.
   - 기존 데이터는 한 번 채운다(backfill 작업).
2. **임베딩 모델.** OpenRouter에 임베딩 엔드포인트(`POST /api/v1/embeddings`, OpenAI 호환)가 있어서 지금 키 하나로 된다. 문서 예시 모델은 `openai/text-embedding-3-small`, `qwen/qwen3-embedding-0.6b`, `openai/text-embedding-3-large`다. **한국어 성능은 후보끼리 비교해서 고른다.**
3. **검색할 때.** Haiku가 도구 입력에 **의미 검색 문장 1개**를 더 넣는다(예: "이번 주 저녁에 볼 만한 공연"). 서버가 그 문장을 임베딩하고, 코사인 거리순으로 후보를 뽑는다(HNSW 인덱스). 확실한 조건(기간·시각·게시판·자리)은 이 갈래에도 똑같이 건다.
4. **합치기.** 의미 갈래 목록과 1단계의 키워드 묶음 목록들을 RRF로 합친다. 가중치 예: 의미 1.3, 키워드 묶음 1.0, 원래 질문 0.5(Onyx 값 참고, 우리 데이터로 조정).
5. **실패 처리.** 임베딩 호출이 실패하거나 느리면 키워드 갈래만으로 답한다. 새 행사의 임베딩이 아직 없으면 키워드 갈래로만 찾힌다.

### 5.2 인프라와 코드

- **로컬 DB 이미지** (`infra/postgres/Dockerfile`): PostGIS처럼 `pgvector` 패키지를 추가한다.
- **운영 RDS:** RDS는 pgvector를 지원하는 것으로 알려져 있지만 **PostgreSQL 18에서 쓸 수 있는 버전을 확인한다.** 마이그레이션에 `CREATE EXTENSION vector`를 넣는다. 인스턴스가 1 GB짜리 micro라 인덱스 메모리를 지켜본다.
- **Prisma:** 벡터 타입을 직접 지원하지 않으므로 컬럼은 `Unsupported("vector(…)")`로 두고, 검색은 raw SQL(`$queryRaw`)로 쓴다. 바뀌는 곳은 검색 서비스 두 곳과 임베딩 생성 경로뿐이다.
- **비용과 지연:** 임베딩은 생성 시 1번, 검색 시 1번 호출된다. 한 메시지의 지연이 조금 늘어난다(미측정). 30초 제한 안에서 재 본다.
- **데이터 정책:** 행사·파티 본문을 임베딩 공급자로 보낸다. 수집 AI와 같은 정책 확인이 필요하다.

### 5.3 효과, 한계, 시간

- **해결:** 뜻이 같은 다른 단어, 첫 글자 오타 일부(임베딩이 비슷하게 나오면), 수천 건 규모의 넓은 질문.
- **남는 한계:** 임베딩 모델의 한국어 품질에 기대고, 결과가 덜 설명적이다(왜 걸렸는지 보기 어렵다).
- **시간:** 8–12 h (확장·이미지·RDS 확인, 임베딩 생성·채우기, 검색 갈래, RRF 통합, 실패 처리, 테스트).
- **시점:** Iteration 4 이후 후보. 행사가 수천 건이 되거나 넓은 질문이 많아질 때.

## 6. 평가와 테스트

### 6.1 검색과 선택을 나눠서 잰다

- **검색 단계(서버, 결정적):** 조건을 주고 검색 서비스를 직접 불렀을 때 **정답이 후보 안에 있는지**(후보 재현율). 모델 없이 돌므로 CI(`pnpm test`)에 넣는다.
- **선택 단계(Haiku, 비결정적):** 채팅 하네스에서 실제 모델로, 보여 준 카드가 정답 집합과 맞는지. CI 밖에서 R0·R1로 돌린다.
- 둘을 나누면 실패했을 때 "서버가 후보에 안 줬다"와 "AI가 못 골랐다"를 구분할 수 있다.

### 6.2 하위 집합 (자세한 정의는 `iter3-p5 메트릭.md` 평가 D)

| 하위 집합 | 예 | 0단계 | 1단계 | 2단계 |
|---|---|---|---|---|
| 글자 그대로 | "공연" → 제목에 공연 | 통과 | 통과 | 통과 |
| 비슷한 말 | "공연" → 피아노 독주회 | 후보 30개 안이면 통과 | AI가 떠올린 말이면 통과 | 통과 기대 |
| 글쓴이 오타 | 재즈 콘서드 | 후보 30개 안이면 통과 | 통과(첫 글자 오타 제외) | 통과 기대 |
| 후보가 많음 | 같은 날 행사 21개 이상 | 단어 맞는 것은 통과 | 통과 | 통과 |
| 시각 경계 | 17:00 이후 | 통과 | 통과 | 통과 |
| 자리 | 자리 찬 파티 빼기 | 통과 | 통과 | 통과 |

- 단계마다 run을 따로 돌려 하나씩 바꾼 효과를 기록한다(기록 규칙은 메트릭 문서 4절).
- 시험용 세계에 비슷한 말 행사, 오타 글, 같은 날 21개 이상의 행사를 넣는다. 세계는 고정 전에 넣어야 한다.

### 6.3 CI 테스트 예

- 시각 경계(정각 포함), 자리 조건, 거르기가 자르기 앞에서 일어나는지.
- 단어 우선순위: 맞는 것이 앞에 오고, 안 맞는 것도 칸이 남으면 포함되는지.
- (1단계) 오타·조사 예시가 유사도 문턱을 넘는지. 한글 locale에서 trigram이 만들어지는지.
- (1단계) RRF 함수: 여러 목록에 나온 것이 위로 오는지, 각 목록 1등이 남는지.
- (2단계) 임베딩 실패 시 키워드 갈래만으로 결과가 나오는지.
- "조건을 더하면 결과는 부분집합"인지.
