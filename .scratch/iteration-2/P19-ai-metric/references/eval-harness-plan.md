# 평가 하네스 만들기

- 작성: 2026-10-20 (KST)
- 대상: P07 AI chat (SNU Now AI). 기준 `2.0/Main`, 커밋 `ef3101d`
- 상태: 계획. 아직 만들지 않음
- 관련: [ai chat improvement.md](ai-chat-improvement.md). 그 문서의 개선은 전부 "측정해서 좋아질 때만 남긴다"를 전제로 하므로, 이 하네스를 먼저 만든다. spec에서는 "P19 AI metric"으로 미뤄져 있다.

## 한 줄 정의

정해 둔 질문 세트를 **실제 LLM(Haiku)**에 넣어 돌리고, LLM이 **어떤 행동을 했는지 자동으로 채점**해서 점수표를 내는 도구다. 프롬프트나 툴을 고친 뒤 다시 돌려 점수가 올랐는지 내렸는지 본다.

## 지금 테스트로는 왜 안 되나

assistant e2e 테스트는 `ScriptedModel`(`main-server/test/scripted-model.ts`)을 쓴다. "1번째 호출엔 이 툴, 2번째엔 이 텍스트"처럼 **사람이 LLM의 행동을 대본으로 정해 둔다.** 서버 코드(FoundIds, 검사, 응답 모양)가 맞는지는 확인되지만, **진짜 LLM이 그 행동을 고르는지는 확인되지 않는다.** 하네스는 이 대본 자리에 진짜 모델을 넣는다.

기존 e2e는 그대로 둔다. 토큰이 0이므로 CI에서 계속 돌린다.

## 구성 5가지

### 1. 문항 파일

질문과 기대 행동을 적는다(예: `main-server/eval/cases/*.yaml`).

```yaml
- id: propose-closed-ambiguous-friend
  category: 파티 만들기 / 대상 모호
  turns:
    - user: "내일 점심 학생회관에서 민수랑 밥"
      expect:
        action: ASK                         # 되묻기여야 함
        tools_include: [resolveFriend]
        tools_exclude: [proposeQuest]       # 제안하면 오답
        text_mentions: [이민수, 김민수]
    - user: "이민수"
      expect:
        action: PROPOSE
        proposal:
          joinPolicy: closed
          startsAt: "2026-10-22T12:00:00+09:00"
          place: 학생회관
          invitees: [이민수]

- id: refuse-report
  category: 거절
  turns:
    - user: "경제학 리포트 2000자 써줘"
      expect: { action: REFUSE, tools_exclude: ["*"] }

- id: menu-tomorrow-dinner
  category: 메뉴
  turns:
    - user: "내일 저녁 학식 뭐야"
      expect:
        action: TOOL
        tool_args: { getMenus: { date: "2026-10-22", meal: dinner } }
        map_buttons: [dining]
```

한 문항에 정답이 둘 이상일 수 있다. 예를 들어 의도가 모호한 문항은 "TOOL + 되묻는 문구"를 정답으로 받는다(아래 "모호한 질문" 참고).

### 2. 고정된 세계

같은 문항이 늘 같은 정답을 갖도록 **DB 시드와 시계를 고정**한다.
- 친구: 이민수, 김민수, 동명이인 한 쌍
- 장소: 학생회관, 301동
- 그 주의 행사, 모집 중인 파티, 메뉴, 셔틀
- 시계: 예를 들어 "2026-10-21 수요일 14:05 KST". "내일"의 정답이 날마다 바뀌면 채점할 수 없다.

기존 e2e의 `startApp`(`main-server/test/start-app.ts`)과 테스트 DB 컨테이너를 그대로 쓰고, `MODEL_PORT`에만 OpenRouter 모델을 넣는다.

### 3. 실행기

- 문항마다 `POST /assistant/messages`를 앱처럼 호출한다.
- **멀티턴**: 1턴 답장(텍스트, 카드, 제안, 툴 호출 요약)을 대화 기록에 붙여 2턴을 보낸다. 사용자 말만 고정이고, 1턴 답장은 실제 모델이 매번 새로 만든다.
- **툴 실행 흔적**(어떤 툴, 어떤 입력, 어떤 결과)을 함께 받는다. 개선안 2번(툴 로그)의 기록을 재사용한다. 행동 종류는 이 흔적으로 판정한다.
- LLM은 같은 질문에도 답이 달라질 수 있으므로, 변경을 확정할 때는 **문항마다 3번씩** 돌려 일관성도 본다.

### 4. 채점기

대부분 **규칙으로 자동 채점**한다. LLM에게 채점을 맡기면 채점 자체가 흔들린다.

| 판정 | 규칙 |
|---|---|
| TOOL | 조회 툴이 `found`를 돌려줬고, 카드나 지도 버튼이 붙었다 |
| ASK | 제안 없이 끝났고, resolver가 several/none이거나 proposeQuest가 거부했거나, 되묻는 문구가 있다 |
| PROPOSE | 응답에 `proposal`이 있다 |
| REFUSE | 툴 호출이 없고, 거절 문항이다 |
| CHAT | 툴 호출이 없고, 잡담 문항이다 |

추가로 확인하는 항목:
- 툴 인자: 날짜, 게시판, resolver에 넘긴 단어
- 제안 필드
- 지도 버튼
- 텍스트에 꼭 들어가야 할 말: 후보 이름, "없어요", 되묻는 문구
- 과잉 호출(부르지 말아야 할 툴을 부름)과 누락(불러야 할 툴을 안 부름)

"해요체인가", "짧은가"처럼 규칙으로 판정하기 어려운 것만 선택적으로 LLM 채점을 붙인다.

### 5. 점수표

한 번 돌리면 아래 형식의 표가 나온다. **숫자는 형식 예시이고 실제로 잰 값이 아니다.**

```
행동별 재현율   TOOL 92%  ASK 61%  PROPOSE 85%  REFUSE 97%  CHAT 90%
툴 선택 정확도 88%   인자 정확도 79%   과잉 호출 6%   누락 9%
카테고리별      메뉴 95% · 셔틀 90% · 행사 82% · 파티찾기 74% · 파티만들기 68% · 멀티턴 55%
일관성(3회 모두 같은 행동) 81%
평균 step 3.1 · 평균 지연 4.2 s · 총 토큰 in 1.9M / out 80k
실패 문항 목록 → 각 문항의 툴 흔적
```

변경 전과 후의 표를 나란히 놓고, **좋아진 변경만 남긴다.** 가장 중요한 지표는 행동별 재현율이다. Calibration 논문(arXiv 2609.00949)이 보였듯, 결과만 채점하면 행동 종류를 잘못 고른 것이 가려진다.

## 문항 수와 설계

경우의 수를 다 만드는 게 아니라 **유형마다 대표 문항을 몇 개씩** 만든다. 문장만 바꾼 변형은 같은 행동을 테스트하므로 많이 늘릴 필요가 없다.

### 표로 칸 채우기

| | 메뉴 | 셔틀 | 행사 | 파티 찾기 | 파티 만들기 | 잡담·거절 |
|---|---|---|---|---|---|---|
| 명확한 요청 → TOOL/PROPOSE | 3–5 | 3 | 3–5 | 3–5 | 5 | — |
| 슬롯 누락·모호 → ASK | 2 | — | 2 | 2 | 5 | — |
| 의도 모호 | 묶어서 8–10 | | | | | |
| 데이터 없음 → "없어요" | 2 | 2 | 2 | 2 | — | — |
| 거절·잡담 | — | — | — | — | — | 8–10 |
| 멀티턴 후속 | 묶어서 10–15 | | | | | |

- **처음 버전: 60–80개.** 큰 문제는 이 정도로 다 드러난다.
- 이후 운영 로그와 실패 사례로 **150–200개**까지 늘린다.
- 한계: 한 카테고리에 문항이 20개면 문항 하나가 5%p라서 2–3%p 차이는 구분하지 못한다. 그걸 잡으려면 수백 개가 필요한데, 지금 단계에서는 과하다.

### 모호한 질문: "모호함의 종류"별로 5–10개씩

| 종류 | 예 | 기대 행동 |
|---|---|---|
| 의도 모호 | "내일 학관에서 점심" (메뉴? 약속?) | 한쪽(조회)을 보여 주고 다른 쪽을 되묻기. 예: 메뉴를 보여 주고 "약속도 잡을까요?" |
| 대상 모호 | "민수랑 밥" (민수가 둘) | ASK. 후보 이름을 나열 |
| 정보 누락 | "운동 모집해줘" (언제? 몇 명?) | ASK. 빠진 것을 한 번에 묻기 |
| 지시어 | "그거 내일로", "두 번째 거" | 직전 턴의 툴 호출 요약을 써서 처리 |

의도가 모호할 때의 정책은 [ai chat improvement.md](ai-chat-improvement.md) 3-1에서 정했다. 그 규칙이 prompt에 들어간 뒤에 이 문항을 넣는다.

### 문장 변형 늘리기

사람이 씨앗 문항을 쓰고, LLM으로 바꿔 쓰게 한 뒤 사람이 검토한다. 예: "내일 학관 점심", "낼 학생회관서 밥", "내일 점심 학관 어때".

## 비용과 운영

### 토큰은 든다

하네스는 실제 모델을 부르므로 **어디서 돌리든 돈이 든다.** CI에 넣지 않는 이유는 push할 때마다 자동으로 반복 결제되기 때문이다. 필요할 때만 사람이 수동으로 돌린다(예: `pnpm eval`).

### 규모 추정

추정치이고, 실제 값은 점수표의 토큰 수로 확인한다.
- 한 턴: system prompt와 툴 정의를 매 step 다시 보내고 평균 3 step이면, 입력 **1만 토큰 안팎**, 출력 수백 토큰이다.
- 80문항 × 평균 1.5턴 × 3회 = 360턴이면 입력 **약 360만 토큰**, 출력 약 7만 토큰이다.
- 금액은 OpenRouter의 Haiku 단가를 곱해 계산한다. 정확히 하려면 문항 5개만 먼저 돌려서 실제 토큰 수로 계산한다.

### 비용 줄이기

- **prompt caching**: 매번 같은 system prompt와 툴 정의가 반복되니 효과가 크다. 개선안 3-2(현재 시각을 프롬프트 뒤로 옮기기)를 먼저 하면 평가 비용도 같이 줄어든다.
- 평소엔 1회만 돌리고, 변경을 확정할 때만 3회 돌린다.
- 바꾼 부분과 관련된 카테고리만 돌린다.

### 키 분리 (필수)

OpenRouter 크레딧은 **고정 $100**이고 사용자 채팅과 같은 크레딧을 쓴다. 평가를 같은 키로 돌리면 사용자용 크레딧이 줄어든다. **평가용 키를 따로 만들고 사용 한도를 건다.**

### 문항 보충

운영 로그에서 틀린 사례를 발견하면 문항으로 추가한다. 로그에는 사용자 텍스트가 남지 않으므로, 사례는 사람이 다시 써 넣는다.

## 만드는 순서

1. 툴 실행 흔적 기록. 개선안 2번(툴 로그)과 같은 기록을 쓴다
2. 고정 시드와 시계, 실행기. 기존 e2e 인프라를 재사용한다
3. 문항 20개쯤과 규칙 채점기로 한 바퀴 돌려 본다
4. 문항을 카테고리별로 늘리고, 멀티턴과 반복 실행을 추가한다
5. 이전 결과와 비교하는 점수표를 만든다
