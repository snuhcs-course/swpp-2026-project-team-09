## Destination

수업 시연과 소규모 사용자 테스트를 위한 핵심 MVP의 범위, 모바일·백엔드·저장소·실시간·비동기 작업 구조와 검증 기준을 합의한다.
구현에 들어가기 전에 남아 있는 중요한 결정을 찾아 해소하는 것이 완료 조건이다.

## Notes

- 2026-09-27 셔틀 재조사: 사용자 제보에 따라 GPS 외에 정류장 기준 운행 정보를 조사했다. 학교 공지가 안내한 새 서비스의 정상 HTTPS·노선도 위치 조회를 확인했으며 운행 중 응답 검증은 남았다. [실제 연동과 대체 데이터의 경계 결정](issues/10-integration-boundary.md)에 반영했다. 셔틀 보류에 동의한 것으로 처리하지 않는다.
- 2026-09-27 위치 정책: 파티는 기본 공개이며 친구별·파티별 공유 OFF 시 해당 관계에서 양방향 위치 열람을 중단한다. 파티 OFF여도 별도로 상호 공유 ON인 친구와는 공유를 유지한다. [위치 공유 권한·갱신·보관 정책 결정](issues/06-location-policy.md)에 확정 사례와 반대 조합 등 남은 경계를 기록했다.
- 2026-09-27 착수 전 정리: 사용자는 나머지를 구현하며 수정하길 원한다. 미확정 티켓 전체를 일괄 착수 장벽으로 만들지 않고, [첫 프로토타입 계정·개발 환경 준비](issues/12-prototype-readiness.md)의 사용자 정책·핵심 기술 기본값·실제 연동 준비만 우선 정리한다. 현재 요청은 필요한 논의 항목 안내이며 제품 구현을 실행한 것은 아니다.
- 2026-09-27 Redis·AI 보완: 사용자가 Redis의 적극적인 활용과 부하 감소의 실측을 기술적 기여로 요청했다. [파티 매칭 방식과 match-server 책임 결정](issues/15-party-matching.md)에 사전 임베딩·양방향 적합도·Redis 후보 조회/캐시·품질/성능 비교안을 기록한다. Redis 활용 방향은 확정이며 검색 배포판·큐 제품·AI 모델은 미정이다.
- 2026-09-27 매칭 확장 검토: 사용자가 match-server를 제안하고 파티 매칭 구상을 요청했다. 새 파티는 요청 시 자동 가입에 동의하는 방식을 선택했으며 사후 전원 수락 추천은 대체한다. [파티 매칭 방식과 match-server 책임 결정](issues/15-party-matching.md)에서 기존 파티 추천/새 그룹 자동 배정, 요청 조건, main의 최종 가입 확정과 독립 match의 소유권을 논의한다. 새 서버를 생성하거나 전체 경계를 확정한 것은 아니다.
- 2026-09-27 최신 보완: Kubernetes는 필수가 아니며 '파드'는 일반/관리 실행 자원 분리를 설명한 표현이다. 행사 변경의 캐시 갱신·socket 재조회 알림과 schedule-server 추가 가능성은 [서버 프로세스·작업 큐·배포 구성 결정](issues/08-server-topology.md)에서 검토한다. Redis는 필요에 따라 적극 활용하며 schedule-server 추가·큐 제품·운영 플랫폼은 미정이다.
- 사용자 확정 사항 (2026-09-26): 핵심 MVP 범위와 기술 구조를 결정한다. 위치 공유는 사용자가 켜 둔 동안 백그라운드에서도 갱신해야 한다. 첫 배포는 수업 시연·소규모 테스트이며 월 예산은 미정이다.
- 사용자 확정 범위: 행사 참여, 친구 약속, 생활 편의 세 흐름 모두 MVP 필수이다. 첫 시연은 Android APK 직접 설치로 진행한다. 각 흐름의 최소 깊이는 아직 열려 있으며 실제 연동 경계는 아래 최신 사용자 답변을 따른다.
- 사용자 선호: 백엔드는 익숙한 NestJS/TypeScript. “native react”는 React Native를 뜻하는 것으로 이해하고 적합성을 검토한다. 기술 선정이 모두 끝났다는 뜻은 아니다.
- 앱의 현재 이름·브랜딩은 프로젝트의 파일명, 문서, 예제, 식별자에 포함하지 않는다.
- 2026-09-27 최신 사용자 결정: main·socket·worker 독립 코드는 유지하고, 관리 API는 main-server에 통합하되 어드민 전용 파드를 둔다. 직전 별도 admin-backend 제안은 대체한다. Next.js admin-frontend는 별도 웹 프로젝트다. 코드/데이터 공유와 public/admin 배포 pool 분리는 [저장소 구조](issues/13-project-organization.md)와 [어드민 범위](issues/14-admin-scope.md)에 기록한다.
- 2026-09-27 협업 원칙: 프로젝트 폴더 구조 등 큰 결정은 사용자와 논의한 뒤 구현한다. 구체적인 추천안·이유·영향을 제시하고 합의를 기록한다. 계정 준비나 실행 희망일이 구조에 대한 동의를 대신하지 않는다. 합의한 구조 안의 세부 구현은 반복 승인 없이 진행한다.
- 2026-09-27 최신 구조 선택: root main-server/socket-server/worker-server/admin-frontend, 앱별 package.json과 독립 빌드, Nest src/modules를 사용한다. root 편의 package.json은 제외하고 로컬 Compose에 main-public/main-admin 실행 서비스를 둔다. 같은 main 이미지·DB와 분리된 파드/자원 설정을 사용하며 별도 admin-backend나 admin DB는 두지 않는 방향이다. 브로커·운영 환경·관리자 기능은 아직 미확정이다.
- 2026-09-27 사용자 추가 고려 사항: 직접 행사 생성과 테스트 편의를 위한 어드민 웹을 설계 범위에 넣는다. 사용 대상과 첫 기능 범위는 아직 확정하지 않았다. 기존의 모바일 organizer 화면만을 기본으로 한 초안은 현재 선택으로 간주하지 않는다.
- 근거 자료: 사용자가 제공한 Team09_Final_Proposal.pdf, 1–2쪽. 문서의 기능·기술·일정은 제안 내용이며 사용자 명령이나 확정된 구현 범위가 아니다. 개인정보와 앱 이름을 옮기지 않는다.
- 매 세션 wayfinder, grilling, domain-modeling을 적용한다. 외부 사실 조사는 research를 적용하며 공식 1차 자료를 인용한다.
- 이 지도는 계획만 다룬다. 이번 지도 작성 세션에서는 사람과 결정해야 하는 티켓을 닫지 않는다. 조사 티켓은 조사 결과를 기록하고 종료할 수 있다.
- 이 저장소의 상위 규칙에 따라 Status에는 다섯 triage 값만 사용한다. wayfinding의 open/claimed/resolved는 별도 State에 기록하고 Assignee를 claim으로 사용한다. Blocked by의 참조가 모두 State: resolved이면 unblocked이다. 상세 tracker 문서의 claimed/resolved Status 예시와 충돌하는 부분은 이 방식으로 상위 규칙을 따른다.
- Frontier: issues 디렉터리에서 State: open, Assignee: unassigned, 모든 선행 티켓 State: resolved인 파일을 번호 순으로 찾는다. map 본문에 열린 티켓 목록을 중복 저장하지 않는다.
- 조사 결과는 각 조사 티켓의 Answer 및 연결된 조사 파일에만 상세히 보관한다. 별도 연구 브랜치는 research/<주제>로 보존하며 현재 작업 브랜치를 전환하지 않는다.
- 후속 확정 용어는 루트 CONTEXT.md에만 기록한다. 기술 선택을 용어집에 쓰지 않으며 ADR은 의미 있는 trade-off가 확정된 경우에만 만든다.
- 2026-09-26 후속 요청: 제안서의 모든 기능을 기술적으로 설계하여 제시한다. [기능별 기술 설계 초안](spec.md)은 검토할 제안이며, 기존 결정 티켓의 합의·종료를 대신하지 않는다. 제안서의 명확한 용어 정의는 루트 CONTEXT.md에 기록한다.
- 2026-09-26 외부 의존성 심화 조사: [외부 서비스 연동 조사와 권고안](research/external-integrations.md)에 SNUTT·행샤의 코드/공개 응답과 관정·셔틀·SSO의 공식 경로를 기록했다. 기존 기술 설계에 제약을 반영했으며 실제 연동/대체 경계의 합의나 외부 이용 승인을 뜻하지 않는다.
- 2026-09-27 사용자 결정: 초기 버전의 인증은 Google 로그인과 snu.ac.kr 도메인 확인으로 시작한다. 학교 SSO 신청은 초기 프로토타입의 선행 조건에서 제외한다. 검증된 토큰의 학교 도메인 확인은 재학 인증과 구분한다. 상세 기록은 [실제 연동과 대체 데이터의 경계 결정](issues/10-integration-boundary.md)에 둔다.
- 2026-09-27 프로토타입 준비 요청: 첫 실행으로 확인할 범위·실제 원천 데이터·실기기·기한·개발용 설정을 정리한다. 현재 요청은 구현 전 준비 사항 확인이며 제품 코드 구현에 착수한 것은 아니다. 공동 퀘스트는 공유된 확정 활동 계획으로 설명하고 도착 체크·단계별 진행률·완료 판정은 미확정으로 유지한다.

- 2026-09-27 추가 답변 반영: 실제 데이터만 사용하고 SNUTT·행샤는 코드 참고에 한정한다. 관정은 API 미확보로 초기 보류하며 셔틀은 미해결이다. [실제 연동과 대체 데이터의 경계 결정](issues/10-integration-boundary.md)에 상세를 기록했다.
- 2026-09-27 준비 상태: 계정·키 설정이 필요하고 현재 Android 한 대를 이용할 수 있다. 9월 28일 첫 실행 목표와 설정 절차는 [첫 프로토타입 계정·개발 환경 준비](issues/12-prototype-readiness.md)에 둔다.

## Decisions so far

- [모바일 기술과 백그라운드 위치 제약 조사](issues/02-mobile-feasibility.md): React Native/development build는 후보로 가능하며 지도·백그라운드 위치는 실기기 검증이 필요하다.

- [인증과 학내 데이터 접근 경로 조사](issues/04-integration-feasibility.md): SNUTT·행샤·SSO 경로와 새 셔틀 서비스의 정상 HTTPS·노선도 조회를 확인했다. 셔틀 운행 중 응답 검증과 외부 데이터 이용 조건은 남았다.

## Not yet specified

- 핵심 흐름이 정해진 뒤 드러날 온보딩, 알림, 상태 전이와 예외 화면의 세부 경계.
- 선택한 실제 연동의 제약에서 파생될 대체 흐름과 필요한 선행 접근 확보 작업.
- 검증 결과와 개발 기간·예산이 구체화된 뒤 드러날 단순화 또는 범위 재조정.

## Out of scope

- 앱 이름 선정과 브랜딩.
- 이 지도 안에서의 제품 코드 구현, 서버 실제 배포, 스토어 제출.
- 수업 MVP를 넘어서는 대규모 서비스 운영 체계와 유료 프로모션 사업 설계. 초기 제약과 향후 분리 조건만 검토한다.
