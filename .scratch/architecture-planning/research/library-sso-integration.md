# 관정 도서관과 서울대학교 SSO 연동 조사

조사일: 2026-09-26 (Asia/Seoul). 공식 공개 자료와 실제 공개 웹 화면을 확인했다. 학교 계정으로 로그인하거나 예약·취소·신청·문의 발송은 하지 않았다. 앱 이름은 기록하지 않았다. **기술 설계 제안과 외부 제공자가 확정한 기능을 구분한다.**

## 핵심 판단

- **학교 SSO는 공식 연동 신청 경로가 있다.** 다만 학생 개발자가 키를 즉시 발급받는 공개 OAuth 서비스로 확인된 것은 아니다. 기관 단위 협의, 운영 책임 주체, 학교 IP·도메인 등 조건이 제시되어 있으므로 담당 교수와 적절한 기관의 지원을 받아 신청 가능성을 먼저 확인해야 한다. **무료 단순인증과 개인정보 조회를 포함한 통합인증을 구분해 문의**하는 것이 이번 프로젝트에 특히 유용하다. [정보화본부 통합인증 안내](https://ist.snu.ac.kr/%ED%86%B5%ED%95%A9%EC%9D%B8%EC%A6%9D-sso/)
- **관정 시설의 사용자용 예약 경로와 이용 규칙은 확인했다.** 열람실 좌석과 그룹스터디룸은 정책이 다르다. 반면 외부 앱에 제공되는 잔여좌석·시간대 조회 API, 사용자 위임 예약·취소 API, SDK, 이용 허가 절차는 공개 자료에서 확인하지 못했다. API가 없다는 결론은 아니다. 도서관 시스템 담당자와 시설 담당자에게 읽기와 쓰기를 나누어 문의해야 한다. [시설 현황](https://lib.snu.ac.kr/using/places-carrel/places/), [서비스별 연락처](https://lib.snu.ac.kr/about/staff-inquiry/services/se-central/)
- **SSO 승인은 도서관 예약 API 사용 승인과 별개다.** 학교에서 본인을 인증하는 것과 특정 시설을 대신 예약할 권한은 다른 계약이다. 아래 예약 어댑터는 도서관이 해당 권한과 방식을 제공한 경우에만 활성화한다.

## 1. 관정 도서관: 어떤 예약인지 먼저 분리

아래는 오래된 블로그가 아니라 조사 당일 도서관 공식 시설 화면에서 중앙도서관을 선택해 확인한 내용이다. 웹 검색 도구는 동적으로 삽입되는 시설 행을 누락하여 실제 브라우저 화면도 읽었다.

| 대상 | 확인한 규칙 | 설계 영향 |
|---|---|---|
| 관정 7A·7B·8A·8B 열람실 | 개인 학습 공간. 현장 배정 또는 예약, 최대 6시간 및 연장. 8B는 대학원생 제한. 예약 후 30분 안에 키오스크에서 배정받지 않거나 좌석을 반납하지 않으면 제재 대상이며 5회 누적 시 10일 좌석 배정 제한 안내 | `reserved`와 `allocated`를 분리한다. 예약만으로 입실·좌석 배정 완료 처리하면 안 된다. 시설별 이용 자격을 확인한다. |
| 관정 2·4층 그룹스터디룸 | 서울대 재학생 대상. 3일 전부터 예약, 최대 3시간. G431은 별도 예약 없이 선착순 | 개인 좌석과 별도 자원 유형·시간대 모델이 필요하다. 인원, 구성원 확인, 동반자 정보와 현장 확인 요건은 추가 문의한다. |
| 공통 | 공식 페이지가 매일 02:30–04:00 S카드 점검에 따른 좌석 예약 불가를 고지 | 예약 버튼과 오류 안내에 운영 중단 상태를 반영하고 이 구간을 단순 장애 재시도로 처리하지 않는다. |

출처: [공식 시설 현황 및 이용 규칙](https://lib.snu.ac.kr/using/places-carrel/places/). 운영시간·시설 정책은 변경될 수 있으므로 코드 상수보다 제공자 설정으로 관리한다. 열람실 화면의 제재 문구 일부에는 ‘좌석반납’으로 표기된 부분이 있으나 바로 아래 상세 설명은 미반납을 제재 대상으로 설명한다.

공식 화면에서 관정 열람실과 그룹스터디룸의 **예약** 버튼은 모두 [관정 시설 예약 진입 페이지](https://k-rsv.snu.ac.kr/NEW_SNU_BOOKING/LibLogin1.jsp)를 가리킨다. 본관 열람실은 [본관 예약 진입 페이지](https://k-rsv.snu.ac.kr/NEW_SNU_BOOKING/LibLogin2.jsp)를 사용한다. 이는 **사용자용 웹 진입 URL**이며 API나 외부 앱에 대한 자동 호출 허가를 뜻하지 않는다. 예약 진입 후의 로그인·예약 기능은 실행하지 않았다.

### 현재 공식 모바일 경로

2023년 4월 이후 공식 앱은 ‘서울대학교 모바일 중앙도서관’이며 이전 ID카드·좌석 예약 앱은 종료됐다. 현재 구성원·동문회원은 SNU 로그인 후 SMS·이메일·모바일 인증을 통한 이중 인증을 사용한다. 도서관 출입 QR은 마이스누 S카드 QR과 다르며 계정·이용증 공유 금지가 안내된다. **새 앱이 학교 비밀번호·OTP를 받아 도서관에 대신 로그인하거나 이용증 QR을 복제하는 설계는 채택하지 않는다.** 도서관이 지원하는 위임 인증 또는 공식 서비스 이동을 사용한다. [도서관 모바일 앱 안내](https://lib.snu.ac.kr/about/mobile/mobile-pass/)

GPS·Bluetooth·Wi-Fi를 통한 현장 인증의 필수 여부, 모바일에서 키오스크 배정을 완전히 대체할 수 있는지, 그룹스터디룸의 현장 확인 방식은 이번 공개 문서로 확정하지 못했다. 해당 기능이 있다고 가정하거나 우회하는 구현을 계획하지 않는다.

### 조회·예약을 구현하는 세 단계

아래는 연구자의 권장 구현 순서다. 학교가 이미 제공하는 API 명세가 아니다.

1. **시설 안내와 공식 예약 이동:** `FacilityCatalog`에 시설 ID, 종류, 위치, 인원, 이용 자격, 운영시간, 공식 URL, 출처·확인시각을 저장한다. 사용자가 원하는 조건과 이동시간으로 시설을 추천하고 공식 예약 화면을 연다. 앱 복귀만으로 성공 판정하지 않는다. 이후 사용자가 예약했다고 표시하면 `user_reported`로 구분한다. 승인 API의 확정 상태와 혼합하지 않는다.
2. **허가받은 실시간 조회:** 도서관이 승인한 read-only 인터페이스가 확보되면 NestJS `LibraryAvailabilityProvider`가 좌석 집계 또는 방별 예약 가능 시간대를 조회한다. 여러 앱의 요청을 서버에서 합치고 제공자 한도에 맞게 캐시한다. `observedAt`, `expiresAt`, `available/unknown/stale`, `source`를 반환한다. 오래된 좌석 수를 0 또는 현재 잔여 수로 표시하지 않는다. 개별 이용자·누가 어느 자리에 있는지는 수집할 필요가 없다.
3. **사용자가 위임한 예약·취소:** 도서관이 지원하는 사용자별 권한과 API가 있을 때만 `LibraryBookingProvider`를 켠다. `requested → confirmed/failed/unknown`과 실제 열람실의 `allocated → returned/expired` 상태를 분리한다. 사용자 최종 확인 후 예약을 요청하고 외부 예약 ID를 받아야 confirmed가 된다. Timeout은 unknown으로 두고 상태를 조회하여 중복 예약 여부를 해결한다. 무조건 POST를 재시도하지 않는다. 현장 배정이 필요하면 남은 시간과 공식 배정 방법을 안내한다.

우리 앱 내부의 예약 요청 ID나 트랜잭션만으로 외부 예약의 exactly-once 처리를 보장할 수 없다. 제공자의 idempotency key 지원, 내 예약 조회, 취소 및 중복 요청 의미가 확정되어야 한다. AI는 후보 조회·설명·예약 의도 정리와 기존 서비스 호출을 담당하며, 자격 판정과 외부 성공 여부를 지어내지 않는다.

### 공개 API를 찾을 때 혼동하지 않을 것

도서관 관련 공개 API가 전혀 없는 것은 아니다. 공식 LikeSNU에 [도서 추천 API 목록](https://likesnu.snu.ac.kr/usr/cmn/api/bookApiList.do)이 있으며 인기 도서, 컬렉션, 학과별 대출, 도서 상세 등의 조회가 나열된다. **도서의 예약 인기 순위 API는 관정 좌석·공간 예약 API가 아니다.** 해당 목록을 근거로 좌석 예약을 구현할 수 있다고 판단하지 않았다.

## 2. SSO: 신청 가능성과 기술 방식

### 확인된 공식 조건과 절차

공식 한국어 SSO 안내의 조건은 다음과 같다. 검색 수집기의 본문이 비어 실제 브라우저에서 페이지를 열어 확인했다.

- 정보보안 지침 준수, 데이터를 책임질 운영 주체, 학교 IP와 `*.snu.ac.kr` 사용.
- 지원 우선 대상은 기관 단위이며 교육기구 항목은 학부/과 단위 이하를 제외한다. 기타 기관은 정보화본부장과 별도 협의한다. **학생 팀에 자동으로 허용되거나 담당 교수 개인 승인만으로 충분하다는 근거는 없다.**
- 담당자 사전 협의 후 마이스누 → 스누인지원 → IT서비스 → 행정서비스 신청 → 통합인증연동신청에서 신청하고 전자결재 공문으로 요청한다.
- **통합인증:** 보안서약서와 개인정보 보유부서의 사용승인 전자문서. WAS별 라이선스 비용은 별도 문의.
- **단순인증:** 기본 신청 경로와 보안서약서는 동일. 라이선스 비용은 무료로 안내. 반환 필드와 현재 구현 방식은 공개 페이지에 명세되어 있지 않다.

출처: [정보화본부 통합인증 서비스](https://ist.snu.ac.kr/%ED%86%B5%ED%95%A9%EC%9D%B8%EC%A6%9D-sso/), [영문 안내](https://ist.snu.ac.kr/en/single-sign-onsso/). 안내는 조사 당일 공개된 내용이며 최신 적용 조건·비용·서식을 담당자가 확정해야 한다. 한국어 페이지의 관련규정 링크가 호스팅 운영지침 PDF를 가리키는 등 링크 정합성 문제가 있어, 그 링크를 SSO 규정 본문으로 인용하지 않았다.

공식 안내의 신청 버튼이 가리키는 [통합인증연동신청 페이지](https://nitsm.snu.ac.kr/xefc/jsp/ui/main.jsp?uri=/xefc/jsp/ui/form/form.jsp&ent_id=SRM&tas_id=TAS00337&frm_id=FRM002989&auth=1&act=1&title=%ED%86%B5%ED%95%A9%EC%9D%B8%EC%A6%9D%EC%97%B0%EB%8F%99%EC%8B%A0%EC%B2%AD)도 확인했다. 버튼의 목적지만 읽었으며 양식 접근·제출이나 로그인은 하지 않았다. 초기 정보화본부 상담에서 현재 포털 경로와 신청 권한을 안내받는 것이 적절하다.

### 기술적으로 알려진 것과 모르는 것

- [학교 공식 Pass-Ni 예제](https://my.snu.ac.kr/passni/sample/main.jsp)에 agent 도메인·ID, 통합로그인 및 로그인 정책 조회 예제가 있다. 기관별 연동 구성이 있다는 근거다. **현재 외부 서비스에 OIDC/OAuth2/SAML이 제공된다는 근거는 아니다.** agent 등록 값이나 다른 기관의 설정을 재사용하지 않는다.
- 2024년 SSO 보안 강화 공지는 ID/PW 뒤 추가 인증, 모바일 인증, 패스키를 안내한다. 따라서 ID/PW만 사용하는 오래된 비공식 클라이언트를 현재 지원 방식으로 취급하면 안 된다. [학교 공식 보안 강화 공지](https://nursing.snu.ac.kr/board/notice?bbsidx=155529&bm=v)
- SNU ID에는 학생 외 동문·교직원·일반인 등의 그룹도 있다. **학교 로그인 성공 자체가 현재 재학 확인은 아니다.** 단순인증에서 반환하는 신분 정보, 재학·휴학·졸업 전환 시 갱신과 재검증 가능 여부를 문의해야 한다. [학교 계정 관리 안내](https://nsso.snu.ac.kr/sso/usr/self/personRegist)
- 학교 메일 소유 확인이나 Google Workspace 로그인을 도입해도 그것은 별도 인증 수단이다. SSO 연동 승인, 학적정보 제공 승인, 도서관 예약 권한으로 간주하지 않는다. 학교는 별도로 Google 및 다른 메일 시스템을 제공한다. [학교 정보화서비스](https://snu.ac.kr/campuslife/aid/it)

### NestJS·React Native 적용 제안

SSO 승인 및 실제 프로토콜 확인 후 다음 경계를 구현한다.

```text
React Native 로그인 요청
→ 외부 시스템 브라우저에서 학교가 승인한 인증 흐름
→ 학교가 승인한 서버 callback / agent
→ NestJS에서 인증 결과의 진위·대상·만료·요청 연계 검증
→ 앱에 일회용 복귀 코드
→ 코드 교환 후 우리 앱 세션 발급
```

이 흐름은 **제안**이다. 학교가 지원하는 모바일 callback, 스킴/App Link, 서버 간 교환 및 인증 자료 형식을 먼저 확인한다. 학교가 agent 설치를 요구하고 Node.js를 지원하지 않는다면 지원 런타임의 작은 인증 브리지로 분리하고 NestJS는 검증된 결과만 받게 할 수 있다. 실제 agent 라이선스와 런타임은 아직 미확인이다.

**호스팅 계획에도 직접 영향을 준다.** 임의의 외부 클라우드 서버에 학교 도메인만 연결하면 학교 IP 조건까지 충족되는 것으로 간주하면 안 된다. 학교 내 승인된 인증 gateway만 두고 외부 NestJS 서버에 검증 결과를 전달하는 구조를 허용하는지, 외부 클라우드 예외가 있는지 먼저 문의한다. 이 분리 구조도 학교가 승인한 경우에만 채택할 수 있다.

`ExternalIdentity(provider, subject, verifiedAt)`로 외부 식별자를 앱 사용자와 연결하고, `StudentStatus(status, source, checkedAt)`는 별도로 둔다. 실제로 제공받지 못한 학번·학과·재학 상태를 가상의 claim으로 구현하지 않는다. 학교 비밀번호와 OTP는 우리 서버로 보내지 않는다. SSO의 장기 access token을 전제로 백그라운드 도서관 예약까지 가능한 것으로 설계하지 않는다.

## 권장 다음 순서

1. SSO는 **무료 단순인증을 포함한 기관 자격·호스팅 요건 상담**부터 진행한다. 단순인증으로 재학 확인까지 가능한지는 따로 확인한다.
2. 도서관은 **개인정보 없는 읽기 API**와 **위임 예약**을 분리한 문의를 보낸다. 예약 연동 승인 지연 때문에 시설 안내·경로 추천까지 막히지 않게 한다.
3. 회신 후 `official_api`, `official_link`, `manual_or_demo` 중 각 기능의 실제 지원 수준을 결정한다. 승인 전에는 실제 예약 완료를 시연한다고 약속하지 않는다.
4. 세 흐름 모두 필수라는 기존 사용자 요구는 유지한다. 공식 링크 이동만으로 도서관 기능의 완료를 인정할지는 MVP 결정에서 사용자가 판단한다.

## 2026-09-27 추가 조사: 첫 Android 프로토타입의 실제 관정 데이터

사용자는 2026-09-28 첫 프로토타입에 샘플 데이터 사용을 허용하지 않았으며, 관정 API를 확보하지 못하면 해당 기능을 후속 MVP로 미루는 것을 허용했다. 초기 인증은 학교 도메인의 Google 로그인으로 계획하고 SSO는 초기 범위에서 제외한다. **공식 예약 페이지 이동을 관정 기능의 대체 완료로 채택한 것은 아니다.**

### 추가로 직접 확인한 결과

1. [공식 시설 안내](https://lib.snu.ac.kr/using/places-carrel/places/)의 공개 HTML을 비로그인 GET으로 읽었다. 이 페이지는 선택한 도서관과 시설 유형에 따라 `GET /using/facility/?libcode=...&type=...`를 호출해 시설 안내 HTML을 삽입한다. 공개 선택지에서 확인한 중앙도서관 코드 `01`과 열람실 유형 `F001`로 [해당 시설 목록](https://lib.snu.ac.kr/using/facility/?libcode=01&type=F001)을 한 번 조회했고 HTTP 200 응답을 확인했다. **응답은 본관·관정 열람실의 위치, 운영시간, 이용 규칙, 예약 링크다. 잔여좌석 수·현재 점유율·좌석별 실시간 상태를 제공하는 응답은 아니다.** ‘전체 3’은 반환된 시설 안내 행 수이며 잔여좌석 수가 아니다.
2. [공식 관정 예약 진입](https://k-rsv.snu.ac.kr/NEW_SNU_BOOKING/LibLogin1.jsp)을 쿠키·계정 없이 GET 요청하면 `SSOweb.jsp`로 이동한다. 받은 페이지는 비로그인 상태에서 SSO 인증을 시작하도록 작성되어 있으며, 좌석 현황 수치를 포함하지 않았다. **HTTP 200은 로그인 진입 HTML을 받았다는 뜻이지 좌석 API가 사용 가능하다는 뜻이 아니다.** 로그인 함수·폼 제출과 그 이후 인증된 화면/API는 실행하거나 조사하지 않았다.
3. 공식 도서관 홈페이지와 시설 안내에 공개된 링크를 확인한 범위에서, 비로그인 상태의 관정 잔여좌석 현황이나 외부 개발자용 예약·취소 API 명세는 확보하지 못했다. 공식 앱 또는 로그인 뒤에 조회 인터페이스가 존재할 가능성은 남지만, 그것이 외부 앱 사용을 허용한 API인지도 미확인이다. 임의의 경로 추측·인증 우회·비공개 API 탐색은 하지 않았다.

### 초기 범위에 대한 결론

- **확보:** 실제 공식 시설 안내 HTML 및 사용자용 SSO 예약 진입 경로.
- **미확보:** 관정의 실시간 잔여좌석/방별 가용시간 read-only API, 우리 앱의 사용자에게 위임받아 예약·조회·취소할 공식 API, 해당 이용 허가·인증 계약.
- **현재 막힌 지점:** 시설 안내에서 연결되는 예약 서비스가 인증을 요구하며, 외부 프로젝트의 데이터 조회·예약 권한을 제공하는 공개 명세를 확인하지 못했다. 학교 도메인 Google 로그인만으로 해당 SSO 세션이나 예약 권한을 얻을 수 있다고 가정하지 않는다.
- **권장 결정:** 사용자가 허용한 대로 **관정 실시간 조회·예약을 첫 프로토타입에서 보류하고 후속 MVP의 외부 연동 조건으로 유지**한다. 기능을 샘플로 채우거나 공식 페이지 이동으로 완료 처리하지 않는다. ‘API가 없다’는 결론이 아니라 ‘초기 구현에 사용할 API를 현재 확보하지 못했다’는 판단이다.
- **재개 조건:** 도서관 학술정보시스템 담당자가 지원하는 조회/예약 인터페이스와 이용 범위, 테스트 인증, 호출 한도·배포 조건을 제공하고 실제 읽기 응답을 검증할 수 있을 때 재개한다. 학교의 제공·승인 여부와 응답 시점을 우리가 확약할 수 없으므로 내일 또는 특정 기한까지 확보한다고 약속하지 않는다.

이 추가 조사는 공개 페이지의 소수 GET 및 공개 HTML 읽기로만 수행했다. 문의 발송·신청·로그인·예약·취소는 하지 않았다. 기존 문의 창구인 `libit@snu.ac.kr` 및 시설 정책 담당자 정보는 위 절을 따른다.
