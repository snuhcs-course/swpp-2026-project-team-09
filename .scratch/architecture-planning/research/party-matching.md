# 파티 매칭과 match-server 경계 조사

조사일: 2026-09-27. 기존 spec 7.4–7.6의 열린 파티 추천·신규 그룹 제안을 독립 서비스로 분리할 때의 검토안이다. Open Match는 개념 참고이며 도입이나 Kubernetes 사용을 제안하지 않는다.

**조사 후 사용자 결정:** 새 파티는 “매칭 요청 시 자동 가입까지 동의”하는 방식을 선택했다. 아래 사후 제안 수락 관련 권고는 이전 비교안이며 현재 정책을 뜻하지 않는다. 현재 설계는 요청의 조건/revision별 동의를 영속 기록하고, 유효한 범위 안에서 자동 확정하며, 기존 파티 가입 정책은 별도다. 서비스 신설·인원·가중치는 아직 미확정이다. 최신 계약은 [파티 매칭 방식과 match-server 책임 결정](../issues/15-party-matching.md)에 둔다.

## 권고 경계

| 담당 | 소유·책임 제안 |
| --- | --- |
| main-server | 계정·공개 프로필·행사·파티·회원·차단 원본, 최종 파티 생성/가입, 정원·자격 재검증 |
| match-server | 매칭 요청, 후보 점수, 그룹 제안과 revision별 수락, 만료·취소·재시도, 추천 피드백 |
| socket-server | 권한 있는 당사자에게 제안/진행/결과 변경 알림; 매칭 판정·회원 생성은 하지 않음 |
| worker-server | 수집·포스터 추출 등 일반 작업; 매칭 요청 생명주기의 원본은 소유하지 않음 |

별도 NestJS 서비스는 매칭 계산·정책 배포·실패를 main에서 격리할 수 있지만, 소규모에서는 추가 통신과 상태 복구 비용이 더 크다. 독립 match-server를 선택한다면 main의 DB를 직접 읽거나 쓰지 않고 서비스 인증된 후보 일괄 조회 API를 우선 사용한다. 이 방법은 매칭 계산을 분리하지만 후보 추출의 main/DB 부하는 남는다. 이후 필요할 때만 허용된 행사·열린 파티·매칭용 요약을 이벤트로 복제한 조회 모델을 둔다. 이 복제본은 원본보다 늦을 수 있어 최종 검증을 대체하지 않는다. 이 경계는 이 프로젝트를 위한 설계 제안이다.

## 두 가지 사용자 경로

1. **기존 열린 파티 추천:** 사용자가 행사/활동과 가능한 시간을 선택 → 참여 가능한 열린 파티 필터 → 점수 정렬 → 사용자가 가입 선택 → main에서 최신 정원·차단·자격을 검사하여 가입한다. 추천만으로 자리가 예약되지는 않는다.
2. **새 그룹 구성:** 동행 찾기를 켠 사용자만 요청을 생성 → 요청 후보를 묶어 그룹 제안 → 제안 revision에 대한 수락 → main이 최종 파티를 생성한다. 다른 사용자가 매칭을 요청했다는 이유만으로 가입시키거나 위치를 공개하지 않는다. 전원 수락을 초기 권고로 제시하되, 최소 인원 도달 시 확정·자동 가입 여부는 제품 결정으로 남긴다.

Open Match의 Match Function도 요청(ticket) 풀을 조회한 뒤 요구 조건에 맞는 그룹 제안을 만든다. 동시에 만든 제안에 같은 요청이 중복 포함될 수 있어 후보 생성과 겹침 제거를 구분한다. 이는 기존 파티 조회와 새 그룹 구성의 처리 경로를 나눌 근거가 된다. [Match Function](https://open-match.dev/site/docs/guides/matchmaker/matchfunction/), [Evaluator and Synchronizer](https://open-match.dev/site/docs/guides/evaluator/)

## 후보 계산 제안

- 입력: 대상 행사/활동, 원하는 날짜·시간 범위, 인원 선호, 관심 태그, 명시적 필수 조건, 요청 만료 시각. 원본 개인 시간표 대신 허용된 가용 시간 구간·최소 프로필만 사용한다. 현재 GPS 공유는 매칭의 필수 입력이 아니다.
- 필수 조건: 현재 매칭 참여 의사, 행사 자격·취소 여부, 활동 전체를 포함하는 공통 가용 시간, 인원 상한, 모든 구성원 쌍의 차단 관계. 요청자가 입력한 조건도 필수와 선호를 구분한다.
- 점수 후보: 공통 관심, 명시적 활동 선호 충족, 시간 여유, 대기 시간. 학과·입학 연도 다양성은 사용자가 선택한 선호일 때만 반영하고 가중치는 아직 정하지 않는다.
- 신규 그룹은 오래 기다린 요청을 기준으로 후보를 추가하는 greedy 방식으로 시작할 수 있다. 매 추가마다 **그룹 전체의 가용 시간 교집합**과 모든 쌍의 차단을 재계산한다. 기준 사용자와 각각 시간이 맞는다는 사실만으로 그룹 시간이 맞지는 않는다. 활동 길이와 필요한 이동 시간을 포함한다.
- LLM은 자연어 조건을 사용자가 확인할 구조로 바꾸거나, 서버가 검증한 추천 이유를 표현하는 역할이 적절하다. 시간 겹침·정원·가입 판정은 결정적 코드로 계산한다. 벡터 검색·학습 모델은 품질 평가 후 검토한다.
- 유효 후보가 없으면 결과 없음과 조건 조정 선택지를 표시한다. 더 오래 기다렸다는 이유로 필수 조건을 자동 완화하지 않는다.

위 알고리즘과 점수 항목은 우리 요구에 대한 설계 제안이며 Open Match가 학교 동행 매칭 품질을 보장한다는 뜻이 아니다.

## 중복 확정과 장애 처리

후보 상태 예시는 `searching → proposed → finalizing → matched`이며 거절·만료·취소 분기도 둔다. 수락은 제안 revision에 묶고 구성원·시간이 바뀌면 이전 수락을 그대로 재사용하지 않는다. 제안 생성 때 매칭 DB의 요청을 잠그거나 조건부 변경하여 동일 요청이 동시에 여러 활성 제안에 배정되는 것을 막는다. 여러 프로세스가 실행될 때도 DB 제약을 최종 방어선으로 쓴다.

**match DB의 행 잠금은 main DB의 파티 생성까지 원자적으로 묶지 않는다.** PostgreSQL 행 잠금은 해당 트랜잭션 안에서 동시 변경을 조정하며, 유일 제약은 같은 테이블의 중복 값을 거부한다. 따라서 두 서비스에 각각 필요한 불변식을 설계해야 한다. [행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html), [유일 제약](https://www.postgresql.org/docs/current/ddl-constraints.html)

main의 내부 최종 생성 API는 다음을 한 트랜잭션으로 처리하는 안이다.

1. `proposalId`와 불변 요청 내용의 해시로 재시도를 식별한다. 같은 ID·같은 내용이면 기존 결과를 돌려주고 같은 ID·다른 내용은 거부한다.
2. 포함된 각 `matchRequestId`의 소비 기록을 유일하게 저장한다. proposalId만 검사하면 서로 다른 제안이 같은 요청을 중복 소비하는 경우를 막지 못한다.
3. 최신 행사·자격·차단과 동의된 시간 관련 상태를 확인하고, 파티·회원·처리 결과·outbox를 함께 저장한다. 기존 파티 가입은 해당 파티를 잠그고 정원과 중복 회원을 다시 검사한다. 확정 일정까지 만들기로 선택한 흐름이라면 기존 일정 잠금 규칙도 함께 따른다.

main에서 생성은 성공했지만 응답이 유실될 수 있다. 따라서 `finalizing`의 HTTP 타임아웃을 곧바로 실패로 간주하여 요청을 풀고 새 제안을 만들면 안 된다. 같은 proposalId로 결과를 조회하거나 재시도하여 성공 여부를 조정한다. 취소·재매칭 전에 main에도 확정 취소/세대 번호를 반영하여 늦게 도착한 이전 최종 생성 요청을 거부하는 절차가 필요하다. 이미 생성이 완료됐다면 별도의 탈퇴/취소 정책으로 처리한다. AWS의 멱등 API 자료도 타임아웃 후 결과가 불명확한 경우와 늦은 재시도를 별도로 다룬다. [멱등 API와 안전한 재시도](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

제안·최종 생성의 상태 변경과 알림 기록은 각 소유 서비스에서 outbox로 저장하고, 알림 소비자는 변경 ID로 중복을 제거한다. 앱은 소켓 힌트를 받아 현재 상태를 다시 조회하며 재연결 때도 복구한다. outbox가 중복 전송 자체를 없애지는 않는다. [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 사용자와 정할 항목

- 독립 match-server를 최초 구성에 넣을지, 동일 경계를 main 내부에서 먼저 검증할지.
- 기존 파티 추천과 새 그룹 구성의 화면 우선순위, 자동 합류 허용 여부.
- 최소/최대 인원, 수락 유효시간, 일부 거절 시 재제안, 매칭 중 취소 정책.
- 확정 파티 가입이 곧 일정·퀘스트 확정을 의미하는지, 계획 합의 단계를 따로 둘지.
- 한 사용자의 복수 요청과 시간 충돌 제한, 대기 시간과 적합도 사이 우선순위.

운영 검증은 추천 수락률·유효 후보 없음 비율·대기 시간 외에 동시 수락, 중복 메시지, 요청 취소 중 최종 생성, main 성공 후 응답 유실, 앱 재연결에 집중한다. 확인되지 않은 부하 수치나 매칭 성공률은 약속하지 않는다.
