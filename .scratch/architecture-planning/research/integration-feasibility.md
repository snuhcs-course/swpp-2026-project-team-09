# 인증과 학내 데이터 접근 경로 조사

조사일: 2026-09-26. 공식 공개 문서의 확인 결과이며, 계정·API 키를 발급하거나 인증·예약을 실행하지 않았다. 공개 페이지의 존재는 외부 앱의 자동 수집·재배포 권한이나 API 계약을 의미하지 않는다. 아래 대안은 의사결정 후보이며 아직 확정된 MVP 명세가 아니다.

후속 조사: 같은 날 사용자가 지정한 SNUTT·행샤와 관정·셔틀·SSO를 더 깊게 조사했다. **SNUTT 선택창, 행샤 공개 조회 API, 셔틀 DWR 구현, SSO 공식 신청 절차를 추가 확인했다.** 이 항목의 최신 근거와 권고는 [외부 서비스 연동 종합 조사](external-integrations.md)를 우선한다. 이 문서의 식단·지도 관련 결과는 계속 참고한다.

## 결론

세 흐름을 모두 MVP에 포함하는 것은 외부 연동을 모두 실서비스 수준으로 완성하는 것과 구분해야 한다. 가장 큰 불확실성은 학생 프로젝트의 학교 SSO 승인, 도서관 실제 좌석·예약 API, 셔틀의 지원 데이터 계약이다. SSO의 기관 대상 신청 절차는 후속 조사에서 확인했으며, 학생 팀 자격·현재 프로토콜은 아직 미확인이다. 도서관의 외부 조회·예약 API는 공개 자료에서 확인하지 못했으며 API가 없다는 뜻은 아니다.

행사·식단의 원문 링크와 표기된 시연 데이터, 사용자가 입력하는 일정, 자체 앱 내 파티·약속·위치 공유로 세 흐름을 구성할 수 있다. 실제 도서관 예약은 공식 서비스로 연결하는 선택지가 있다. 다만 이것을 사용자가 요구한 생활 편의 흐름의 완료로 인정할지는 후속 HITL 결정이 필요하다.

## 확인 결과와 남은 조건

|---|---|---|
| 학교 SSO | SNU 통합계정이 학교 주요 서비스의 인증 수단이다. 계정 운영지침에는 포털 서비스 구축의 사전협의와 시스템 연동 요청 절차가 있다. [정보화서비스](https://snu.ac.kr/campuslife/aid/it), [계정·포털 운영지침](https://nsso.snu.ac.kr/sso/usr/self/personRegist) | 학생 프로젝트가 사용할 OIDC/SAML 클라이언트 등록, 제공 claim, 승인 기간은 미확인. 제안서의 SSO를 즉시 사용 가능한 인증으로 가정하지 않는다. |
| 학교 관리 Google 로그인 | 학교 메일은 구성원 그룹별로 Google 또는 Dooray를 사용한다. Google ID 토큰은 서명·aud·iss·exp 검증 후 조직 도메인 hd를 검사할 수 있고, 사용자 식별에는 sub를 쓴다. 이메일 끝부분만 검사해서는 관리 도메인 소속을 증명하지 못한다. [학교 메일 안내](https://snu.ac.kr/campuslife/aid/it), [Google 토큰 검증](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) | 학교 계정의 실제 hd, 대상 학생의 계정 사용 가능 여부, 프로젝트 OAuth 허용은 테스트 전이다. 관리자는 외부 앱 접근을 통제할 수 있다. Google 로그인이 현재 재학 여부·학교 SSO 연동·학사정보 열람 권한까지 보장하지 않는다. 학교 정책 확인 전 시연 계정 대안을 둔다. [Workspace 앱 접근 통제](https://support.google.com/a/answer/7281227?hl=en) |
| 공지·행사 | 컴퓨터공학부 공식 홈페이지에 날짜·분류가 있는 공지와 세미나 경로가 공개되어 있다. [컴퓨터공학부](https://cse.snu.ac.kr/ko) | 범학과 통합 API, 자동 수집·저장·재배포 허가, 행사 필드 품질은 미확인. 우선 한 학과·한 행사 유형부터 데이터 형태를 확인하고, 시연용 자체 행사와 원문 링크를 사용할 수 있다. |
| 학식 | 생협 공식 식단에 식당별 아침·점심·저녁과 휴무 안내 등이 게시된다. [생협 식단](https://snuco.snu.ac.kr/foodmenu/) | 문서화된 외부 API·수집 허가·갱신 SLA는 미확인. 허가된 입력/수집 경로 확보 전 원문 보기와 명시적 시연 데이터가 후보. 원문 확인시각과 식단 적용 날짜가 필요하다. |

## 지도 표시와 도보 소요시간은 별도 기능

현재 카카오 공식 REST 문서에는 `GET /v2/routing/walk`가 있으며 REST API 키를 요구하고, 별도 Requirements는 `-`로 표시되어 있다. 응답은 도보 거리·소요시간·경로 좌표·카카오맵 연결 URL을 포함한다. 따라서 과거 자료를 근거로 “카카오는 도보 API가 없다”거나 “모든 도보 API가 제휴 전용이다”라고 단정하면 안 된다. [카카오맵 REST API: 도보 경로](https://developers.kakao.com/docs/en/kakaomap/rest-api)

반면 **카카오모빌리티의 별도 제휴용 도보 API**는 계정·앱 정보 전달 후 승인을 안내한다. 두 제품의 접근 경로를 혼동하지 않는다. [제휴용 도보 API 시작하기](https://developers.kakaomobility.com/affiliate/walking/start)

지도 SDK 선택과 도보 경로 데이터 공급자를 별도로 검증해야 한다. 앱 등록·키 발급·현재 쿼터/과금, 실제 교내 계단·지름길 경로 품질은 아직 검증하지 않았다. 키로 교내 대표 출발지/목적지 몇 쌍의 결과를 확인한 뒤 채택하는 것이 다음 조사다. 실패 시 공식 카카오맵 길찾기 URL로 연결할 수 있다. 단, 외부 길찾기 열기만으로 앱 내부의 도보 ETA 기반 약속 추천 계산이 해결되지는 않는다. [지도 Web API 링크 가이드](https://apis.map.kakao.com/web/guide/)

## 구조에 미치는 영향 — 연구자의 제안

- 외부 제공자마다 읽기 인터페이스와 출처·관측시각·신선도·실데이터/샘플 구분을 둔다. 어느 연동 하나가 지연되어도 세 흐름을 검증할 수 있게 한다.
- 공지·식단의 주기적 갱신과 셔틀/좌석의 빠른 갱신은 서로 다른 주기와 오류 정책이 필요하다. 이 차이는 작업 종류를 나누는 이유이지 곧바로 여러 서버를 설치할 이유는 아니다.
- 친구 약속의 가용시간은 초기에는 자체 입력으로 구성 가능하다. Google 로그인만으로 Calendar 접근을 얻지 못하며, 캘린더 데이터 접근에는 별도 OAuth scope와 사용자 동의가 필요하다. [Google OAuth 안내](https://developers.google.com/identity/protocols/oauth2)
- 다음 결정에서 실제 연동이 반드시 필요한 항목과 공식 링크/샘플 허용 항목을 기능별로 정한다. 세 흐름 모두 필수라는 사용자의 답변을 기능 삭제로 바꾸지 않는다.
