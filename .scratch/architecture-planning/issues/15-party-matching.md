## Question

열린 파티 추천과 새 파티 구성을 어떻게 수행하고, match-server를 독립 배포할 경우 main의 파티 원본·가입 확정과 매칭 요청·배정의 책임을 어디에서 나눌 것인가? 후보 조건·점수·요청 시 자동 가입 동의·동시성·AI 역할을 검토한다.

## 기존 초안과 분리 제안

기존 초안은 main 내부에서 열린 파티 추천과 새 그룹 구성을 계산하는 안이었다. 사용자 요청에 따라 **독립 NestJS match-server를 두는 안을 추천 후보로 구체화**한다. 매칭 정책·대기 요청·제안 상태와 계산 부하에 독자적인 책임이 있으므로 캐시 무효화만 맡는 추가 서버보다 분리 경계가 명확하다. 다만 한 번 더 네트워크를 거치며 파티 확정을 두 저장소에 걸쳐 복구해야 하는 비용이 생긴다. 작은 첫 시연에는 main 내부 모듈로도 충분하므로 성능상 필수라고 주장하지 않는다.

제품 코드·새 애플리케이션 폴더는 생성하지 않는다. 추가 서비스와 아래 소유권은 제안 상태이며, 사용자가 가입 정책을 선택했다고 서비스 구조 전체를 승인한 것으로 해석하지 않는다.

사용자 확정(2026-09-27): **새 파티는 매칭 요청 시 자동 가입까지 동의한다.** 구성원별 사후 수락 단계를 권했던 이전 제안은 대체한다. 사용자가 확인한 요청 조건 범위에서만 자동 가입하며 조건을 벗어난 배정은 새 동의가 필요하다. 기존 열린 파티에 대한 자동 가입까지 확장한 답변은 아니다.

추가 사용자 방향: Redis를 필요에 따라 적극 활용하고 부하 감소를 기술적 성과로 제시한다. match-server의 AI가 자연어 해석을 넘어 실제 매칭 품질에 기여하도록 아래 의미 검색·양방향 점수 설계를 제안한다. Redis 활용 방향은 합의되었으나 모델·Search 배포판·큐 제품·최종 가중치는 아직 선택 전이다.

## 두 가지 사용자 흐름

### 열린 파티 추천

1. 선택 행사/활동, 가용 시간, 희망 인원·관심 조건으로 요청한다. 행사별 공개 파티와 활동별 파티를 구분한다.
2. 공개/발견 가능 여부, 실제 모집 중 상태, 정원, 행사 참여 자격, 기존 구성원 모두와의 차단 관계, 시간·이동 가능성을 검사한다.
3. 통과 후보에 관심 태그·명시한 동행 선호·시간 여유·사용자가 제공한 출발지 기준 이동 부담을 점수화해 상위 후보와 이유를 제시한다. 점수와 가중치는 평가 후 조정할 후보이며 숫자를 확정하지 않는다.
4. 추천은 좌석 예약이 아니다. 사용자가 가입할 때 main이 현재 상태와 정원을 다시 검증한다. 기존 파티의 자유 가입/파티장 승인 정책은 아직 미확정이며 새 파티의 요청 시 자동 가입 동의와 구분한다.

### 참여 희망자로 새 파티 구성

1. 매칭을 직접 신청한 사람만 대기 목록에 넣는다. 행사/활동·가용 시간·희망 그룹 크기·필수/선호 조건·요청 만료를 저장한다. 앱 접속 여부나 관심 태그만으로 등록하지 않는다.
2. 같은 행사/활동·호환 시간대 후보를 추린 뒤 오래 기다린 요청부터 출발점으로 삼아 후보를 추가한다. 매번 **그룹 전체 시간 교집합, 활동 길이, 모든 사용자 쌍의 차단 관계, 각자의 허용 인원 조건**을 다시 검사한다. 시작 요청과 각 후보가 각각 잘 맞아도 그룹 전체가 유효하다는 뜻은 아니다.
3. 초기에는 필터+가중 점수+greedy 묶기를 사용한다. 전역 최적화를 보장하는 알고리즘은 아니며 후보 수·계산 시간 상한을 둔다. 오래된 요청 우선과 거절 이력으로 굶주림·같은 조합 재제안을 줄이되, 매칭 불가능한 요청 때문에 다른 요청까지 막지 않는다.
4. 예: A 14–16시, B 14시30분–16시30분, C 15–17시면 공통 15–16시를 제안할 수 있다. 반면 고정 행사 15–17시 참석에는 1시간 교집합만으로 충분하지 않다. 행사 전체와 필요한 이동 시간을 충족해야 한다. 예시의 그룹 크기·시각은 실제 데이터나 확정 정책이 아니다.
5. 사용자 선택에 따라 요청 시 활동·시간 범위·인원 조건과 자동 가입 동의를 확인한다. 조건에 맞는 그룹을 찾으면 서버 내부 후보를 검증해 파티를 자동 생성/가입시키고 확정된 구성원·활동·장소·시간을 알려 준다. 사후 전원 수락 화면은 두지 않는다. 최신 사용자 결정에 따라 파티 위치 공유는 기본 ON으로 안내하되 OS 권한·전체/관계별 설정을 존중한다. 한쪽이 해당 파티 공유를 끄면 그 관계에서 양방향 열람이 중단된다. 후보 계산 단계의 위치 공개나 개인 시간표 공개를 허용한 것은 아니다. [위치 정책](06-location-policy.md)
6. 확정 전 취소·만료·요청 조건 변경이 있으면 해당 요청 revision을 제외하고 다시 계산한다. 요청 범위 안의 후보 변경에는 매번 추가 동의를 요구하지 않지만, 범위를 벗어난 활동·시간·인원 배정은 허용하지 않는다. 조건을 넓히려면 새로운 요청/동의를 받는다. 대기 유지 여부·최소/최대 인원·만료 시간은 제품 결정으로 남긴다.
7. 후보가 없으면 요청을 대기시키고 사용자에게 조건 변경을 제안한다. 필수 조건을 몰래 완화하거나 가짜 사용자를 채우지 않는다. 첫 테스트에 두 기기만 있으면 두 실제 참여자 시나리오로 검증하고, 다인원 알고리즘 테스트 픽스처를 실제 사용자 매칭으로 제시하지 않는다.

## 서버·데이터 소유권 제안

| 실행 서비스 | 책임과 원본 |
| --- | --- |
| main-server | 계정·행사·시간표/가용 시간 원본·차단/권한·파티·가입 정보, 파티 생성/가입 최종 판정 |
| match-server 후보 | match_requests와 조건/revision별 자동 가입 동의, 내부 배정 후보, 요청 점유·최종 확정 진행 상태, 후보 점수·정책 버전·매칭 피드백 |
| socket-server | 인증된 대상에게 matching.searching/matched/cancelled 등 상태 변경을 알려 재조회 유도 |
| worker-server | 수집·이미지 추출·일반 비동기 작업. match 도메인 계산을 worker와 중복 소유하지 않음 |

- 초기 전체 적재·cache miss·복구에는 main의 인증된 배치 API로 필요한 후보 요약을 가져온다. 사용자/파티마다 N+1 조회하지 않고 main DB에 직접 SQL을 보내지 않는다. 관심 태그·허용된 가용 구간·공개 파티 요약을 사용하며 원본 시간표나 숨긴 GPS를 가져오지 않는다.
- 부하 감소를 위한 최신 제안은 매칭 참여 중인 요청에 필요한 행사/모집 상태/허용된 프로필 요약을 match 소유 Redis 조회 모델로 유지하고 관련 변경 이벤트로 갱신하는 것이다. main API를 모든 점수 계산 때 반복 호출하지 않는다. 변경 기록의 버전·소비 진행 위치와 주기적 복구를 갖추며 DB보다 뒤처질 수 있으므로 사용자 노출 전 필요한 권한 확인 및 최종 확정 시 main 재검증이 필요하다. 요약 삭제/수정 전파와 장애 후 재구축 비용도 측정한다. 전체 학생 데이터를 복제하지 않는다.
- 계정/행사/파티 원본과 match 저장소는 논리 DB/schema·role·migration 소유권을 분리하는 안이다. 물리 PostgreSQL 인스턴스 공유는 가능하지만 교차 DB 직접 쓰기·교차 서비스 FK로 결합하지 않는다. Redis는 후보 인덱스/캐시 후보이며 요청 동의와 확정 원본을 휘발성 저장소에만 두지 않는다.
- 새로운 요청, 취소, 관련 조건 변경 때 해당 매칭 후보군 계산을 깨우고 짧게 요청을 합친다. 전체 DB를 모든 클라이언트 요청마다 전수 비교하지 않는다. 작업 중복을 허용하되 결과 적용은 버전 검사로 제한하고, 누락 복구용 점검을 둔다. 정확한 큐 제품·합치는 시간은 미정이다.
- match-server 채택 시 root에 자체 package.json·lockfile·Dockerfile·src/modules를 둔다. 독립 컨테이너로 실행할 수 있으며 Kubernetes·물리 서버 추가가 필수는 아니다.

## 요청 동의와 자동 확정의 경계

요청 상태 예시: `searching → finalizing → matched`, 또는 확정 전 `expired/cancelled`. 내부 배정 후보의 최종 검증 실패는 조건이 유효한 요청을 다시 searching으로 돌릴 수 있다. 자동 가입 동의는 requestId+requestRevision+조건에 묶고, proposalId는 내부 배정 시도 ID일 뿐 사용자 수락 화면을 뜻하지 않는다. 이름·상태의 상세 스키마는 구현 전 확정한다.

- 한 match 요청은 동시에 한 활성 제안에서만 점유하도록 match DB에서 잠금/조건부 갱신·유일 제약을 사용한다. 여러 matcher 인스턴스가 계산한 후보가 겹치면 실제 제안 저장 단계에서 하나만 성공한다.
- 그룹 후보 확정 시 각 요청의 자동 가입 동의·revision·조건 충족·만료·취소·점유 상태를 match DB transaction으로 검사하고 finalizing 상태와 파티 생성 명령 outbox를 함께 저장한다. 네트워크 호출을 기다리면서 DB 잠금을 계속 잡지 않는다.
- main은 인증된 생성 명령의 proposalId, revision, requestIds, 동의한 구성을 받아 최신 행사 상태·참여 자격·차단·일정·인원 등 확정 조건을 검사한다. 관련 변경과 경합하는 조건은 main의 일관된 잠금/버전 정책으로 직렬화한다. 한 transaction에서 파티/가입, 생성 결과, 소비된 match_request ID와 결과 outbox를 기록한다.
- main에서 proposalId는 멱등 키다. 같은 ID에 다른 구성은 거절하고, 재시도에는 동일 partyId/결과를 돌려준다. **소비된 requestId도 unique**로 제한하여 동일 요청이 서로 다른 proposalId로 중복 확정되는 것을 막는다. 서로 다른 요청으로 복수 파티에 참여할 수 있는지, 같은 시간대 요청을 제한할지는 별도 정책이다.
- match DB의 행 잠금은 main DB transaction까지 원자화하지 않는다. main 응답이 끊기면 finalizing을 실패로 단정해 점유를 풀지 않는다. proposalId로 생성 결과를 조회하거나 같은 멱등 명령을 재시도하여 결과를 확정한 뒤 confirmed/rejected와 요청 점유를 갱신한다. [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html), [Unique constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)
- finalizing 중 사용자 취소와 main 확정이 경합하는 경우도 같은 명령 상태/버전으로 다뤄야 한다. 취소 성공을 먼저 표시하고 뒤늦은 생성 명령을 허용하지 않는다. 결과가 불명확하면 취소 확인 중으로 표시하고, 이미 확정된 경우에는 파티 탈퇴 절차를 따른다. 정확한 취소 우선순위와 보상 처리 계약은 미확정이다.
- main의 확정 결과를 match가 영속 반영한 뒤 socket으로 대상자에게 알린다. socket 중복/누락은 최신 상태 조회로 복구한다. 사용자는 파티 생성 응답을 받은 후에만 합류가 완료된 것으로 본다.

## AI 역할과 검증

기존의 자연어 해석·설명 중심 안을 **조건 추출 → 구조 필터/의미 후보 검색 → 양방향 점수 → 그룹 구성 → 원본 재검증/자동 확정**으로 확장하는 설계 제안이다. 후보 생성·점수·재정렬을 분리하는 일반 추천 구조를 적용하되 아래 학교 동행 점수의 품질은 직접 검증해야 한다. [Google 추천 구조](https://developers.google.com/machine-learning/recommendation/overview/types)

### 요청 해석과 입력 확정

LLM이 자유문을 activity/eventId 참조, timeWindows, partySize, hardConstraints, softPreferences의 허용 schema로 해석한다. 스키마 검증과 실제 ID/시간/조건 검증을 따로 수행하고, 자동 가입 요청 직전에 사용자가 정리된 조건을 확인하도록 한다. 날짜 기준·시간대가 없는 상대 날짜, 원문에 없는 인원·동행 성향은 임의 확정하지 않는다. 구조화된 폼 입력만으로도 매칭을 시작할 수 있다.

### 변경 때 계산하는 임베딩

- 명시적으로 제공한 관심사·활동 방식 소개를 profile vector `p_i`, 현재 요청의 원하는 동행 조건을 preference vector `q_i`로 표현한다. 같은 의미 공간의 모델과 권장 입력 형식을 사용하고 modelVersion·차원·정규화 정책을 고정한다. '관심사가 비슷함'과 '요청한 동행 조건에 적합함'을 구분하기 위한 두 입력이며 별도 학습된 two-tower 모델이 이미 있다는 의미는 아니다.
- 프로필/요청이 바뀔 때만 생성하고 contentHash+modelVersion+입력 포맷 버전으로 결과를 재사용한다. 요청마다 모든 후보를 다시 임베딩하지 않는다. 일반 worker에 계산을 위임하더라도 match가 입력/피처 버전과 결과 적용을 소유하고 오래된 작업 결과를 거절한다. 모델을 바꿀 때 기존 벡터와 새 벡터를 섞지 않고 인덱스 세대를 바꾼다.
- 'LLM 활용'과 '생성형 AI 서비스 제작'처럼 표면 태그가 다른 선호의 의미를 가까운 후보로 검색할 수 있는지를 한국어 평가셋에서 확인한다. 임베딩 유사도는 텍스트 유사도 신호이며 사람의 실제 궁합이나 만족 확률이 아니다. [임베딩 유사도](https://sbert.net/docs/sentence_transformer/usage/semantic_textual_similarity.html)

### 필터와 의미 후보 검색

- Redis의 행사/활동·날짜·상태 인덱스로 후보군을 좁히고 벡터 검색을 결합한다. 시간 bucket은 후보 추출의 근사 조건일 뿐 실제 전체 시간 교집합·이동 시간·차단·동의는 정확히 검사한다. 모든 학생 간 N×N 계산이나 LLM 전체 사용자 프롬프트를 사용하지 않는다.
- 초기 작은 후보군은 Redis Set/ZSet+제한된 exact cosine 또는 Redis Search FLAT을 비교한다. 큰 후보군에서만 HNSW를 성능/검색 정확도 실험 후보로 둔다. Redis vector Search는 해당 기능을 지원하는 배포판/버전이어야 하며, metadata filter와 KNN의 실제 실행 순서는 optimizer에 달렸으므로 항상 물리적 prefilter라고 단정하지 않는다. [Redis vector search](https://redis.io/docs/latest/develop/ai/search-and-query/vectors/)
- 후보 수 K는 시험 설정이다. 의미 top-K만 쓰면 오래 기다린 요청·입력 부족 사용자를 놓칠 수 있으므로 태그/활동 기반 후보와 대기 우선 후보도 합쳐 평가한다. 필요한 인원이 안 나오면 허용 조건 안에서 K를 늘리거나 다른 후보 생성기를 사용하고 필수 조건을 완화하지 않는다.

### 양방향 점수와 그룹 구성

점수 예시(제안): `c(i,j) = min(s(q_i,p_j), s(q_j,p_i))`, 여기서 s는 같은 모델의 cosine 등을 일관된 범위로 정규화한 값이다. i가 원하는 동행에 j가 맞는 정도와 반대 방향을 함께 본다. 한쪽 점수만 높은 배정을 줄이는 보수적 기준이며 평균/가중 평균과 비교할 휴리스틱이다. 상보적 역할·다양성 선호는 단순 유사도만으로 해결되지 않아 명시적 feature와 평가가 필요하다.

유효 그룹의 점수 후보는 `α·평균 c + β·최저 c + γ·대기 보정 - δ·이동 부담`이다. 변수는 정규화하고 가중치는 아직 정하지 않는다. 그룹 전체의 시간·인원·모든 쌍 차단·각 요청 조건은 점수와 무관한 필수 제약이다. 초기 greedy를 비교 기준으로 두고, 계산 상한을 둔 beam search 또는 작은 구성원 교환이 그룹 적합도를 개선하는지 실험할 수 있다. 어떤 알고리즘도 전역 최적이나 실제 친화도를 보장했다고 주장하지 않는다.

### 상위 후보만 재정렬하는 심화 실험

더 정교한 텍스트 비교가 필요하면 검색된 소수 후보만 cross-encoder/소형 reranker로 재점수화한다. 두 입력을 함께 읽는 모델은 후보별 추론 비용이 있으므로 전체 대기자에 호출하지 않는다. 문서 검색용 pretrained 모델의 점수가 동행 적합도라는 가정은 하지 않고 한국어·양방향 조건 사례로 검증한다. 학습용 사용자 피드백이 부족한 초기에는 새로운 개인화 모델을 학습한다고 주장하지 않는다. [Retrieve & Re-rank](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

초기 핵심 제안은 구조화+사전 임베딩+규칙/양방향 점수다. reranker와 beam search는 품질 향상이 지연/비용을 정당화할 때 추가한다. LLM 설명은 공개 가능한 확정 feature/이유 코드에만 근거하며 원문에 없는 성격·성향을 만들어내지 않는다. 단순 템플릿으로 대체 가능하고, 설명 생성을 파티 확정의 필수 성공 조건으로 두지 않는다. AI 실패 시 필수 조건을 유지하는 태그/규칙 fallback을 제공한다.

NestJS match는 요청·피처 버전·점수 조합·상태를 관리한다. 임베딩/재정렬 실행은 provider API 또는 worker에 위임하는 후보로 비교하고, 무거운 모델 추론을 HTTP event loop에서 직접 실행하지 않는다. 특정 모델·차원·한국어 성능·가격이나 별도 Python AI 서버 도입은 아직 결정하지 않았다.

## Redis 활용과 부하 감소 제안

| 대상 | 구조/키 후보 | 줄이려는 비용 |
| --- | --- | --- |
| 공개 행사·열린 파티 요약 | version 있는 Hash/JSON·TTL | 반복 DB 조회와 직렬화 |
| 참여 중인 매칭 요청 | 행사/활동 Set, 시간/대기순 ZSet, 최소 feature Hash | 전체 테이블 scan·매칭마다 main API 호출 |
| 임베딩 | contentHash+modelVersion; 검색 기능 지원 시 vector index | 같은 텍스트의 반복 모델 호출·후보 비교량 |
| 이미 계산한 쌍 점수 | 양측 request/profile revision+model/policyVersion+TTL | 동일 후보 쌍 재추론/재계산 |
| 동시 같은 입력 처리 | 소유자 토큰을 갖는 짧은 lease/요청 합치기 | cache miss 폭주와 중복 AI 호출 |
| 요청 제한·최신 위치 등 | 용도별 별도 namespace/TTL | 과도한 요청·고빈도 영속 쓰기; 위치는 공개 제어 경계 유지 |

- 캐시는 절약할 비용이 충분한 항목에만 적용한다. 값싼 cosine 연산보다 Redis 왕복이 비싸면 배치 조회한 벡터로 match 메모리에서 계산하고, 쌍 점수 캐시는 비싼 재정렬/재사용이 확인된 항목에 한정한다. 후보 인덱스 자체가 누락되면 결과가 비므로 cache miss와 후보 없음은 구분해 rebuild/batch fallback한다.
- 취소·프로필/가용 시간·행사 변경은 버전이 있는 이벤트로 인덱스/캐시를 갱신한다. 늦은 임베딩·점수 결과가 새로운 revision을 덮지 못하게 한다. 캐시 TTL만으로 정합성을 보장하지 않으며 최종 확정은 main/match DB의 조건·중복 제약을 유지한다. 갱신과 조회가 경합하는 실패 시험을 포함한다.
- 자연어 해석 결과를 캐시한다면 요청자/접근 범위·기준 날짜/시간대·프로필/문맥 revision·prompt/schema/modelVersion·정확한 입력 hash를 키에 포함한다. 비슷한 문장이라는 이유로 다른 사용자의 시간/권한/가입 동의를 재사용하지 않는다. 민감 원문을 key나 로그에 그대로 쓰지 않는다.
- SET NX 같은 lease는 중복 계산을 줄이는 장치다. 만료 뒤 이전 처리기가 살아날 수 있으므로 토큰 검증·version fencing을 적용하고 실제 중복 가입 방지는 DB가 맡는다. 단일 lease로 exactly-once 파티 생성을 보장하지 않는다.
- 캐시/벡터 인덱스와 큐의 메모리·복구 정책은 다르다. BullMQ/Streams를 채택하면 유실되면 안 되는 작업용 Redis와 eviction 가능한 캐시 Redis의 별도 인스턴스 구성을 검토한다. DB 번호나 key prefix만 나누어 eviction 정책이 분리되지는 않는다. 브로커 제품 교체를 여기서 확정하지 않는다.
- Redis 장애 시 무제한 DB fallback을 허용하지 않는다. 동시성 제한·대기·회로 차단과 원본의 제한된 batch 조회로 부하를 제어한다. 장애 상태에서 강제로 매칭을 확정하지 않으며 저장된 요청은 복구 뒤 처리한다. [Redis·큐·측정 조사](../research/matching-ai-redis.md)

## 발표용 성능·품질 검증 설계

같은 입력·필수 제약·하드웨어·도착률로 아래 비교를 수행한다. 첫 실사용 데이터가 작으면 생성한 부하 시험 데이터는 별도 환경에서 사용하고 실제 가입자/외부 서비스 데이터로 제시하지 않는다. 아직 벤치마크는 수행하지 않았으며 향상률을 미리 적지 않는다.

| 실험 | 비교 목적 |
| --- | --- |
| A: DB/태그·규칙, Redis 조회 모델 없음 | 재현 가능한 기준 |
| B: A + 사전 임베딩/양방향 점수 | AI 피처의 품질·추론 비용 효과 |
| C: B + Redis 조회 모델/캐시/합치기 | 알고리즘을 고정한 상태에서 부하 감소 측정 |
| D: C + 상위 후보 reranker 또는 탐색 개선 | 각 추가 기능을 따로 켜 품질·비용 효과 검증 |

- 부하: 요청당 SQL 수/읽은 행·DB CPU/연결 수, main 호출 수, 각 서비스 CPU·메모리, Redis command 수/latency/메모리/eviction, hit rate, AI 호출/토큰/요금. DB 비용이 Redis나 모델 추론으로 이동한 양까지 함께 보고한다.
- 지연: 조건 해석, 후보 검색, 점수 계산, 그룹 구성, 최종 DB 확정의 p50/p95/p99와 큐 대기를 분리한다. 실제 동행이 들어오기를 기다리는 시간은 계산 지연과 별도다. warm/cold cache·행사 변경 burst·취소·Redis/AI 장애에서도 측정한다.
- 품질: 사용자 의도 추출 정확도, 필수 조건 위반, 블라인드 평가한 후보 적합도/NDCG@K, 그룹 최저 적합도, 매칭 가능 요청 중 성사율/대기 시간, 사용자 만족도. ANN Recall@K는 exact vector 검색 대비 근사 검색 손실이지 사용자 만족도 지표가 아니다.
- 자동 가입 정책에서 '가입 완료' 자체를 선호나 수락의 증거로 학습하지 않는다. 명시적 만족/불만 피드백을 우선하고 조기 탈퇴·재매칭은 상황에 영향을 받는 보조 신호로 다룬다. 평가용 요청/사용자와 학습·튜닝 데이터를 나눠 결과 누출을 막는다.

합의 후 검증: hard constraint 위반률, 유효 그룹의 공통 시간, 중복 matcher 경쟁, 자동 확정 중 요청 취소/만료/조건 변경, main 생성 후 응답 유실, 재전달·서로 다른 proposal의 동일 request 소비, 파티 정원 경합, 후보 없음/오래 기다리는 요청, 동의 범위 밖 배정 차단, 재연결 후 결과 복구. 이번에는 문서 설계만 수행한다.
