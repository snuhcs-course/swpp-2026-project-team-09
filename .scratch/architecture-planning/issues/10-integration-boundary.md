## Question

사용자는 샘플을 거절하고 실제 원천 데이터 연결을 요구했다. 인증, 행사·학식·장소, 이동시간, 도서관, 셔틀의 실제 접근 경로와 첫 구현 완료 수준을 정한다. 데이터 제공자 접근이 확보되지 않은 기능의 완료 조건과 대체 흐름은 무엇인가? API 키/승인 확보가 먼저 필요한 경우 별도 선행 task를 만든다.

## Comments

2026-09-27 사용자 결정: “초기 버전은 google 로그인으로 하고 snu.ac.kr을 확인하는 정도”. 초기 인증은 Google ID token의 서버 검증과 학교 도메인 확인으로 구현하고 학교 SSO를 선행 조건에서 제외한다. Google Workspace 여부는 hd로 확인하고 실제 학교 계정의 반환 값을 최소 연동에서 검증한다. 현재 재학·도서관 위임 권한을 증명한다고 표시하지 않는다. 나머지 실제 연동/샘플 경계는 아직 미정이므로 티켓은 열어 둔다.

2026-09-26 심화 조사 근거: [외부 서비스 연동 조사와 권고안](../research/external-integrations.md). 권고 후보는 SNUTT picker snapshot, 행샤 서버 캐시, 도서관 공식 예약 이동 후 승인 API 확장, 승인된 셔틀 feed다. SSO는 공식 신청 제도가 있지만 학생 팀·책임 기관·학교 IP/도메인 조건을 먼저 확인해야 한다. 사용자가 세 흐름 모두 필수라고 한 범위는 유지한다. 링크·demo로 충분한 기능과 실제 연동이 필요한 기능의 완료 기준은 아직 합의되지 않았으므로 이 결정은 열린 상태로 둔다.


2026-09-27 최신 사용자 답변과 조사 반영 (이전 권고를 대체):

- 첫 프로토타입부터 실제 연동. SNUTT·행샤는 코드 참고만 사용하며 해당 운영 API·picker를 초기 데이터 공급자로 쓰지 않는다. 코드 공개와 데이터 이용 권한은 구분한다.
- [공식 원천 직접 연동 조사](../research/direct-campus-feeds.md): 공식 행사 목록·상세와 생협 당일 식단 공개 GET은 실제 데이터를 반환한다. NestJS 수집기·HTML 파서·DB 캐시가 구현 후보다. 전체 학과/비교과 상세 접근이나 상시 수집 조건까지 확보한 것은 아니다.
- 사용자: “API가 존재하는지 확인해보고 없다면 아예 기능 자체를 추후 MVP로 미뤄도 될 것 같아.” [관정 추가 조사](../research/library-sso-integration.md)에서 외부 앱이 사용할 좌석·예약 API를 확보하지 못했다. API가 전혀 없다고 단정하지 않으며, 현재 첫 프로토타입의 관정 기능을 보류한다. 공식 페이지 이동 대체는 채택하지 않는다.
- [최신 셔틀 조사](../research/shuttle-app-stop-info.md): 사용자 제보에 따라 정류장 기준 정보를 다시 조사해 학교 공지가 안내한 새 서비스의 정상 HTTPS와 조회 경로를 확인했다. 순환/역순환 노선의 위치 표현은 노선도 좌표이며 GPS와 구분한다. 9/27 일요일 새벽 응답에는 운행 차량이 없었으므로 실제 운행 중 갱신·정류장 대응·이용 조건은 미검증이다. 구형 DWR의 인증서 문제를 새 경로의 문제로 간주하지 않는다. 샘플로 대체하지 않으며 사용자가 셔틀 보류를 승인한 것도 아니다.
- OAuth·지도·AI 계정과 키는 아직 없으며 설정 안내가 필요하다. [첫 프로토타입 계정·개발 환경 준비](12-prototype-readiness.md)에서 후속 준비를 추적한다. 셔틀·경로 API 등의 실제 실행은 아직 검증하지 못했으므로 티켓 전체를 닫지 않는다.
